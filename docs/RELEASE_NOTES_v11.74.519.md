# v11.74.519 — первый маршрут доставки: «часики» больше не висят

Собирается из `d78fcbb`. Этот выпуск отвечает на последнюю жалобу владельца:
«друг отправил мне сообщение, сообщение я уже прочитал, а у него так висит
отправка с часиками». Проверять его надо на двух телефонах: А отправляет
личное сообщение, телефон Б свёрнут и заблокирован.

**Сообщение не потеряно — потерялась квитанция о нём.** Это подтверждается
логом с телефона владельца на 518: входящее сохранилось
(`Saved incoming message to chat`), три входящих показаны в чате, квитанция
даже ушла с устройства — `MQTT FANOUT QUEUED: operation=mesh receipt publish
brokers=2` после каждого входящего. Но квитанция уходит без сохранения на
брокере (retain=false) при QoS 1, а это гарантия доставки только
подключённому подписчику. Телефон отправителя в этот момент свёрнут, и
разбудить его нечем: за всё время на этом устройстве не зарегистрировалось
**ни одного** маршрута доставки — `токен=нет`, `маршрутов=0`,
`фаза=failed`, 17 попыток пробуждения подряд `not_registered`, при том что
сама служба доставки отвечает `/health`. До открытия приложения квитанция
теряется, сообщение уже в статусе «отправлено», поэтому повторной досылки не
происходит. Отсюда и «часики», которые не снимаются, хотя текст прочитан.

**Почему маршрут не мог зарегистрироваться ни при каких повторах.** В доверии
к маршруту было замкнутое кольцо. Запись о регистрации умеет заводить только
хранилище (`PushRegistrationStore.ensure`), а вызвать его можно было только
из регистратора (`PushRegistrationRunner.register`), а попасть туда — только
после успешной проверки доверия (`PushTrustResolver`). Успешная проверка в свою
очередь требовала, чтобы запись уже существовала. Запись нужна для
регистрации, регистрация — для записи: кольцо не открывалось ни одним
повтором, поэтому маршрутов оставалось ноль навсегда. Рядом знали про эту же
форму и подсыпали кандидатов из закреплённых пинов — не дошёл только
доверительный резолвер. Сам он этот случай и предписывал: «при (пере)регистрации
запись может ещё ждать первого подтверждения».

**Что исправлено.** Ослаблен только один случай: записи нет вообще — и только
для регистрации. Приём не тронут: он по-прежнему требует запись, которую
служба уже подтвердила; запись в неподтверждённом состоянии по-прежнему не
даёт доверия ни на приём, ни на регистрацию; доверие по-прежнему дают только
закреплённый пин, локальная привязка и секрет обмена. Тест
`aFirstRegistrationNeedsNoRecordYet` закрывает случай «записи нет» — ровно тот,
который есть на свежей установке; прежний тест покрывал только запись с
`registeredAtMs = 0`.

**2. Квитанция служебного кадра снимает ту блокировку, которую доказала.** Если
принимающий телефон прислал квитанцию про служебный пакет (набор текста,
файл, стикер, группа, реакция, репост, оценка, звонок, приглашение), то
удержание этого пакета больше не снималось, хотя квитанция и есть
подтверждение доставки. Теперь удержание снимается по квитанции для всех
служебных пакетов, включая новые пакеты с префиксом `eph1-`.

**3. Разбор отчёта с телефона — что оказалось не тем, чем казалось.** В отчёте
с 518 есть строка «собеседник не подтверждает ни одной записи». Она неверна:
квитанции приходят, `ACK без локальной строки=186` в той же сессии. Счётчик не
отличает квитанцию служебного кадра (у него строки в чате нет по устройству)
от квитанции настоящего сообщения без строки. Само по себе не смертельно, но
вводило в заблуждение при разборе.

**Как проверить выпуск.** Поставить 519 на оба телефона. На телефоне Б
свернуть приложение и заблокировать экран. С телефона А отправить личное
сообщение. Должно прийти уведомление на экран Б. Затем открыть на Б и смотреть
на телефоне А: часики должны смениться на галочку. В отчёте с телефона А в
разделе `[push]` должно стать `токен=записан` и `маршрутов>0` вместо
`токен=нет` и `маршрутов=0`. Пришлите, пожалуйста, отчёт с отправителя после
проверки.

**Что этот выпуск не закрывает.** Кандидат 519 собирается вместе с исправлением
квитанций служебных кадров (`4119a86`), которое в 518 ещё не вошло. Очередь
пересылки у этого телефона переполнена чужими копиями (3586 на 9 получателей
при лимите 500) — доставка от этого не падает, получатель берёт сообщение
с брокера напрямую, но это лишние очереди. Прямых соседей по-прежнему ноль,
помощник доставки за 148 попыток не выбрал ни одного кандидата.
