# Рой и «торрент» через мобильную связь

**Статус: реализовано (2026-09-18).** Просьба владельца: раздача роем
(файлы групп + APK-обновление) должна работать не только в одной Wi-Fi, а и
через мобильную сеть. Код на Kotlin только (Rust не тронут); JVM-часть
проверена прогоном (формат/сборка + loopback-пробивание), **на телефонах
не проверено**, первый компилятор — CI.

## 1. Почему сейчас не работает через мобильную

Куски и сигналы файловой передачи (предложение, ACK, WANT, фрагменты)
идут только по **прямому каналу**:

- LAN-TCP — только в одной Wi-Fi (одна /24, скан подсети);
- прямой QUIC — за CGNAT мобильной сети не поднимается (тот же диагноз,
  что у звонков, 0j: «новый endpoint на каждую отправку, рубильник 45 с»).

В `FileTransferSender.sendItem`: получатель не досягаем напрямую →
`RecipientOfflineException` → **передача замирает** до прямой связи.
Знаковое же (рой: `fwant`/`fhave`, `upk`/`upwant`) идёт обычными mesh-
сообщениями через брокера — через мобильную доходит. То есть сеть видит
«сосед раздаёт», а сам файл не доходит.

## 2. Что уже решено в проекте (воспроизводим)

Звонки (v11.70.15) умеют пробивать NAT: `data/call/CallUdpChannel` +
`StunCodec` (RFC 5389): сокет, кандидаты (STUN-отражение + IPv6 + IPv4),
пробы каждые 200 мс на все адреса, флаг `seen=1`, фиксация пары
локальный↔удалённый, keep-alive 4 с, смерть 8 с. Симметричный NAT с
обоих концов — не пробивается (штатный исход, остаётся брокер).

## 3. План (только Kotlin, без Rust — ядро не трогаем)

UDP-канал для файловых пакетов, тот же движок пробивания, тот же
формат текста, что и у LAN-пути (`apu-file1|…`, содержимое уже
зашифровано ключом файла). Брокер при этом остаётся сигнальным и
запасным.

### 3.1 Канал `FileUdpChannel` (новый, `data/file/`)

- Один сокет на собеседника (как сокет на звонок). Потоки-читатель и
  пробер, как в `CallUdpChannel`.
- Датаграммы (магика `APUUDP01`, ≤1231 байт — в MTU без фрагментации):
  - **проба** `kind=0`: `seen` + подписанная привязка ключа обмена
    отправителя (≤512 Б). Получатель проверяет подпись и `pk_`-узел
    (те же `verifyFileExchangeBinding`/`fileExchangeBindingNodeId`, что
    в рое) — чужие пробы отбрасываются;
  - **данные** `kind=1`: `sessionTag(12 Б) | fragId:u32 | seq:u16 |
    cnt:u16 | part(≤1200 Б)` — часть base64-текста `apu-file1|…`;
    сборка по `fragId` (TTL 10 с, LRU), собранный текст уходит в
    `routeIncoming(senderId, "direct", …)` — **тот же приёмный путь,
    что и у LAN**: ни приёмник, ни рой, ни APK-сидер не знают, что кусок
    приехал по UDP.
- `sessionTag` объявляется в сигналах; данные принимаются только от
  совпавшего тега (связка с подписанным сигналом через брокера).

### 3.2 Сигналы обмена кандидатами (через брокера — доходят по мобильной)

Текст, не запечатывается (как `APULAN1`: адрес + публичная привязка,
секрета нет; добавлен в белый список `sealOutgoing`):

- `APUUDP1|ufseek|b64(привязка)|адресы;…|sessionTag` — «я хочу прямой
  канал, вот мои UDP-кандидаты»;
- `APUUDP1|ufcand|b64(привязка)|адресы;…|sessionTag` — ответ: «я открыл
  канал, вот мои кандидаты, бей».

Отправляет первый файл-пакет → `ufseek` (не чаще раза в 30 с на
собеседника). Получивший `ufseek` открывает свой канал, шлёт `ufcand`,
обе стороны начинают пробы. Брокерные пути сигналов — те же durable-
mesh-сообщения (`RustBridge.sendMessage`), что и весь рой.

### 3.3 Цепочка `directSend` в роутере (было: LAN → QUIC)

```
LAN (одна Wi-Fi) → UDP-HP (пробито/пробивается) → QUIC
→ брокер (только если собеседник в сети по presence) → иначе пауза
```

- `trySend` UDP — когда канал OPEN; пока пробиваем — пакеты уходят
  дальше по цепочке (QUIC/брокер), и канал всё равно соберётся.
- Брокер-фолбэк — сигнал живучести: мобильная + симметричный NAT с двух
  сторон. Медленно (троттлинг брокера), но файл доходит; передача
  перестаёт «умирать» без прямой связи.
- Режим работы на собеседника (LAN/UDP/QUIC/БРОКЕР) роутер помнит:
  - **K3-бинарный путь (APUF) остаётся за QUIC**: если прямой режим
    собеседника — UDP, APUF не включается (`onFcap` не помечает,
    `binarySend` понижает помеченное в текстовый путь — `demoteBinary`
    в `FileTransferSender`). Текст по UDP несёт те же фрагменты, что и
    LAN — потерянные датаграммы добираются WANT/ACK-механизмом
    (протокол идемпотентен по (transferId, chunkIndex)).

### 3.4 Что автоматически получает от этого рой

`GroupFileSeeder` (файлы групп, полосы от нескольких сидов) и APK-сидер
(`apkseed`) шлют пакеты через те же `directSend`/`binarySend` — мобильная
работает для них без отдельной доработки. Сигналы роя (`fwant`/`upk`/…)
и так ходили через брокера.

## 4. Где живёт

- `data/file/FileUdpWire.kt` (новый) — чистый формат: датаграммы,
  сигналы, сборщик (JVM-тесты без Android).
- `data/file/FileUdpChannel.kt` (новый) — сокет, STUN (переиспользует
  `StunCodec`), пробы, фиксация, менеджер каналов на собеседника.
- `data/file/FileTransferRouter.kt` — цепочка `directSend`, ветка
  `routeIncoming` для сигналов, режимы, `onFcap`/`binarySend` под UDP.
- `data/file/FileTransferSender.kt` — `demoteBinary` (APUF → текст).
- `data/RustBridge.kt` — `sealOutgoing`: сигналы `APUUDP1` не
  запечатываются (как `APULAN1`).

## 5. Границы и честность

- STUN — внешний ресурс (stun.l.google.com / stun.cloudflare.com, только
  отражение адреса; как у звонков). Нет STUN/DNS — остаются свои адреса
  (IPv6 через мобильную часто работает напрямую).
- Симметричный NAT с обеих сторон — UDP не пробьётся; остаётся
  брокер-фолбэк (медленно). Это потолок, а не баг.
- Проверено на JVM в песочнице (2026-09-18): формат/сборка датаграмм и
  сигналов (41 проверка), протокол пробивания на loopback (handshake
  `seen=1`, доставка фрагмента 5.6 КиБ в обе стороны, отклонение чужого
  `sessionTag`, устойчивость к чужим пробам). **На телефонах и в реальном
  NAT не проверено; первый компилятор — CI.** Лог: `FileUdpChannel:
  udp punched for …`, `FileUdpChannel: udp candidates …`, `FileUdpChannels:
  ufseek sent to …`.
- Датаграммы не шифруются на этом слое — содержимое уже шифр (ключ
  файла), привязки подписаны; та же модель, что у LAN-пути.
- `binarySend` стал свойством класса (не локальный лямбда в init), чтобы
  не было forward-ссылки на `senderLocal`; `return@binarySend` в Kotlin
  не резолвится — понижение через if/else.
