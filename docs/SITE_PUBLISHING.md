# Автоматическая публикация релиза на сайт apu.clan.su

Владелец потребовал: «когда выпускаем релиз с новыми файлами, они должны
автоматически загружаться на сайт». Здесь — как это работает и что нужно
сделать владельцу один раз, чтобы автоматика включилась.

## Как это работает

1. Сборка релиза (тег `v*`) собирает APK и из него же — **9 zip пакетов
   функций + `feature-packs.json`** (`scripts/release/make-feature-packs.py`)
   и прикладывает всё к GitHub Release вместе с APK и контрольной суммой.
2. Релиз сначала черновик: владелец проверяет и публикует его для всех.
3. В момент публикации срабатывает workflow **Publish release to official
   site** (`.github/workflows/site-publish.yml`). В текущей ветке подготовлено
   изменение для следующих релизов: он сверяет файлы с GitHub Latest и
   загружает на uCoz в `/downloads` под временными именами; размер сверяется
   до переименования в публичное имя. Порядок: zip пакетов →
   `feature-packs.json` → `app-release.apk` → `latest.json` последним. Затем
   файлы по HTTP скачиваются и проверяются по размеру и SHA-256.
4. Пререлизы на сайт не попадают; ручной запуск тоже требует именно stable
   Latest. Это изменение ещё не входило в tag-сборку v11.74.508: её старый
   публикатор во время медленной передачи раздавал неполный APK.

Переименование одного файла не делает весь набор атомарным: до смены
манифеста старые клиенты могут увидеть несовпадение хешей и должны отклонить
такой файл. FTP-сервер должен поддерживать SIZE и замену существующего имени
через RNTO; отказ не удаляет старый публичный файл. Окончательная проверка
загруженных байтов обязательна. При аварии может остаться временный файл с
префиксом `apumir-stage-`, который сам по себе не является публичным APK.

Телефоны забирают пакеты именно оттуда: сначала
`https://apu.clan.su/downloads/feature-packs.json`, затем сам zip; если
сайт не отвечает — рой соседей (docs/FEATURE_PACKS.md).

## Независимая проверка выпуска

Workflow **Verify release assets and site** не публикует и не изменяет релиз.
Он сверяет оба APK с checksum и GitHub, проверяет package/version и все три
ABI, сравнивает подписи с предыдущим stable отдельно для Android API 26–27 и
28–35. Для draft проверка на этом заканчивается; после публикации и окончания
загрузки на сайт она дополнительно скачивает APK и девять пакетов с сайта и
сверяет их реальные SHA-256 с GitHub/манифестом. Если ключ намеренно меняется,
разные сертификаты требуют отдельной проверки lineage, а не автоматического
объявления совместимости.

Ручной запуск через Actions → **Verify release assets and site** доступен, когда
workflow существует в default-ветке; затем можно выбрать ветку и тег. В этой
Arena-сессии `main` не меняется. На `arena/**` проверка запускается push-ем с
`[verify-publication-draft]` или `[verify-publication-public]` в сообщении
коммита, если изменён workflow, скрипт или tracker. GitHub не показывает draft
токену только с чтением, поэтому job draft получает `contents: write`, хотя
проверочный скрипт ничего не публикует; job public ограничен `contents: read`.
В исходниках есть двенадцать автономных тестов этой проверки; они не
заменяют реальную загрузку с сайта или установку на устройствах.

Для разбора зависшей публикации существует **Inspect site publication (read
only)**: на `arena/**` она запускается push-ем с `[inspect-site-publish]` при
изменении её workflow, скриптов или tracker. Диагностика читает только
публичные метаданные сайта и ход публикации, не имеет FTP-секретов и не
выводит лог целиком. Текущий лог выполняющегося job может быть недоступен;
имя последнего начатого файла не означает, что он загружен. Она также
потоково хеширует один снимок APK, но не проверяет пакеты и не гарантирует,
что сайт не изменится во время загрузки. Она не заменяет независимый public
verifier выше.

Отдельный **Probe site FTP staging** проверяет совместимость FTP: только при
специальном push-маркере `[probe-ftp-staging]` он создаёт два уникальных
маленьких временных файла в каталоге загрузок, проверяет SIZE и замену одного
другим и пытается удалить оба. Существующие release-файлы он не меняет;
неудачная уборка выводится как ошибка. До и после пробы он сверяет фактический
сайт с GitHub. Проба проверяет операции сервера, но не доказывает атомарность
переименования при сбое и не публикует новую версию.

## Что сделать владельцу (один раз)

### 1. Отдельный FTP-доступ на uCoz

1. Откройте панель управления сайтом apu.clan.su на uCoz.
2. Найдите раздел FTP (обычно «Безопасность» → пароль FTP / доступ по FTP):
   там видны хост и логин. Задайте **отдельный пароль только для FTP**
   (FTP у uCoz без шифрования: пароль нельзя использовать где-то ещё).
3. **Пароль в чат не присылайте и в репозиторий не записывайте** — только
   в секреты GitHub (следующий шаг).

### 2. Три секрета в GitHub

Откройте `github.com/vzhem/APUMIR` → **Settings** → **Secrets and
variables** → **Actions** → **New repository secret** и создайте:

| Имя секрета | Что вписать |
|---|---|
| `APU_UCOZ_FTP_HOST` | Хост FTP из панели uCoz |
| `APU_UCOZ_FTP_USER` | Логин FTP из панели uCoz |
| `APU_UCOZ_FTP_PASSWORD` | Отдельный FTP-пароль из шага 1 |

Каталог на сайте по умолчанию `/downloads`. Если когда-нибудь понадобится
другой: Settings → Secrets and variables → Actions → вкладка **Variables**
→ `APU_UCOZ_FTP_REMOTE_DIR`.

### 3. Проверка после следующего релиза

1. GitHub → **Actions** → workflow **Publish release to official site** —
   должен быть зелёным.
2. Откройте `https://apu.clan.su/downloads/feature-packs.json` — там
   версия релиза и 9 пакетов с контрольными суммами.
3. В приложении: Настройки → Дополнительные функции → включить пакет —
   статус «Скачиваем с официального сайта…», затем «Скачано».

В подготовленной версии workflow отсутствие FTP-секретов, ошибка проверки
размера или отказ переименования делают job красным, а не создают ложный
зелёный результат. Текущая проверенная публикация v11.74.508 выполнена
предыдущей версией workflow.

### Ручной повтор

Actions → **Publish release to official site** → **Run workflow** →
указать тег **текущего стабильного Latest**, а не старой версии. Если после
скачивания релиз сменится, новый публикатор прекратит дальнейшую замену файлов.

## Загрузка на сайт — тоже кусками по 100 МБ

Подготовленный staged-публикатор допускает один FTP-файл не более 100 МБ;
файл большего размера он **отклоняет**, а не загружает целиком. Скрипт
`scripts/release/ftp_upload.py` отдельно реализует FTP APPE/REST с паузами,
но в staged-публикатор пока не подключён. Поэтому staged-загрузка файлов
более 100 МБ ещё не реализована и не должна считаться работающей. Отдельный
REST-канал ниже сохраняет нарезку и паузы, если настроен приёмник.

## REST-передачи кусками по 100 МБ (система готова)

Владелец потребовал готовую систему на случай больших файлов: разрезка
на REST-передачи **максимум по 100 МБ** с **задержкой 5 минут** между
кусками. Сейчас таких файлов у нас нет (крупнейший пакет — 37 МБ), но
система реализована и проверяется тестами в каждом CI:

- `scripts/release/chunked_upload.py`: режет файл на куски ≤100 МБ,
  пишет манифест `{файл}.parts.json` (SHA-256 каждого куска и файла
  целиком), передаёт куски по одному (`PUT`, токен — только из
  окружения), пауза 300 секунд между передачами, манифест — последним.
- Повторный запуск не передаёт уже принятые куски (проверка `HEAD`).
- `--reassemble <каталог> <файл>` собирает файл обратно и сверяет SHA-256.
- В workflow публикации шаг REST-канала включается сам для любого файла
  больше 100 МБ, когда владелец задаст секреты `APU_UPLOAD_REST_BASE`
  (адрес приёмника) и `APU_UPLOAD_TOKEN`. Пауза меняется переменной
  `APU_UPLOAD_DELAY_SECONDS` (по умолчанию 300).

Запуск вручную (пример):

```bash
APU_UPLOAD_TOKEN=… python3 scripts/release/chunked_upload.py \
  --base https://example.org/upload app-release.apk
python3 scripts/release/chunked_upload.py --dry-run app-release.apk
```

## Безопасность

- Секреты живут только в GitHub Secrets; в коде, документах и чате их нет.
- Пакеты на сайте принимаются телефоном только при совпадении SHA-256 с
  манифестом; APK — при совпадении с `latest.json` (как раньше).
- FTP без TLS: отдельный пароль, смените его, если он где-то засветился.

Страж автоматики: `scripts/ci/check-site-publishing.py` (каталог пакетов
в сборке совпадает с приложением, workflow на месте, нарезка и паузы
проверены тестами).
