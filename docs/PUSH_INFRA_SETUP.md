# Подготовка доступа к инфраструктуре push через GitHub

Эта памятка нужна **для подготовки**, не для включения push. Мы ещё не
разворачивали сервер, Android не регистрирует FCM и не обрабатывает удалённые сигналы.
После настройки проверка будет только читать состояние Cloudflare и проверять
формат конфигураций; она не создаст Worker, не передаст ему секреты, не войдёт в
Google и не отправит уведомление. О готовой доставке это ничего не говорит.
Текущее состояние разработки — в [трекере](APP_DELIVERY_TRACKER.md).

**Не присылайте в чат никакие токены, ключи, JSON или скриншоты со значениями.**
Не добавляйте их в файлы Git, логи, задачи и релизы. Значения вводятся только
в доверенном интерфейсе GitHub. Если приватный ключ попал в переписку или другое
непредназначенное место, считайте его скомпрометированным, даже если сообщение
удалено. Рекомендуемая мера — отозвать именно раскрытый ключ в Google и заменить
его, предварительно проверив последствия для приложений. Владелец отказался от
удаления раскрытого ключа и попросил вернуться к его замене после того, как всё
заработает; без отдельного согласования ничего не удалять и не менять. Владелец
позднее подтвердил, что текущий серверный ключ в защищённом окружении новый и
не попадал в переписку. Это сообщение владельца, а не независимая проверка
действительности или прав ключа. Ранее раскрытый ключ нельзя использовать для
авторизации или развёртывания. Замена секрета не отзывает старый ключ, а отзыв
может прервать приложения и не отменяет уже выданные краткосрочные токены.
Справка: [отзыв ключа Google](https://cloud.google.com/iam/docs/keys-create-delete).

## 1. Защитить окружение GitHub

Интеграция разработки видит репозиторий, но не смогла создать окружение из-за
ограничения прав API (HTTP 403), поэтому это должен сделать владелец:

1. Откройте [Settings → Environments](https://github.com/vzhem/APUMIR/settings/environments)
   репозитория `vzhem/APUMIR`, создайте окружение **`apu-push-staging`**.
   Убедитесь, что вы настраиваете именно его, а не секреты всего репозитория.
2. В **Deployment protection rules** поставьте галочку **Required reviewers**,
   в поле введите `vzhem` и выберите этого пользователя из списка. Галочку
   **Prevent self-review** не ставьте. Снимите галочку **Allow administrators
   to bypass configured protection rules**: тогда администраторы не смогут
   обходить проверку. Нажмите кнопку сохранения правил (**Save protection rules**).
3. В **Deployment branches and tags** выберите **Selected branches and tags** и
   добавьте ровно одно правило типа **Branch**, без звёздочек:
   `arena/1266946d-apumir`. Не добавляйте правила для тегов или других веток.
4. Сохраните настройки. Только потом добавляйте секреты **внутри этого
   окружения**, а не в Repository secrets. Если интерфейс не предлагает эти
   защиты, остановитесь и сообщите об этом без значений секретов.

На публичном репозитории эти правила доступны для текущих планов GitHub; перед
одобрением всё равно необходимо проверить точный коммит и код: утверждённый job
получает секреты окружения. Ограничение ветки не заменяет доверия к её коду.
Документация GitHub: [Managing environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).

## 2. Секреты Cloudflare для проверки без записи

В том же окружении добавьте два **Environment secrets**:

| Имя | Что сохранить |
| --- | --- |
| `APU_PUSH_CLOUDFLARE_ACCOUNT_ID` | ID выбранного аккаунта Cloudflare: 32 шестнадцатеричных символа в нижнем регистре. |
| `APU_PUSH_CLOUDFLARE_TOKEN` | Отдельный API token для этого аккаунта с доступом только **Account → Workers Scripts → Read**. |

Создайте токен в Cloudflare с ограничением только на нужный аккаунт. Для этой
проверки **не нужны** глобальный API key, право редактирования Workers, доступ к
DNS или другим аккаунтам. Право чтения списка скриптов может раскрывать сведения
об имеющихся Workers, поэтому токен тоже считается секретом. В дальнейшем для
развёртывания нужен отдельный токен с правом записи; расширять этот токен не
нужно. Справка Cloudflare: [API tokens для CI](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/)
и [Workers permissions](https://developers.cloudflare.com/workers/authorization/).

### Отдельный токен для создания выключенного Worker

Владелец сообщил, что создал `Edit`-токен, но сначала сохранил его в
`APU_PUSH_CLOUDFLARE_TOKEN`, предназначенный для `Read`. Позже он сообщил, что
сохранил `Edit` отдельно в `APU_PUSH_CLOUDFLARE_DEPLOY_TOKEN` и выполнил
инструкцию по восстановлению отдельного `Read`-токена. На предыдущем снимке при
создании `Edit` ещё стояло `All accounts`; позднее владелец отдельно подтвердил
выбор одного аккаунта APU и только `Account → Workers Scripts → Edit` без других
разрешений. Уровень секретов, права, область и работоспособность deploy-токена
независимо не проверены; GitHub не показывает сохранённые значения.
[Read-only preflight](https://github.com/vzhem/APUMIR/actions/runs/43353976959)
после отдельного одобрения прошёл на `68c4127`: токен активен и может читать
Workers выбранного аккаунта, project ID Firebase совпадают, RSA проверен локально.
Он не подтверждает, что токен имеет только `Read`, не использует токен
развёртывания и не проверяет права `Edit`, Google OAuth, FCM или доставку.

Владелец сообщил, что проверил разрешения токена `APU Push Deploy`; при повторной
проверке используйте следующие шаги, не показывая значение:

1. Откройте [Cloudflare → API Tokens](https://dash.cloudflare.com/profile/api-tokens)
   под тем пользователем, который создавал токен. Если создавали токен аккаунта,
   используйте **Manage Account → API Tokens** этого аккаунта.
2. Найдите `APU Push Deploy` и откройте просмотр или редактирование настроек
   токена через меню рядом с ним. Посмотрите все политики и разрешения, но не
   нажимайте **Roll**, **Revoke** или удаление; токен в чат не копируйте.
3. Должно быть только **Account → Workers Scripts → Edit**, без DNS, Workers
   Routes и других разрешений. Один аккаунт APU владелец уже подтвердил. Если
   права отличаются или экран непонятен, остановитесь и сообщите только об этом;
   значения и снимки экрана с ними не присылайте. Само чтение настроек ничего не
   развёртывает. [Справка Cloudflare](https://developers.cloudflare.com/fundamentals/api/get-started/create-token/).

Если токен ещё не создан, в [Cloudflare API Tokens](https://dash.cloudflare.com/profile/api-tokens)
выберите **Create Token → Start from scratch → Start with an Account policy**
(в старом интерфейсе — **Create Custom Token**). Разрешение — **Account → Workers
Scripts → Edit**, ресурсы — только тот же аккаунт, где находится APU. Доступ к
DNS и Workers Routes не нужен. Можно задать короткий срок действия; ограничение
по IP для GitHub runners оставьте пустым. Скопируйте токен один раз и сохраните
его только как **Environment secret** `APU_PUSH_CLOUDFLARE_DEPLOY_TOKEN` в
[окружении `apu-push-staging`](https://github.com/vzhem/APUMIR/settings/environments).
Не присылайте токен, ID, JSON или скриншоты со значениями в чат. Если не получается
найти нужное право, остановитесь и сообщите только название шага без секрета.

**Важное ограничение:** такой токен ограничен аккаунтом, но может изменять и
другие Workers в этом аккаунте. Проверки в коде не ограничивают его права на
стороне Cloudflare. Не использовать глобальный API key или роль Owner. После
сохранения напишите только «готово»; это не запускает и не одобряет deployment.
Перед отдельным запуском агент должен прислать ссылку и точный SHA, а владелец —
проверить код и подтвердить защищённый job. Действующий relay и DNS менять не
планируется. Действительность и достаточность нового токена пока не проверены.

### Если проверка отклонила формат Account ID

Сообщение `cloudflare_account_invalid` означает, что значение
`APU_PUSH_CLOUDFLARE_ACCOUNT_ID` не прошло локальную проверку формата. В этом
случае запросы к Cloudflare и Google ещё не выполнялись; новый токен сам по себе
не нужно пересоздавать, но его реальная действительность ещё не проверена.

1. Откройте [панель Cloudflare](https://dash.cloudflare.com/) и выберите тот же
   аккаунт, которому выдали доступ при создании токена. Перейдите в **Workers &
   Pages**, в разделе **Account Details** нажмите кнопку копирования рядом с
   **Account ID**. Это не **Zone ID** и не API token. Также на странице аккаунта
   можно открыть поиск и выбрать команду **Copy account ID**. Справка:
   [Cloudflare: поиск Account ID](https://developers.cloudflare.com/fundamentals/account/find-account-and-zone-ids/).
2. В [GitHub Environments](https://github.com/vzhem/APUMIR/settings/environments)
   откройте **apu-push-staging → Environment secrets** и нажмите **Update**
   напротив `APU_PUSH_CLOUDFLARE_ACCOUNT_ID`. Вставьте только скопированный ID:
   32 символа `0–9` и `a–f` в нижнем регистре, без кавычек, адреса или пробелов.
3. Сохраните и сообщите агенту «готово», не отправляя ID или скриншоты с ним.
   Остальные секреты не меняйте; новый защищённый запуск потребует отдельного
   подтверждения владельца.

### Если проверка отклонила формат Cloudflare-токена

Сообщение `cloudflare_token_invalid` означает, что полученное значение
`APU_PUSH_CLOUDFLARE_TOKEN` не прошло **локальную проверку формата**; запрос в
Cloudflare ещё не выполнялся, а остальные значения могли ещё не проверяться.

1. Если надёжно сохранили созданный для APU токен, скопируйте его значение
   целиком. Если значение потеряно, создайте отдельный новый токен: в
   [Cloudflare API Tokens](https://dash.cloudflare.com/profile/api-tokens)
   выберите **Create Token**, затем в разделе **Policies** — **Start from scratch →
   Start with an Account policy**. Задайте доступ только **Account → Workers
   Scripts → Read** и ограничьте ресурсы конкретным нужным аккаунтом. Для
   разовой проверки можно выбрать срок **7 days**: после истечения потребуется
   новый токен. Фильтр клиентского IP оставьте пустым, поскольку адреса runner
   GitHub Actions могут меняться. В старом интерфейсе этот вариант может
   называться **Create Custom Token**. Затем проверьте сводку и выберите создание
   токена. Скопируйте показанный токен: Cloudflare показывает его значение один раз.
   Не используйте Global API Key и не давайте право **Edit** для этой проверки.
2. Откройте [GitHub Environments](https://github.com/vzhem/APUMIR/settings/environments)
   → **apu-push-staging** → **Environment secrets**. Напротив
   `APU_PUSH_CLOUDFLARE_TOKEN` нажмите **Update**; если такой записи нет,
   выберите **Add secret** с этим именем.
3. Вставьте **только сам токен**: без `Bearer ` перед ним, кавычек, команды,
   адреса, пробелов и переносов строки. Не подставляйте Account ID вместо
   токена. Сохраните и напишите агенту «готово»; значение и скриншоты с ним в
   чат не отправляйте. Остальные секреты самостоятельно менять не нужно.

Новые пользовательские и аккаунтные API-токены могут начинаться с `cfut_` и
`cfat_` соответственно; старые действующие токены могут не иметь префикса.
Это не проверка действительности токена или его прав. Подробности:
[форматы Cloudflare API-токенов](https://developers.cloudflare.com/fundamentals/api/get-started/token-formats/).

## 3. Серверная учётная запись Firebase

Это отдельная техническая учётная запись, от имени которой сервер в будущем
сможет отправлять сигналы через Firebase. Пока что никакие сигналы не отправляются.

1. Откройте [Service Accounts в Google Cloud](https://console.cloud.google.com/iam-admin/serviceaccounts).
   Вверху выберите проект с тем же **Project ID**, что в `project_info.project_id`
   исходного `google-services.json`, использованного для секрета клиентской
   конфигурации. Одного имени приложения `com.vladimir.messenger` недостаточно:
   одинаковое имя пакета может присутствовать в разных проектах. Если не знаете,
   какой именно файл использован, остановитесь и сообщите агенту без его содержимого.
2. В этом же проекте проверьте, что [Firebase Cloud Messaging API](https://console.cloud.google.com/apis/library/fcm.googleapis.com)
   включён (**API enabled**). Если он выключен, нажмите **Enable**. Старый
   Cloud Messaging API (Legacy) включать не нужно. Сам preflight не проверит
   включение API и право отправки.
3. Вернитесь на страницу **Service Accounts**. Если в этом проекте уже есть
   отдельная созданная для APU push учётная запись, используйте её. Иначе нажмите
   **Create service account** / **Создать сервисный аккаунт**, в поле имени
   напишите, например, `apu-push-fcm`, затем нажмите **Create and continue**.
4. Для новой учётной записи в поле **Select a role** выберите именно **Firebase
   Cloud Messaging API Admin** и нажмите **Continue**, затем **Done**. Это готовая
   роль для FCM: она шире одного права отправки, но не является ролью владельца
   или редактора всего проекта. **Owner** и **Editor** не выбирайте. При наличии
   возможности можно вместо неё создать свою роль только с
   `cloudmessaging.messages.create`. Права ранее существовавшей учётной записи
   нужно отдельно проверить в IAM проекта; сам preflight их не проверяет.
5. В списке нажмите на подходящую учётную запись, откройте вкладку **Keys** и
   выберите **Add key → Create new key → JSON → Create**. На компьютер скачается
   файл `.json`. Это секретный ключ, храните его как пароль.
6. Откройте скачанный файл обычным текстовым редактором и скопируйте **всё** его
   содержимое. Откройте [настройки GitHub Environments](https://github.com/vzhem/APUMIR/settings/environments),
   выберите `apu-push-staging` → **Environment secrets**. Если
   `APU_PUSH_FCM_SERVICE_ACCOUNT` уже существует, нажмите **Update** рядом с ним;
   иначе нажмите **Add secret** и задайте это имя. В поле значения вставьте весь
   текст файла и сохраните. Не вставляйте его в чат или файлы Git. Обновление
   перезапишет значение GitHub, но не отзовёт автоматически старый ключ в Google.
7. После сохранения безопасно удалите временную локальную копию JSON. При
   настройке серверного ключа самостоятельно не меняйте существующий
   `APU_FIREBASE_ANDROID_CONFIG`: это другой, клиентский файл
   `google-services.json`. Серверный ключ нельзя добавлять в приложение или APK.

Если Google не предлагает создать ключ или нужную роль, остановитесь и сообщите
только название шага или текст ошибки **без содержимого ключа**. После настройки
проверка сверит project ID и формат, но не подтвердит вход в Google или права
отправки FCM. При утечке рекомендуется отзыв и замена ключа; решение владельца
для раскрытого ключа описано выше. [Роли Firebase](https://firebase.google.com/docs/projects/iam/roles-predefined-product).

### Если проверка сообщает о разных проектах Firebase

`project_mismatch` означает, что `project_id` серверной учётной записи не
совпадает с `project_info.project_id` клиентской конфигурации, доступной этому
job. Проверка остановилась локально, до проверки RSA-ключа и до запросов в
Cloudflare или Google; действительность и права учётных данных пока не доказаны.

Не нужно искать или сравнивать идентификаторы вручную и не следует сразу
создавать ещё один ключ. Агент может подготовить описанное ниже защищённое
сравнение с контрольной Android-конфигурацией; оно выполняется только после
отдельного подтверждения владельца и не выводит ID или JSON. Если неизвестно,
какой Android-файл является контрольным, не угадывайте и не меняйте секреты:
сообщите об этом агенту без содержимого файлов. Имя приложения или проекта
само по себе не гарантирует совпадение ID, а GitHub не показывает сохранённые
значения секретов.

В GitHub Environment секрет с именем `APU_FIREBASE_ANDROID_CONFIG` может
перекрыть одноимённый Repository secret для защищённого job; обычная сборка без
этого окружения берёт Repository secret. Чтобы это выяснить, откройте
[GitHub Environments](https://github.com/vzhem/APUMIR/settings/environments) →
**apu-push-staging** → **Environment secrets** и посмотрите только, есть ли там
имя `APU_FIREBASE_ANDROID_CONFIG`. Значение не открывайте и не меняйте. Если оно
есть или неизвестно, из какого файла сохранена клиентская конфигурация, сообщите
агенту без значений. Учитывайте источник конкретной клиентской конфигурации,
прежде чем заменять серверный ключ. Не вставляйте серверный service-account JSON
в клиентский секрет или APK.

### Сравнение проектов без ручного поиска ID

Чтобы не искать и не сравнивать ID вручную, отдельная защищённая диагностика
использует Environment secret `APU_PUSH_REFERENCE_ANDROID_CONFIG` в
`apu-push-staging`: в нём должен быть именно контрольный клиентский
`google-services.json`, а не серверный ключ. Владелец уже сообщил, что сохранил
его для текущей проверки; без необходимости не менять этот или другие секреты.
После отдельного подтверждения владельца workflow сравнивает в памяти проект этого
файла с проектами клиентской конфигурации и серверной учётной записи, доступных
job. Он сообщает только, какие из двух совпали с контрольным проектом, без ID и
содержимого файлов. Проверка защиты обращается к GitHub API, но диагностика не
проверяет ключ, не обращается к Cloudflare или Google и ничего не развёртывает.
Это не подтверждает права, доступность FCM, совпадение файлов целиком или доставку.

### Если совпал Android-проект, а серверный — нет

Результат `The GitHub Android configuration refers to the reference project; the
GitHub service account does not` означает только, что `project_id` серверного
JSON в этом job отличается от проекта контрольного Android-файла. Сам файл
Android и клиентский secret по project ID совпали; не нужно их заменять. Это не
доказывает существование второго проекта у владельца, работу ключа или права FCM.

Чтобы подготовить отдельную серверную настройку без ручного поиска ID:

1. Откройте [Firebase Console](https://console.firebase.google.com/) и выберите
   именно тот проект, из которого скачивали контрольный `google-services.json`.
   Если неизвестно, какой это проект, остановитесь: совпадение имени Android-пакета
   само по себе не доказывает совпадение проекта.
2. В проекте откройте **⚙ → Project settings → Service accounts → Manage service
   account permissions**. Откроется Google Cloud для выбранного проекта; не
   переключайте проект. Если открылась страница IAM, перейдите там в **IAM & Admin →
   Service Accounts**.
3. Выберите **Create service account** и задайте новое имя, например
   `apu-push-correct-2`; если занято, выберите другое. Нажмите **Create and
   continue**, добавьте роль **Firebase Cloud Messaging API Admin**, затем
   **Continue → Done**. Роли **Owner** и **Editor** не выбирайте. Эта роль шире
   одного разрешения отправки, но уже роли владельца проекта. При отсутствии
   нужной роли или доступа остановитесь и сообщите название шага без значений.
4. Откройте созданную учётную запись → **Keys → Add key → Create new key → JSON →
   Create**. Скачается новый серверный JSON; не показывайте и не отправляйте его
   в чат. Инструкции Google: [создание service account](https://cloud.google.com/iam/docs/service-accounts-create)
   и [создание JSON-ключа](https://cloud.google.com/iam/docs/keys-create-delete).
5. С согласия владельца откройте [GitHub Environments](https://github.com/vzhem/APUMIR/settings/environments)
   → **apu-push-staging** → **Environment secrets** → **Update** напротив
   `APU_PUSH_FCM_SERVICE_ACCOUNT`; вставьте содержимое нового серверного файла
   целиком и сохраните. Это перезапишет прежнее значение GitHub, но не удалит
   никакую учётную запись и не отзовёт старый ключ у Google. Не меняйте два
   Android-секрета. Ранее раскрытый ключ остаётся скомпрометированным и не должен
   использоваться для авторизации или развёртывания.
6. Сообщите агенту только «готово». Агент повторит защищённое сравнение с новым
   отдельным owner review. Зелёный значок означает, что сравнение выполнилось, но
   сам по себе не означает совпадения проектов, права FCM или доставки.

### Куда сохранить Android-файл по решению владельца

При необходимости сам владелец может сохранить известный `google-services.json`
в [GitHub Actions secrets репозитория](https://github.com/vzhem/APUMIR/settings/secrets/actions)
как **Repository secret** `APU_FIREBASE_ANDROID_CONFIG` (не в `apu-push-staging` и
не в `APU_PUSH_FCM_SERVICE_ACCOUNT`). Если запись есть, используется **Update**;
иначе — **New repository secret**. В значение вставляется полный текст именно
клиентского файла, в котором есть Android-пакет `com.vladimir.messenger`, без
дополнительных кавычек или преобразования в base64. Файл или значение не
присылаются агенту.

Обновление перезапишет прежнее значение, которое GitHub не показывает; если
файлы отличаются, следующие сборки APK получат другую конфигурацию Firebase.
При повторном открытии формы редактирования секрет снова выглядит пустым — это
нормально, сохранённое значение не отображается. Сам локальный файл
`google-services.json` при этом не должен быть пустым. Уже установленные APK
от обновления секрета не меняются. Такая замена сама по себе не доказывает
совпадение с серверным ключом, доступ к Google или готовность push.

## 4. Запуск проверки

1. Когда сохраните настройки и секреты, напишите в чат **«готово»**. Значения
   присылать не нужно. Сейчас самостоятельно запускать проверку не требуется.
2. Агент сначала ещё раз проверит правила GitHub, затем запустит проверку и
   пришлёт её ссылку и точный номер коммита (SHA). Она может остановиться до
   запроса подтверждения, если защита окружения настроена неправильно.
3. Откройте присланную ссылку. Прежде чем нажать **Review deployments → Approve**,
   сверьте SHA и изменения в `.github/workflows/push-infrastructure-preflight.yml`,
   `scripts/ci/push-infra-preflight.py` и используемых файлах. Не утверждайте
   неожиданный коммит или незнакомый код. Если SHA отличается или что-то вызывает
   сомнение, не нажимайте Approve и сообщите об этом. Не включайте Actions debug
   logging. Новая отправка в ветку отменяет ожидающий старый запуск.
4. После подтверждения дождитесь результата. Проверка ещё раз сверит правила,
   затем проверит формат ключа, совпадение проектов и доступ к чтению Cloudflare.
   Сообщите название шага или фиксированную ошибку, если что-то не прошло, без
   секретных значений.

Эта проверка только читает данные: она не развёртывает Worker, не обращается к
FCM и не подтверждает право записи или доставку. Проверки настроек не являются
атомарной блокировкой правил GitHub; администраторы и код должны быть доверенными.
Обычный `workflow_dispatch` может быть недоступен до попадания workflow в default
branch; это не повод менять ветку или запускать чужой код.

## Подготовка разового создания выключенного Worker

В ветке подготовлены `.github/workflows/deploy-disabled-push.yml` и
`scripts/ci/push-disabled-deploy.py`. Они **ещё не запускались с правами записи**.
Владелец отдельно согласился на создание выключенного Worker после автономных
проверок и дополнительного ручного owner review точного SHA в GitHub. Маркер
`[deploy-push-disabled]` запускает подготовительные тесты, после которых job с
правом записи должен ждать review среды `apu-push-staging`; сам маркер не является
подтверждением защищённого job. На момент подготовки этого запроса owner review
ещё нет и запись в Cloudflare не выполнялась. Проверка защиты окружения и
совпадения HEAD повторяется после подтверждения, но не является атомарной
блокировкой ветки или Cloudflare; владелец и код должны быть доверенными. Токен
имеет доступ ко всему выбранному аккаунту, даже если сценарий этого не использует.
Существующие relay, DNS и другие Workers не являются целью.

Вместо проверки списка с последующей безусловной перезаписью сценарий делает
`POST` создания нового Worker с именем из SHA. Документация Cloudflare
[указывает](https://developers.cloudflare.com/workers/platform/infrastructure-as-code/),
что создание отвергается, если имя занято. Только после успешного ответа с
новым ID отправляется версия по этому ID; ссылок на другие Workers, маршрутов
DNS, FCM-ключей и rate-ключа в ней нет. Она также **не содержит binding или
миграции Durable Object**: выключенной проверке хранилище не нужно, а
[Cloudflare предупреждает](https://developers.cloudflare.com/workers/platform/infrastructure-as-code/#considerations-with-durable-objects),
что binding первой версии может зависеть от уже развёрнутой миграции. Неизвестно,
возникла бы ошибка именно с `deploy=true`; эта мера устраняет такую зависимость из
подготовленного запроса. Подключение хранилища позднее требует отдельного плана и
проверки. Файл `wrangler.toml` описывает более широкий прототип с DO; его
`--dry-run` ничего не развёртывает и не является тем API payload, который
проверяется отдельно в локальном workerd. Не запускайте обычный `wrangler deploy`.

Отдельный `GET` сверяет исходные модули и метаданные созданной версии, включая оба
`false`-флага и отсутствие ожидаемых признаков DO; другой `GET` дважды сверяет
имя, новый ID, включённый `workers.dev` и `previews_enabled=false` вокруг проверки
единственной активной версии. Адрес `workers.dev` предполагается **публичным**;
сервис на нём должен отвечать отказом. Для версии без DO могут существовать
[Version URLs](https://developers.cloudflare.com/workers/versions-and-deployments/version-urls/):
сценарий запрашивает их выключение, но фактическое поведение и возможная временная
доступность у провайдера не проверены. `/health` должен ответить `503`; запрос к
нему не содержит токена и использует неперсональный User-Agent вместо стандартного
Python. По [документации Cloudflare](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/#browser-integrity-check-on-workersdev)
стандартные клиенты могут блокироваться до исполнения Worker. User-Agent не
гарантирует прохождения проверки: реальная сеть ещё не испытана. Эти запросы —
отдельные снимки, а не атомарная блокировка: параллельное изменение аккаунта
может произойти между ними или позже. Они не проверяют Google, FCM или доставку.
Формат ответов API и права токена в реальном аккаунте ещё не проверялись; при
несовпадении клиент останавливается после возможного создания, без удаления.

При потере ответа или ошибке после начала создания новый Worker **может уже
существовать**. Не перезапускайте такой job и ничего не удаляйте автоматически:
сначала нужно отдельно изучить состояние аккаунта. Повторное создание занятого
имени, согласно документации, должно быть отклонено, а не обновлять Worker.
В локальных тестах провайдер подменён; exact-модули версии с выключенными
флагами также проверяются локальным workerd. Это не настоящая запись Cloudflare.

## Что остаётся после проверки

Дальше нужны отдельная проверка и развёртывание изолированного сервиса с
выключенными флагами, проверка авторизации и сети Google, реализация Android
FCM/WorkManager/получения/уведомлений, устойчивая дедупликация и испытание всей
цепочки. Само по себе принятие FCM или сервером не доказывает доставку. Не
затрагивать существующий relay и не включать push по результату этого preflight.

Владельцу пока не нужно вручную вставлять или редактировать код в панели
Cloudflare. Отключённый серверный прототип находится в `tools/worker/push/`;
он ещё не развёрнут. Позже для него потребуется отдельно согласованное безопасное
развёртывание и интеграция с Android. Проверочный токен только на чтение не даёт
права развёртывать Worker; существующий relay и DNS менять не нужно.
