# Подготовка доступа к инфраструктуре push через GitHub

Эта памятка нужна **для подготовки**, не для включения push. Сервер ещё не
развёрнут, Android ещё не регистрирует FCM и не обрабатывает удалённые сигналы.
После настройки проверка будет только читать состояние Cloudflare и проверять
формат конфигураций; она не создаст Worker, не передаст ему секреты, не войдёт в
Google и не отправит уведомление. О готовой доставке это ничего не говорит.
Текущее состояние разработки — в [трекере](APP_DELIVERY_TRACKER.md).

**Не присылайте в чат никакие токены, ключи, JSON или скриншоты со значениями.**
Не добавляйте их в файлы Git, логи, задачи и релизы. Значения вводятся только
в доверенном интерфейсе GitHub. Если ключ случайно попал в публичное место,
отзовите его у соответствующего провайдера и создайте новый.

## 1. Защитить окружение GitHub

Интеграция разработки видит репозиторий, но не смогла создать окружение из-за
ограничения прав API (HTTP 403), поэтому это должен сделать владелец:

1. Откройте [Settings → Environments](https://github.com/vzhem/APUMIR/settings/environments)
   репозитория `vzhem/APUMIR`, создайте окружение **`apu-push-staging`**.
   Убедитесь, что вы настраиваете именно его, а не секреты всего репозитория.
2. В **Deployment protection rules** включите **Required reviewers** и укажите
   единственного проверяющего — `vzhem`. Оставьте возможность самостоятельного
   утверждения (не включайте **Prevent self-review**), чтобы единственный владелец
   мог подтвердить проверку. Запретите обход проверок администраторами
   (**Prevent administrators from bypassing configured protection rules**).
3. В **Deployment branches and tags** выберите **Selected branches and tags** и
   добавьте ровно одно правило типа **Branch**, без звёздочек:
   `arena/1266946d-apumir`. Не добавляйте правила для тегов или других веток.
4. Сохраните настройки. Только потом добавляйте секреты **внутри этого
   окружения**, а не в Repository secrets. Если интерфейс не предлагает эти
   защиты, остановитесь и сообщите об этом без значений секретов.

На публичном репозитории эти правила доступны для текущих планов GitHub; перед
одобрением всё равно необходимо проверить точный коммит и код: утверждённый job
получает секреты окружения. Ограничение ветки не заменяет доверия к её коду.
Документация GitHub: [Managing environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).

## 2. Секреты Cloudflare для проверки без записи

В том же окружении добавьте два **Environment secrets**:

| Имя | Что сохранить |
| --- | --- |
| `APU_PUSH_CLOUDFLARE_ACCOUNT_ID` | ID выбранного аккаунта Cloudflare: 32 шестнадцатеричных символа в нижнем регистре. |
| `APU_PUSH_CLOUDFLARE_TOKEN` | Отдельный API token для этого аккаунта с доступом только **Account → Workers Scripts → Read**. |

Создайте токен в Cloudflare с ограничением только на нужный аккаунт. Для этой
проверки **не нужны** глобальный API key, право редактирования Workers, доступ к
DNS или другим аккаунтам. Право чтения списка скриптов может раскрывать сведения
об имеющихся Workers, поэтому токен тоже считается секретом. В дальнейшем для
развёртывания потребуется отдельно согласованный токен с минимальными правами
записи; расширять этот токен сейчас не нужно. Справка Cloudflare:
[API tokens для CI](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/)
и [Workers permissions](https://developers.cloudflare.com/workers/authorization/).

## 3. Серверная учётная запись Firebase

1. Выберите **тот же Firebase/Google Cloud проект**, для которого ранее была
   сохранена Android-конфигурация `APU_FIREBASE_ANDROID_CONFIG` для приложения
   `com.vladimir.messenger`. Включённый Cloud Messaging API v1 сам по себе не
   подтверждает, что выбран правильный проект.
2. В Google Cloud создайте отдельный **service account** для push. На проекте
   ему понадобится право `cloudmessaging.messages.create`: предпочтительна
   отдельная минимальная роль; если создать её нельзя, используйте встроенную
   **Firebase Cloud Messaging API Admin**, понимая, что она шире одного права.
   Не назначайте Owner/Editor проекта. Проверьте, что включён Firebase Cloud
   Messaging API. [Перечень ролей Google](https://docs.cloud.google.com/iam/docs/roles-permissions/firebasecloudmessaging).
3. Создайте для этой учётной записи JSON-ключ. Полное содержимое файла поместите
   в **Environment secret** с именем `APU_PUSH_FCM_SERVICE_ACCOUNT`, затем
   безопасно удалите временную локальную копию. Ключ разрешает действовать от
   имени service account, поэтому хранить и передавать его нужно как пароль.
4. Существующий `APU_FIREBASE_ANDROID_CONFIG` — это **клиентский**
   `google-services.json`, а не service-account JSON. Не заменяйте его серверным
   ключом и не добавляйте серверный ключ в Android или APK. Проверка сверит
   project ID и формат, но не подтвердит возможность входа в Google или права
   отправки FCM. Ключи можно и нужно ротировать/отзывать при подозрении на утечку.

## 4. Запуск проверки

Сообщите в чат только **«готово»**, без значений. Агент отправит отдельный
зафиксированный коммит с маркером запуска на разрешённой ветке и сообщит его
SHA. Файл workflow ещё находится в рабочей ветке, поэтому обычный
`workflow_dispatch` в интерфейсе может быть недоступен до попадания workflow
в default branch; это не повод менять ветку или запускать чужой код.

Порядок:

1. Откройте **Actions → Push infrastructure preflight (read only)** и проверьте,
   что запущен именно сообщённый SHA из ветки `arena/1266946d-apumir`. Job
   `protection-check` проверит настройки окружения без доступа к его секретам. Ошибка здесь
   означает, что надо исправить правила из раздела 1; не обходите защиту.
2. Перед **Review deployments → Approve** проверьте этот SHA и изменения в
   `.github/workflows/push-infrastructure-preflight.yml`,
   `scripts/ci/push-infra-preflight.py` и используемых им файлах. Не утверждайте
   неожиданный коммит или незнакомый код. Новая отправка в ветку отменяет
   ожидающий старый запуск. Не включайте Actions debug logging: проверка с
   `RUNNER_DEBUG=1` или известными настройками Actions debug остановится до
   доступа к секретам.
3. После утверждения правила окружения проверяются повторно перед доступом к
   значениям; это не атомарный замок настроек GitHub, поэтому доверенный владелец
   должен контролировать администраторов и сам код. Проверка выдаст только
   фиксированный результат без значений.
   Она сверит формат серверного ключа с существующей клиентской конфигурацией,
   активность Cloudflare-токена и чтение Workers в указанном аккаунте. Проверка
   не устанавливает право записи, не развёртывает Worker и не обращается к FCM.
   В случае ошибки сообщите название шага или фиксированный текст без секретов.

## Что остаётся после проверки

Дальше нужны отдельная проверка и развёртывание изолированного сервиса с
выключенными флагами, проверка авторизации и сети Google, реализация Android
FCM/WorkManager/получения/уведомлений, устойчивая дедупликация и испытание всей
цепочки. Само по себе принятие FCM или сервером не доказывает доставку. Не
затрагивать существующий relay и не включать push по результату этого preflight.
