# Подготовка доступа к инфраструктуре push через GitHub

Эта памятка нужна **для подготовки**, не для включения push. Мы ещё не
разворачивали сервер, Android не регистрирует FCM и не обрабатывает удалённые сигналы.
После настройки проверка будет только читать состояние Cloudflare и проверять
формат конфигураций; она не создаст Worker, не передаст ему секреты, не войдёт в
Google и не отправит уведомление. О готовой доставке это ничего не говорит.
Текущее состояние разработки — в [трекере](APP_DELIVERY_TRACKER.md).

**Не присылайте в чат никакие токены, ключи, JSON или скриншоты со значениями.**
Не добавляйте их в файлы Git, логи, задачи и релизы. Значения вводятся только
в доверенном интерфейсе GitHub. Если ключ случайно попал в публичное место,
отзовите его у соответствующего провайдера и создайте новый.

## 1. Защитить окружение GitHub

Интеграция разработки видит репозиторий, но не смогла создать окружение из-за
ограничения прав API (HTTP 403), поэтому это должен сделать владелец:

1. Откройте [Settings → Environments](https://github.com/vzhem/APUMIR/settings/environments)
   репозитория `vzhem/APUMIR`, создайте окружение **`apu-push-staging`**.
   Убедитесь, что вы настраиваете именно его, а не секреты всего репозитория.
2. В **Deployment protection rules** поставьте галочку **Required reviewers**,
   в поле введите `vzhem` и выберите этого пользователя из списка. Галочку
   **Prevent self-review** не ставьте. Снимите галочку **Allow administrators
   to bypass configured protection rules**: тогда администраторы не смогут
   обходить проверку. Нажмите кнопку сохранения правил (**Save protection rules**).
3. В **Deployment branches and tags** выберите **Selected branches and tags** и
   добавьте ровно одно правило типа **Branch**, без звёздочек:
   `arena/1266946d-apumir`. Не добавляйте правила для тегов или других веток.
4. Сохраните настройки. Только потом добавляйте секреты **внутри этого
   окружения**, а не в Repository secrets. Если интерфейс не предлагает эти
   защиты, остановитесь и сообщите об этом без значений секретов.

На публичном репозитории эти правила доступны для текущих планов GitHub; перед
одобрением всё равно необходимо проверить точный коммит и код: утверждённый job
получает секреты окружения. Ограничение ветки не заменяет доверия к её коду.
Документация GitHub: [Managing environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).

## 2. Секреты Cloudflare для проверки без записи

В том же окружении добавьте два **Environment secrets**:

| Имя | Что сохранить |
| --- | --- |
| `APU_PUSH_CLOUDFLARE_ACCOUNT_ID` | ID выбранного аккаунта Cloudflare: 32 шестнадцатеричных символа в нижнем регистре. |
| `APU_PUSH_CLOUDFLARE_TOKEN` | Отдельный API token для этого аккаунта с доступом только **Account → Workers Scripts → Read**. |

Создайте токен в Cloudflare с ограничением только на нужный аккаунт. Для этой
проверки **не нужны** глобальный API key, право редактирования Workers, доступ к
DNS или другим аккаунтам. Право чтения списка скриптов может раскрывать сведения
об имеющихся Workers, поэтому токен тоже считается секретом. В дальнейшем для
развёртывания потребуется отдельно согласованный токен с минимальными правами
записи; расширять этот токен сейчас не нужно. Справка Cloudflare:
[API tokens для CI](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/)
и [Workers permissions](https://developers.cloudflare.com/workers/authorization/).

## 3. Серверная учётная запись Firebase

Это отдельная техническая учётная запись, от имени которой сервер в будущем
сможет отправлять сигналы через Firebase. Пока что никакие сигналы не отправляются.

1. Откройте [Service Accounts в Google Cloud](https://console.cloud.google.com/iam-admin/serviceaccounts).
   Вверху выберите тот же проект, где раньше добавляли Android-приложение
   `com.vladimir.messenger` и скачивали `google-services.json`. Если не уверены,
   выберите проект, где есть это приложение; последующая проверка сверит проект
   с уже сохранённой Android-конфигурацией.
2. Нажмите **Create service account** / **Создать сервисный аккаунт**. В поле
   имени напишите, например, `apu-push`, затем нажмите **Create and continue**.
3. В поле **Select a role** выберите именно **Firebase Cloud Messaging API Admin**
   и нажмите **Continue**, затем **Done**. Это готовая роль для FCM: она шире
   одного права отправки, но не является ролью владельца или редактора всего
   проекта. **Owner** и **Editor** не выбирайте. При наличии возможности можно
   вместо неё создать свою роль только с `cloudmessaging.messages.create`.
4. В списке нажмите на созданную учётную запись, откройте вкладку **Keys** и
   выберите **Add key → Create new key → JSON → Create**. На компьютер скачается
   файл `.json`. Это секретный ключ, храните его как пароль.
5. Откройте скачанный файл обычным текстовым редактором и скопируйте **всё** его
   содержимое. Откройте [настройки GitHub Environments](https://github.com/vzhem/APUMIR/settings/environments),
   выберите `apu-push-staging`, в разделе **Environment secrets** нажмите
   **Add secret**. Имя секрета: `APU_PUSH_FCM_SERVICE_ACCOUNT`. В поле значения
   вставьте весь текст файла и сохраните. Не вставляйте его в чат или файлы Git.
6. После сохранения безопасно удалите временную локальную копию JSON. Не меняйте
   уже существующий `APU_FIREBASE_ANDROID_CONFIG`: это другой, клиентский файл
   `google-services.json`. Серверный ключ нельзя добавлять в приложение или APK.

Если Google не предлагает создать ключ или нужную роль, остановитесь и сообщите
только название шага или текст ошибки **без содержимого ключа**. После настройки
проверка сверит project ID и формат, но не подтвердит вход в Google или права
отправки FCM. При подозрении на утечку ключ необходимо отозвать и заменить.
[Роли Firebase](https://firebase.google.com/docs/projects/iam/roles-predefined-product).

## 4. Запуск проверки

1. Когда сохраните настройки и секреты, напишите в чат **«готово»**. Значения
   присылать не нужно. Сейчас самостоятельно запускать проверку не требуется.
2. Агент сначала ещё раз проверит правила GitHub, затем запустит проверку и
   пришлёт её ссылку и точный номер коммита (SHA). Она может остановиться до
   запроса подтверждения, если защита окружения настроена неправильно.
3. Откройте присланную ссылку. Прежде чем нажать **Review deployments → Approve**,
   сверьте SHA и изменения в `.github/workflows/push-infrastructure-preflight.yml`,
   `scripts/ci/push-infra-preflight.py` и используемых файлах. Не утверждайте
   неожиданный коммит или незнакомый код. Если SHA отличается или что-то вызывает
   сомнение, не нажимайте Approve и сообщите об этом. Не включайте Actions debug
   logging. Новая отправка в ветку отменяет ожидающий старый запуск.
4. После подтверждения дождитесь результата. Проверка ещё раз сверит правила,
   затем проверит формат ключа, совпадение проектов и доступ к чтению Cloudflare.
   Сообщите название шага или фиксированную ошибку, если что-то не прошло, без
   секретных значений.

Эта проверка только читает данные: она не развёртывает Worker, не обращается к
FCM и не подтверждает право записи или доставку. Проверки настроек не являются
атомарной блокировкой правил GitHub; администраторы и код должны быть доверенными.
Обычный `workflow_dispatch` может быть недоступен до попадания workflow в default
branch; это не повод менять ветку или запускать чужой код.

## Что остаётся после проверки

Дальше нужны отдельная проверка и развёртывание изолированного сервиса с
выключенными флагами, проверка авторизации и сети Google, реализация Android
FCM/WorkManager/получения/уведомлений, устойчивая дедупликация и испытание всей
цепочки. Само по себе принятие FCM или сервером не доказывает доставку. Не
затрагивать существующий relay и не включать push по результату этого preflight.
