# Рой прежде внешнего ресурса — статус проверок и ограничения

**Статус на 2026-10-13:** по отдельному решению владельца `v11.74.353`
опубликован как общедоступный Latest для испытаний на телефонах, **без прохождения
функциональных проверок ниже**. Тег указывает на `54f39a35`; релизный CI
`38455291159` прошёл сборку ядра для всех ABI, UniFFI, Gradle-тесты и проверку
подписи APK. GitHub сообщает SHA-256 APK
`ff9059acfe4f6f75322a740007c824fa6cadd421c7f2d796104f9cb8a2bd1414`;
содержимое `SHA256SUMS.txt` подтверждено хешем этого asset. Установка APK и
роевые переходы на реальных устройствах **не проверялись**. Публикация не
означает, что пункты ниже исправлены, что обеспечен нулевой внешний трафик или
что доставка гарантирована. Деплой нового гибернирующего worker владельцем не
подтверждён; APK его не устанавливает. Риски отражены в release notes.

## Обновление 2026-10-26: launcher-safe fallback

Ниже сохранён исторический договор строгого режима для v11.74.353. Для текущей
задачи с ПК-лаунчером/эмулятором он **заменён** bounded-fallback политикой:

- mDNS, multicast и входящий QUIC остаются оптимизацией и получают ограниченное
  окно поиска 20 секунд после старта/смены сети;
- после этого MQTT/WSS остаётся доступен **даже при живом прямом соседе**: один
  подписанный QUIC-сеанс не доказывает, что именно нужный собеседник доступен
  или что у него есть нужные данные;
- для среды, где входящие UDP/LAN-соединения запрещены, основной обходной путь —
  исходящий WebSocket через TLS/HTTPS 443 к relay-брокеру. Он не использует
  localhost и не требует отключения firewall; текущая логика TCP↔WSS reconnect и
  failover сохраняется;
- в «Настройки → Сеть → Сообщения» путь показывается словами «через relay по
  TLS-443», рядом видны ConnAck и последняя ошибка. Это диагностика транспорта,
  а не доказательство доставки конкретного сообщения.

Фактический launcher пользователя и runtime ConnAck пока не проверены. Worker
должен быть задеплоен с MQTT Durable Object binding; его `/mqtt/health` остаётся
проверкой готовности relay, а не новым транспортом.

## Договор с владельцем

1. После старта/смены сети искать соседей по mDNS, сохранённым **непосредственно
   подтверждённым** адресам и подписанному APUX1. Пятьдесят контактов не
   доказывают, что хотя бы один доступен. Не считать MQTT-presence, старую
   lease, запись в азбуке или `send()` доказательством ответа.
2. Спрашивать у роя именно нужную вещь. Если у него есть данные/байты,
   использовать их. Только если прямого подтверждённого пути нет после
   ограниченного окна поиска, спрашивать соответствующий внешний источник
   за недостающим (с таймаутом/лимитами), не держать внешний транспорт, когда
   появился живой сосед. **Выбранный владельцем строгий режим:** даже если
   подключённый сосед не знает нужной вещи, внешний канал закрыт. Это может
   означать пропущенные входящие/неоткрытую ссылку; не маскировать это как
   успешную доставку или «обновлений нет».
3. Передавать другим полезные новые сведения по прямому каналу в разумный
   срок (например, собственный новый IP только как короткоживущую подписанную
   lease, копию азбуки только зашифрованной, APK после проверки байтов).
   Не выдавать неподписанный чужой адрес/адрес из HTTP за проверенный.
   Секреты, тексты сообщений и приватную историю чужих IP не рассылать.
4. Переходы между транспортами должны быть наблюдаемыми. Если нет подписки
   на брокер из-за живого соседа, входящие от старых APK и спящих телефонов
   могут не дойти — владелец **явно** принял такой риск, но это не делает
   потерю сообщений незаметной и не отменяет испытаний.

## Решение владельца 2026-10-15: ручная проверка версии — исключение

Пункт 2 договора (строгий режим) остаётся в силе для **автоматических** проверок
(foreground, background-воркер, авто-опрос): рой прежде внешнего. Исключение
получила кнопка «Проверить новую версию»: на телефоне с живым соседом она
раньше никогда не доходила до GitHub, строка «Скачать v…» не появлялась вовсе, и
раздел «Обновления» выглядел неполным. Теперь кнопка спрашивает рой, **не ждёт
его** и открывает внешний канал (GitHub API, затем наш worker) даже при живом
соседе; окно этого разрешения — 30 минут, при начале загрузки APK продлевается
до 90 минут (файл ~40 МБ на слабом LTE качается дольше получаса), значение
переживает перезапуск процесса, потому что загрузку ведёт DownloadManager.
Пока окно открыто, фоновый цикл 2,5 с не отменяет начатую официальную загрузку.
Новых внешних доменов не добавлено. Итог каждой ручной проверки виден и в
«Логах» (`last_check_result`, `last_check_manual_external_window`), и в тосте:
если ни рой, ни внешний канал не ответили, приложение говорит «проверить не
удалось», а не «обновлений нет».

## Что уже есть в исходниках (НЕ доказано на устройствах)

- Rust: окно поиска 20 с, выбор подтверждённых *открытых* QUIC-соседей с
  повторной выборкой каждые 5 с и TTL 15 с; при них нет STUN и MQTT-сессии,
  возвращение к fallback после потери маршрута; поздний ответ не становится
  «соседом». Подписанный PEX распространяет свой свежий публичный адрес.
- Азбука: прямой запрос живым соседям, хранилище отвечает ACK с SHA-256
  именно записанного конверта; `send()`/старый ACK не считаются копией.
  Отложенное после поиска резервное восстановление вливается в **работающее**
  ядро; следующему доступному соседу зашифрованное обновление предлагается
  из фонового цикла в пределах минуты. При отсутствии ключа/соседа это не
  обещание сохранности на сервере или у роя.
- Обновления: запрос версии у непосредственно доступных сидов, проверка
  свежих предложений APK/патча до GitHub; чтение внешнего патча останавливается
  при закрытии fallback. Активные официальные задания DownloadManager
  отменяются при появлении роя (проверка не реже 2,5 с, пока сервис работает).
- Android: гейт на HTTP реестра, резервных релеев и служебных API, WSS зеркала,
  UDP STUN, автоматические Coil HTTP-превью; установленная модель ML Kit
  работает локально, новый пакет не скачивается при прямом рое. Короткий код
  сначала ищется в ограниченном локальном кеше, затем запрашивается только
  по запечатанному прямому каналу у живых соседей (ответ сверяется с алгоритмом
  worker); лишь после этого допустим запрос `/short/<код>` при отсутствии роя.
  Новый код для браузера никогда не объявляется готовым, пока worker его не
  зарегистрировал: при живом рое делимся длинной ссылкой.

## Известные риски, не устранённые решением о тестовом релизе

| Ситуация | Проблема / обязательная проверка |
|---|---|
| Два устройства одной личности, одно — тень без Rust-ядра | Тень не может проверить живой рой. Строгий гейт сейчас не позволяет ей открыть WSS, через ~45 с она может повысить себя в активное устройство. Нужен прямой защищённый протокол выбора роли/синхронизации или иной доказуемый swarm-first bootstrap. Нельзя ни объявлять зеркало работающим, ни делать постоянное исключение для worker. |
| Официальная загрузка APK | DownloadManager живёт вне процесса: отмена через 2,5 с — ограничение ущерба, **не** гарантия нулевого трафика в интервале гонки, во сне телефона или до запуска ядра. Нужна собственная прерываемая загрузка с проверкой маршрута на каждом чтении и корректным возобновлением. Изображения/HTTP и Google ML Kit тоже могут иметь уже запущенный запрос в момент появления соседа. |
| Сведения, ещё не имеющие peer-протокола | Настройки поддержки, поиск GIF, резервная копия профиля и неполученная прежде мета-информация обновлений пока используют локальный кеш или откладываются при живом соседе, а не получают нужные данные у него. Нужны адресные запросы и контролируемое распространение результатов. |
| Нет прямого соседа | Через 20 с только разрешён fallback: это не доказательство работающего внешнего ресурса, доставки сообщения или того, что новый worker уже задеплоен. Проверить единственный минимальный запрос к соответствующему источнику, таймаут и возврат к рою, в том числе после Doze/смены Wi‑Fi/LTE/NAT. |
| Процессы/ABI | Rust/UniFFI и Android compile CI прошли; релизная сборка и проверка подписи `v11.74.353` прошли. CI генерирует Kotlin bindings из `lib.udl`; лежащая в git копия не является доказательством корректности нового ABI. Нужны два и более реальных устройства, в том числе старая APK. |

## Проверки для подтверждения режима после тестового выпуска

- Блокирующие `cargo check --release --features mqtt-dual-broker`,
  `cargo test --release --features mqtt-dual-broker --lib`, генерация UniFFI,
  **фактически успешная** `:app:compileReleaseKotlin` (Android-шаг в PR теперь
  блокирующий), тесты Kotlin/протоколов.
- На двух и более телефонах: один Wi‑Fi; разные LTE; потеря/смена публичного
  адреса; экран погашен/Doze; наличие 50 **офлайновых** контактов; живой
  сосед без нужного объекта; ответ держателя и отсутствие ответа; новый и
  прежний APK, звонок/тень и восстановление азбуки после переустановки.
- Сетевым счётчиком/pcap подтвердить: **0** DNS/TLS/STUN/MQTT/WSS/HTTP запросов
  к внешним узлам при живом рое (и отсутствие фоновой дочитки), затем
  ограниченный fallback при потере всех подтверждённых соседей и закрытие
  внешних соединений после восстановления. Смотреть не только на логи UI.
- Доказать, что серверные сведения стали доступны прямым соседям без
  неподписанных «свидетельств», а при отсутствии ответа система не ставит
  ложный статус «доставлено». До этих проверок не считать режим подтверждённым;
  `v11.74.352` не перезаписывать и теги 343–352 повторно не использовать.
