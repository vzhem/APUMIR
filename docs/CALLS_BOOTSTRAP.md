# Звонки между абонентами — инструкция для нового ИИ-чата

**Тематический handoff по уже существующим голосовым звонкам APU.** Это не новая
задача на реализацию звонков с нуля: UI, сигнализация и аудиотракт уже есть в коде.
Для общего статуса проекта точка входа — `docs/START_HERE.md`; факты о звонках и
их проверки сверять по этому файлу и журналу `AI_COLLABORATION_NOTES.md`.

## Текущий статус проекта (2026-10-03)

- Общий stable Latest — **v11.74.168**; актуальный срез релиза, ветки и тестов —
  `docs/START_HERE.md` §3. Упоминание v11.29.0 ниже — старый снимок, не Latest.
- Звонки реализованы: ранние звуковые звонки/транспорты выпускались в v11.70.14,
  v11.70.15 и следующих версиях; состояние звонка также входит в зеркало устройств
  начиная с v11.74.130. Наличие кода не доказывает текущий phone-runtime.
- Основные точки текущего кода: `data/call/CallManager.kt`, `CallWire.kt`,
  `CallAudioEngine.kt`, `CallAudioChannel.kt`, `CallBrokerLink.kt`,
  `CallUdpChannel.kt`, `service/CallService.kt`, `ui/screens/call/CallScreen.kt` и

  прочитать журнал по `CallManager`/`CallUdpChannel` и проверить фактический код;
  не использовать старые утверждения «звонков нет», «всё ещё план» или «релиз 11.30».

### 8.2 Проводной формат `APUCALL1` (сигнализация)

Префикс `APUCALL1`, поля через `|`, строки с произвольным содержимым —
base64url без дополнения. Максимум конверта 4 КиБ. `callId` — 32 hex-символа
(16 случайных байт звонящего): вся порядковая защита и дедупликация по нему.
Пакеты:

```
APUCALL1|offer|<callId>|<callerName_b64>|<tsMs>|<lanIp>|<lanPort>|<proto>|<mediaKey_b64>
APUCALL1|ring|<callId>
APUCALL1|accept|<callId>|<lanIp>|<lanPort>|<proto>|<mediaKey_b64>
APUCALL1|reject|<callId>|<reason>       decline | busy
APUCALL1|bye|<callId>|<reason>          end | cancel | timeout | failed
APUCALL1|au|<callId>|<seq>|<tsMs>|<payload_b64>   (голос по текстовому фолбэку, PCM)
APUCALL1|ab|<callId>|<n>|<seq>|<tsMs>|<payload_b64>…   (бандаж n ≤ 8 PCM-кадров)
APUCALL1|ac|<callId>|<n>|<seq>|<tsMs>|<payload_b64>…   (бандаж n ≤ 8 ADPCM-кадров, v11.70.14)
APUCALL1|cap|<callId>|<кодеки через запятую>[|ack]     (возможности стороны, v11.70.14)
APUCALL1|cand|<callId>|<ip>/<port>[,<ip>/<port>…]      (кандидаты прямого UDP, ≤ 6, v11.70.15)
APUCALL1|probe|<callId>|<seen>                          (проба пробивания NAT, seen = 0|1, v11.70.15;
                                                         только внутри шифрованного control по UDP)
```

Правила:

- `lanIp`/`lanPort` — адрес сокета звонка стороны, которая шлёт пакет;
  `-` = «LAN нет, не стучись». Звук идёт на endpoint из `accept` у обеих
  сторон сразу после него.
- `proto` — версия голосового канала: `tcp1` сейчас; `udp1` добавится позже
  без смены формата (кто не понял — работает на `tcp1`).
- `mediaKey` — 16 байт AES-ключа (base64url): в `offer` ключ для потока
  звонящий→принимающий, в `accept` — для обратного. Ездит только внутри
  E2E-зашифрованного текста mesh/QUIC, на сам сокет ключ не попадает никогда.
  Кадры шифруются AES-128-GCM (чистый JVM `Cipher`, nonce из seq), поэтому
  голос закрыт и на LAN-сокете, и на relay. Поле в формате с v1, чтобы формат
  больше не менять.
- messageId для транспортной дедупликации детерминированы:
  `c<callId>o<n>` (offer, попытка n), `c<callId>r`, `c<callId>a`,
  `c<callId>j`, `c<callId>b<n>`, кадры `c<callId>au<seq>`, `cap` —
  `c<callId>p<n>` (n = попытка offer у звонящего, 0 у принимающего), `cand` —
  `c<callId>n<1 звонящий | 0 принимающий>`. Повтор
  offer — каждые 3 с до таймаута 30 с (bounded-очередь relay повторы
  переживёт, дедуп по messageId схлопнет).
- `cap` идёт отдельным пакетом следом за offer/accept (формат offer/accept
  не трогаем: старые сборки разбирают их строго по числу полей, а неизвестный
  kind молча отбрасывают). Нет `cap` от собеседника = старая сборка = только
  PCM и никаких `ac`/моста в его сторону.
- Сигналы посылаются тем же `RustBridge.sendMessage`, что сообщения (плюс
  `sendDirectPayload` как ускоритель по прямому QUIC где есть). Живой звонок,
  офлайн-устойчивость не нужна: `offer` старше 60 с при разборе = пропущенный
  (не зажигать звонок по протухшему пакету из очереди).

### 8.3 Машина состояний

Звонящий: `IDLE → OFFERING (offer, повтор) → RINGING (пришёл ring) →
CONNECTING (пришёл accept, настройка звука ≤10 с) → ACTIVE → ENDING (bye) →
IDLE`; `reject`/таймауты → конец с причиной. Принимающий:
`IDLE → INCOMING (offer) → ожидание пользователя ≤45 с → CONNECTING (accept +
настройка звука) → ACTIVE`; отказ → `reject|decline`, пришёл повторный offer
на активный звонок → `reject|busy`. Обрыв: 5 с без кадров — статус
«восстановление», 20 с — `bye|failed`. Тайминги молчат в UI, показываются
только статусы: «Вызов…», «Гудки…», «Соединение…», таймер разговора.

### 8.4 Медиа-план (голос)

Порядок попыток, всё без новых FFI:

1. **LAN-сокет звонка** (оба в одной сети): `CallAudioChannel` по образцу
   `LanDirectChannel`: отдельный TCP на фиксированном порту **42109** (рядом с
   42108 файлового), текстовый handshake-кадр `APUCALLHS1|<nodeId>|<callId>|<proto>`
   и ответ `APUCALLHS1|ok|<nodeId>`, дальше бинарные кадры
   `[u32 len][u16 codec][u32 seq][u64 ptsMs][payload]`, len ≤ 64 КиБ.
   Отдельный сокет, а не файловый канал, потому что 50 кадров/с нельзя гнать
   через файловый `incomingRoute` (Room-запросы на кадр). endpoint доезжает в
   сигналах, плюс скан /24 по образцу `discoverPeer`, если mesh мёртв.
2. **Прямой UDP через интернет** (`CallUdpChannel`, v11.70.15): один
   UDP-сокет на звонок, открывается вместе с мостом (на offer у принимающего,
   на кнопку у звонящего). Кандидаты: внешний адрес от STUN
   (`stun.l.google.com:19302`, `stun.cloudflare.com:3478`; Binding Request по
   RFC 5389, разбор XOR-MAPPED-ADDRESS в `StunCodec`, проверен векторами
   RFC 5769; DNS ≤ 1,5 с и ответ ≤ 1,5 с на сервер, неудача не фатальна) +
   глобальные IPv6 своих интерфейсов (≤ 2) + site-local IPv4 (≤ 2), всего ≤ 6.
   Список уходит собеседнику пакетом `cand` durable-путём (relay/QUIC) и по
   мосту как control (≤ 3 раз за звонок). Когда есть сокет, ключ моста и
   адреса собеседника — пробивание: на каждый адрес раз в 200 мс уходит
   `probe|<callId>|<seen>` внутри шифрованного `CallLinkWire`-control (тот же
   ключ и тот же счётчик nonce, что у моста), 8 с (16 с, если собеседника
   уже слышно). Адрес собеседника фиксируется только по пробе с `seen=1` или
   по подлинному не-пробному пакету (симметричный NAT: слышать ещё не значит
   быть услышанным); повтор старой пробы с другого адреса отбивается по
   монотонному seq. Дальше медиа как на мосту (`[0xAC]…`), но по 2 кадра
   (40 мс) в датаграмме; keep-alive 4 с, 8 с тишины → CLOSED → голос обратно
   на мост. Джиттер-буфер 4 / 15. Статус в UI: «Через интернет — прямое
   соединение». Симметричный NAT с обеих сторон — ожидаемый отказ, звонок
   остаётся на мосту.
3. **Мост через брокер** (`CallBrokerLink`, v11.70.14): ОДНО постоянное
   MQTT 3.1.1-соединение на весь звонок (чистый Kotlin, `MqttPacket`, без
   ядра и FFI), тема `apucall1/<sha256(callId, nodeId получателя)>` — вне
   `p2pm2/#`, ядро её не видит. QoS0, кадры уходят сразу, приём — блокирующее
   чтение сокета (задержка = сети, а не 5-секундного опроса). Провод
   `CallLinkWire`: control `[0x02][seq u64][AES-GCM(APUCALL1-строка)]`
   ключом `deriveLinkKey(mediaKey звонящего)` (звонящий считает seq от 0,
   принимающий от 2^62); media `[0xAC][codec][n] n×([seq u32][len u16][шифр])`
   — пачки по 4 кадра (80 мс), каждый кадр закрыт медиа-ключом направления как
   на LAN. Рукопожатие: на OPEN шлём `cap`, на чужой `cap` отвечаем
   `cap|…|ack`, любой расшифрованный пакет собеседника = «мост жив в обе
   стороны» (`peerLinkAlive`); до этого `cap` повторяем раз в секунду. Умерший
   мост переоткрываем ≤ 3 раз за звонок с паузой 4 с; после конца звонка мост
   живёт ещё 1,5 с, чтобы ушёл последний `bye`. Сигналы ring/accept/reject/bye
   идут по мосту И по durable-пути (relay + QUIC) — дубли машина глотает.
   Мост поднимается сразу на offer (принимающий) / на нажатие кнопки
   (звонящий), пока телефон ещё звонит. Клиент-id `apc`+10 знаков nodeId+10
   знаков callId (≤ 23, как требует 3.1.1). Брокеры те же, что у ядра
   (`broker.hivemq.com`, `broker.emqx.io`, 1883).
4. **Прямой QUIC** (`RustBridge.sendDirectPayload`): `au` (PCM) или `ac` из
   одного кадра; через мобильную сеть без hole punching не поднимается,
   рубильник 45 с после 2 промахов.
5. **Текстовый фолбэк через ядро** (`ab`/`ac` бандажами по 8 кадров через
   `sendMessageMqtt`) — только для сборок без моста. **v11.70.18:** строка
   уходит в конверте `<мой pk_>|<audioBatchMessageId>|direct|<APUCALL1…>`
   (`CallManager.TEXT_FALLBACK_SCOPE`). До этого она шла голой, приёмник
   ядра резал её как `sender|msgId|chatId|text` → у собеседника рождался
   контакт-призрак «Contact APUCALL1» с обрывком пакета, а голос по этому
   пути не доходил вовсе (`AI_HANDOFF.md` 0n). **Честно владельцу:
   публичные брокеры троттлят ~1 КБ/с, и даже ADPCM (≈ 8 КБ/с) — best-effort;
   гарантия звонка — LAN; для мобильной сети основной путь — прямой UDP
   (п. 2, v11.70.15), запасной на будущее — свой relay (Cloudflare Worker /
   WebSocket), владелец разрешил 2026-09-12.**
   Статус в UI: «Через интернет — сжатый звук, возможна задержка» (мост) или
   «Медленный канал — собеседник не в одной Wi-Fi сети» (фолбэк).
Кодеки: `1 = PCM 16 кГц mono s16le` (LAN, 32 КБ/с), `2 = Opus 16 кГц`
(резерв, MediaCodec), `3 = IMA ADPCM 16 кГц` (`AdpcmCodec`, 164 Б/20 мс,
≈ 8 КБ/с, каждый кадр самодостаточен — потеря пачки не ломает следующие).
Выбор: LAN → PCM; UDP/мост/фолбэк → ADPCM, если собеседник объявил `3` в
`cap`, иначе PCM. Джиттер-буфер: LAN разгон 2 / предел 8 кадров, прямой UDP
4 / 15, мост 10 / 30; опоздавшие кадры (seq) роняем. LAN-сокет умер посреди
разговора → голос переезжает на UDP (если пробит) или на мост с ADPCM и
«интернетным» буфером (обратно на LAN не возвращаемся); UDP умер → обратно
на мост. Порядок транспорта: LAN → прямой UDP → мост → QUIC → текст.

**Внешние ресурсы (решение владельца 2026-09-12): подключать можно и нужно,
но приложение обязано работать при их долгой блокировке.** Правило для
каждого внешнего звена звонков — таймаут + путь без него: STUN — DNS ≤ 1,5 с
и ответ ≤ 1,5 с на сервер, нет ответа → кандидаты только с интерфейсов
(IPv6/LAN) или вовсе без прямого UDP; брокеры — переоткрытие ≤ 3 раз,
hivemq → emqx, нет моста → QUIC / текстовый фолбэк через ядро; ни один из
них не держит сигнализацию — offer/accept/bye всегда идут и durable-путём.
Под блокировкой звонок хуже (задержка, сжатие), но состоится.

### 8.7 Исторический поэтапный план и оставшиеся проверки

1. `CallWire` + `CallStateMachine` + unit-тесты + строка в гейте → гейт.
2. `CallManager` + dispatch в `CoreServerService` + экран звонка + кнопка →
   гейт → два телефона: дозвон, гудки, принять/отклонить/завершить, таймауты
   (звука ещё нет).
3. Звук по LAN (`CallAudioChannel` + `CallAudioEngine` + CallService + GCM) →
   приёмка в общей Wi-Fi: голос в обе стороны, мьют, динамик, обрыв сокета.
4. Звук по прямому QUIC (`au` + Opus) → приёмка через интернет.
5. Relay-фолбэк best-effort + статус «медленный канал». **v11.70.14:** мост
   через брокер + ADPCM + `cap` (п. 8.4/3). **v11.70.15:** прямой UDP + STUN
   + пробивание NAT (п. 8.4/2; «да» владельца на внешние ресурсы 2026-09-12).
   Оба на телефонах через мобильную сеть НЕ проверены; проверять: два
   телефона в разных сетях, лог `CallManager: media channel: direct UDP (...)`
   или `... broker link (...)`, статус на экране, смена сети посреди
   разговора. Следующий шаг — свой relay (Cloudflare Worker / WebSocket).
6. «Пропущенный звонок» строкой в чат (опционально), полировка → «выпускай» →
   релиз v11.30.0 по разделу 3 + бэкап на флешку.
