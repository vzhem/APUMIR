# Звонки между абонентами — инструкция для нового ИИ-чата

**Единственная задача чата: сделать голосовые звонки между абонентами
в мессенджере APU.** Этот файл — точка входа: что за проект, как здесь
работают и с какого места начинать смотреть звонки. Правила картотеки:
одна тема — один документ; факты о звонках дальше живут только здесь
(и в журнале `AI_COLLABORATION_NOTES.md`).

Свежесть: 2026-09-01, релиз **v11.29.0** в latest.

## 4. Где смотреть звонки (стартовая карта)

Звонков в приложении **нет вообще** — ни UI, ни транспорта, ни аудио
(совпадения «CALL» в `uniffi/p2p_core/p2p_core.kt` — это статусы uniffi,
не звонки). Начинать с этих мест:

1. **Транспорт 1:1.** Как ходят личные сообщения и файлы между двумя нодами:
   `data/relay/`, `data/file/` (пример готового wire-протокола поверх ядра:
   оффер/чанки/квитанции), `data/group/GroupWire*` (пример конвертов
   сообщений), `service/` (фоновая доставка). Звонок = новый wire-тип
   (offer/accept/reject/bye + медиа-поток) по тем же рельсам.
2. **Rust-ядро.** `rust-core/src/` — что уже умеет libp2p-узел: темы,
   прямые соединения, relay, LAN-канал (`LanDirectChannel*` в
   `data/file/` — готовый пример прямого канала поверх ядра, пригодится
   для голоса в локальной сети). Новые FFI-методы ядра = правка Rust +
   регенерация биндингов — это делает ПК владельца (`build-rust.ps1`),
   согласовывай минимальную FFI-поверхность.
3. **UI.** Экран чата `ui/screens/chat/ChatDetailScreen.kt` (там уже есть
   иконка видеокамеры в значках тем — место для кнопки звонка), навигация,
   `ui/components/` (образцы: `AnimatedTopicIcon.kt`, `ChatWallpaper.kt`),
   уведомления/рингтон — по образцу существующих уведомлений сообщений.
4. **Аудио.** В приложении ничего нет: потребуются `AudioRecord`/
   `AudioTrack` (режим `VOICE_COMMUNICATION`), разрешение `RECORD_AUDIO`,
   foreground-service для идущего звонка, обработка прерываний
   (`AudioManager`/`TelecomManager`), echo cancellation (`AcousticEchoCanceler`).

## 5. Подход к задаче (план-минимум для приёмки)

1. Кнопка «звонок» в личном чате → экран звонка (исходящий/входящий,
   принять/отклонить/завершить, таймер, статусы «гудки/соединение»).
2. Сигнализация offer/accept/reject/bye доставляется существующей
   relay-доставкой (офлайн-устойчиво не нужно — звонок живой).
3. Голос: сначала **LAN-прямой канал** (оба в одной сети) и/или прямой
   libp2p-поток; fallback — relay через брокер маленькими чанками
   (помнить грабли: брокер терял фрагменты >33 КБ, кадры голоса мелкие).
   WebRTC со внешним STUN — только после явного «да» владельца
   (внешний ресурс = «провод», но решает он).
4. Приёмка владельцем на двух телефонах (Аня + подключит второй):
   дозвон, голос в обе стороны, завершение, обрыв связи.
5. Гейт GREEN → установка → «выпускай» → релиз по разделу 3.

### 8.2 Проводной формат `APUCALL1` (сигнализация)

Префикс `APUCALL1`, поля через `|`, строки с произвольным содержимым —
base64url без дополнения. Максимум конверта 4 КиБ. `callId` — 32 hex-символа
(16 случайных байт звонящего): вся порядковая защита и дедупликация по нему.
Пакеты:

```
APUCALL1|offer|<callId>|<callerName_b64>|<tsMs>|<lanIp>|<lanPort>|<proto>|<mediaKey_b64>
APUCALL1|ring|<callId>
APUCALL1|accept|<callId>|<lanIp>|<lanPort>|<proto>|<mediaKey_b64>
APUCALL1|reject|<callId>|<reason>       decline | busy
APUCALL1|bye|<callId>|<reason>          end | cancel | timeout | failed
APUCALL1|au|<callId>|<seq>|<tsMs>|<payload_b64>   (голос по текстовому фолбэку)
```

Правила:

- `lanIp`/`lanPort` — адрес сокета звонка стороны, которая шлёт пакет;
  `-` = «LAN нет, не стучись». Звук идёт на endpoint из `accept` у обеих
  сторон сразу после него.
- `proto` — версия голосового канала: `tcp1` сейчас; `udp1` добавится позже
  без смены формата (кто не понял — работает на `tcp1`).
- `mediaKey` — 16 байт AES-ключа (base64url): в `offer` ключ для потока
  звонящий→принимающий, в `accept` — для обратного. Ездит только внутри
  E2E-зашифрованного текста mesh/QUIC, на сам сокет ключ не попадает никогда.
  Кадры шифруются AES-128-GCM (чистый JVM `Cipher`, nonce из seq), поэтому
  голос закрыт и на LAN-сокете, и на relay. Поле в формате с v1, чтобы формат
  больше не менять.
- messageId для транспортной дедупликации детерминированы:
  `c<callId>o<n>` (offer, попытка n), `c<callId>r`, `c<callId>a`,
  `c<callId>j`, `c<callId>b<n>`, кадры `c<callId>au<seq>`. Повтор offer —
  каждые 3 с до таймаута 30 с (bounded-очередь relay повторы переживёт,
  дедуп по messageId схлопнет).
- Сигналы посылаются тем же `RustBridge.sendMessage`, что сообщения (плюс
  `sendDirectPayload` как ускоритель по прямому QUIC где есть). Живой звонок,
  офлайн-устойчивость не нужна: `offer` старше 60 с при разборе = пропущенный
  (не зажигать звонок по протухшему пакету из очереди).

### 8.3 Машина состояний

Звонящий: `IDLE → OFFERING (offer, повтор) → RINGING (пришёл ring) →
CONNECTING (пришёл accept, настройка звука ≤10 с) → ACTIVE → ENDING (bye) →
IDLE`; `reject`/таймауты → конец с причиной. Принимающий:
`IDLE → INCOMING (offer) → ожидание пользователя ≤45 с → CONNECTING (accept +
настройка звука) → ACTIVE`; отказ → `reject|decline`, пришёл повторный offer
на активный звонок → `reject|busy`. Обрыв: 5 с без кадров — статус
«восстановление», 20 с — `bye|failed`. Тайминги молчат в UI, показываются
только статусы: «Вызов…», «Гудки…», «Соединение…», таймер разговора.

### 8.4 Медиа-план (голос)

Порядок попыток, всё без новых FFI:

1. **LAN-сокет звонка** (оба в одной сети): `CallAudioChannel` по образцу
   `LanDirectChannel`: отдельный TCP на фиксированном порту **42109** (рядом с
   42108 файлового), текстовый handshake-кадр `APUCALLHS1|<nodeId>|<callId>|<proto>`
   и ответ `APUCALLHS1|ok|<nodeId>`, дальше бинарные кадры
   `[u32 len][u16 codec][u32 seq][u64 ptsMs][payload]`, len ≤ 64 КиБ.
   Отдельный сокет, а не файловый канал, потому что 50 кадров/с нельзя гнать
   через файловый `incomingRoute` (Room-запросы на кадр). endpoint доезжает в
   сигналах, плюс скан /24 по образцу `discoverPeer`, если mesh мёртв.
2. **Прямой QUIC** (`RustBridge.sendDirectPayload`): звук как `au`-пакеты,
   base64-кадры внутри E2E-текста. codec=Opus, если энкодер есть на устройстве.
3. **Relay мелкими чанками** (тот же `sendMessage`): кадры ~20 мс Opus,
   ~30–60 байт → base64 ≤ 90 символов, `au`-конверт далеко под границей
   «33 КБ терялись брокером». **Честно владельцу: публичные брокеры троттлят
   ~999 Б/с — голос по ним НЕ потянет; это best-effort на живом брокере,
   гарантия звонка — LAN и прямой QUIC.** Статус в UI при фолбэке:
   «медленный канал».
Кодеки: `1 = PCM 16 кГц mono s16le` (LAN, безупречно и просто, 32 КБ/с),
`2 = Opus 16 кГц` (MediaCodec, узкие пути). Поздние кадры (seq/pts) роняем.
UDP (`proto=udp1`) — следующий шаг после приёмки TCP-голоса.

### 8.7 Поэтапный план (итерация = гейт на ПК владельца)

1. `CallWire` + `CallStateMachine` + unit-тесты + строка в гейте → гейт.
2. `CallManager` + dispatch в `CoreServerService` + экран звонка + кнопка →
   гейт → два телефона: дозвон, гудки, принять/отклонить/завершить, таймауты
   (звука ещё нет).
3. Звук по LAN (`CallAudioChannel` + `CallAudioEngine` + CallService + GCM) →
   приёмка в общей Wi-Fi: голос в обе стороны, мьют, динамик, обрыв сокета.
4. Звук по прямому QUIC (`au` + Opus) → приёмка через интернет.
5. Relay-фолбэк best-effort + статус «медленный канал»; WebRTC/STUN — только
   по отдельному «да» владельца (внешний «провод»).
6. «Пропущенный звонок» строкой в чат (опционально), полировка → «выпускай» →
   релиз v11.30.0 по разделу 3 + бэкап на флешку.
