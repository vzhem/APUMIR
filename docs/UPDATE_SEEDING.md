# Раздача обновления (APK) роем — проект

**Статус: выпущено в v11.74.0 (2026-09-18, Latest).** Просьба владельца (2026-09-18): (1) доделать систему
«как торрент» — телефоны берут куски файла друг у друга, без сервера;
(2) файл обновления (APK) раздаётся другим телефонам кусками, каждая новая
версия заменяет старую; (3) если APK передан в чат (например с ПК, без
официального релиза) и это новая версия — его можно в настройках отметить
как версию для раздачи, и он раздаётся соседям, у которых версия ниже.

## 1. Что уже есть и почему достаточно

Передача файлов уже «торрент» для групп (К2, v11.70.25): общий манифест
`grp_<метка>` (ядро `create_group_file_manifest`), один ключ, одни
зашифрованные куски; любой, у кого файл есть целиком (авторская копия
`OUTGOING/SEEDING` или своя входящая `INCOMING/COMPLETE`), — сид
(`GroupFileSeeder`): плечи, окна, инвентарь WANT, CANCEL, полосы от
нескольких сидов. **Куски идут только по прямому каналу (LAN/QUIC) —
сервер в данных не участвует**; брокер/LAN несут лишь сигнальные пакеты
несколько килобайт. Разница «личного» файла и файла группы — только в
метке манифеста и в том, КТО может просить/отдавать.

Вывод: APK — ещё одна «группа». Виртуальное сообщество `apkseed` (id
фиксирован, в БД групп его нет), метка манифеста `grp_apkseed` (проходит
ядро `file_transfer::is_group_scope`: буквы/цифры и `-_.:`, длина ≤ 128).
Новая версия — другой файл (своё имя, свой sha256, свои куски), метка одна
на всех: «замена версии» — это поведение раздающего (см. §4), а не новый
формат.

Всё, что ниже, — тонкий слой над существующим механизмом: три маленьких
сигнальных пакета (рой, `GroupWire`), один класс-сид на стороне раздающего
и просителя, карточка в настройках. Файловая машина (манифест, конверты,
куски, ACK, инвентарь, сидер) не трогается.

## 2. Протокол (новые виды пакетов в `GroupWire`)

Старые телефоны вид не знают и молча отбрасывают (установленный для всех
новых видов). Формат — как у `fwant`/`fhave`: `|`-поля, base64 для бинарного.

- `upk` — «я раздаю обновление»: `APUGRP1|upk|<версия>|<sha256>|<байт>|<atMs>`.
  Шлёт сид всем известным узлам (контакты + участники сообществ, потолок
  500 по рейтингу), как `cap`: только от самого узла, без эпидемии, не
  чаще раза в 10 минут; повторно при смене версии.
- `upwant` — «пришли мне обновление»: `APUGRP1|upwant|<версия>|<sha256>|<b64(привязка)>`.
  Привязка — подписанный ключ обмена просителя (как у `fwant`): без неё
  сид не запечатает конверт (ответит `upnone`, проситель повторит, когда
  HELLO дойдёт).
- `upnone` — «нет/не сейчас»: `APUGRP1|upnone|<версия>|<sha256>`. Ответ
  просителю: версии у меня нет, я занят очередью или файл уже отдаю —
  проси у другого.
- `upask` — «у тебя есть что-нибудь новее, чем у меня?»
  (`APUGRP1|upask|<моя_версия>`). Шлёт телефон по кнопке «Проверить новую
  версию» (Настройки) всем известным узлам; сид, у которого версия новее,
  отвечает одним `upk` ИМЕННО этому узлу — так проверка находит соседей
  немедленно, а не через расписание объявлений. Ответ идёт только по
  запросу, без веера, и только если версия реально новее.

- `uppk` — «я раздаю ПАТЧ обновления» (раунд 133):
  `APUGRP1|uppk|<от_версии>|<до_версии>|<sha256_патча>|<байт>|<sha256_apk>|<atMs>`.
  Расписание то же, что у `upk` (веер раз в 10 минут, только от самого узла).
  Интересен телефону, чья версия РОВНО `<от_версии>`, а `<до_версии>` новее.
- `uppwant` — «пришли мне патч»:
  `APUGRP1|uppwant|<от_версии>|<до_версии>|<sha256_патча>|<b64(привязка)>`.
  Отказ — прежний `upnone`, где `<версия>` = `<до_версии>`, `<sha256>` =
  sha256 патча. Сам патч идёт файловой машиной в `apkseed` (общий манифест,
  куски, полосы) — он просто маленький файл со своим sha256.

Приёмник версий: предложение файла с меткой `grp_apkseed` принимается,
только если я сам запрашивал этот sha256 (рой `routeOffer` — тот же
механизм, что у файлов групп; `ApkSeeder.routeApkOffer`; раунд 133
добавил: и если я запрашивал ПАТЧ с этим sha256).

## 3. Роли

### 3.1 Сид (раздающий)

- **Отметить файл** (`mark`): проверка, что это APK (ZIP с
  `AndroidManifest.xml` и хотя бы одним `classes*.dex`), что версия
  разбирается и НОВЕЕ текущей версии приложения (иначе — честный отказ
  «это не новая версия»), расчёт sha256, копия в
  `noBackupFilesDir/apk_seed/v1/<sha256>.apk`. Далее `prepareGroupCopy`
  (метка `apkseed`) → строка `OUTGOING/SEEDING` + общая копия кусков.
  Если источник — уже принятый файл приложения (из «Полученных APK» или
  автоматическая раздача после установки) — строка `INCOMING/COMPLETE`
  подходит как есть: куски и ключ у телефона остались, перешифровка
  не нужна (механизм К2).
- **Ответ на `upwant`**: версия совпадает с моей раздачей и ключ
  просителя закреплён → `GroupFileSeeder.offer` (плечи/окна/инвентарь —
  прежние). Ключа нет → попросить HELLO, проситель повторит. Файла/версии
  нет или плечи заняты (`BUSY`) → `upnone`. Отдавать можно любому узлу:
  конверт ключа запечатан именно под его ключ обмена, а общий манифест
  старые версии и чужие телефоны отбросят (у них для `grp_apkseed` нет
  «слова роя»).
- **Помпа**: повтор `upk` по расписанию, обслуживание плеч (
  `GroupFileSeeder.pump`), снятие истёкших копий.
- **Замена версии** («каждый раз заменяя версию более новой»): пометка
  файла НОВОЙ версии стирает прежнюю раздачу (копия, строка, куски, файл,
  объявление) и поднимает раздачу новой. Пометку версии НИЖЕ текущей
  раздачи не принимать (кроме явного «остановить раздать») — иначе рой
  бы откатил сеть назад.
- **Снять раздачу** (`unmark`): убрать объявление и копию.

### 3.2 Проситель

- **Объявления `upk`** складываются в `offers` (на диске, по узлу —
  последнее): версия ≤ моей → не показывается (и не запрашивается) —
  ровно «всем, у кого ниже версия»: у более новых телефонов предложение
  невидимо. Несколько сидов с одной версией — один карточкой.
- **Запрос** (`request`): к известным сидам той же версии поочерёдно
  (порядок `SwarmPeerDirectory.order`), `upwant` с моей привязкой;
  повтор по расписанию и смена сида по `upnone`/молчанию — тот же круг,
  что у `GroupFileSwarm.ask`/`reask`. Просьба держится на диске
  (перезапуск не сбрасывает).
- **Приём**: предложение ложится в `apkseed` (строка `INCOMING`,
  `routeApkOffer`), куски — полосами у нескольких сидов: приёмник
  принимает предложения всех сидов одного файла (до 4,
  `MAX_GROUP_SEEDS`), каждому рассылает инвентарь недостающих кусков,
  а хук `onOfferAccepted` → `ApkSeeder.onSeedJoined` просит следующего
  известного сида той же версии, пока их меньше `STRIPE_SEEDS` (3) —
  файл качается кусками СО ВСЕХ телефонов, у которых он есть. Ход — по
  строке передачи (UI: «Принимаю v…; N МБ из M МБ; кусками от K сосед(ей)»).
- **Готово**: файл в `file_received/v1/<tid>/<имя>.apk` (строка
  `COMPLETE`, куски и ключ сохранены — телефон СРАЗУ готов стать сидом:
  «у одного появилась новая версия — он раздаёт другим»). Кнопка
  «Установить» (FileProvider, как у `UpdateChecker.installApk`).
  Пометка «раздавать дальше» ВКЛЮЧЕНА по умолчанию.

### 3.3 Авто-раздача после установки

При старте: если версия приложения равна версии скачанной копии, файл
на месте (sha256), и пометка «раздавать» стоит — телефон сам становится
сидом (строка-источник — его `INCOMING/COMPLETE`, без перешифровки).
Так обновление расходится по сети без человека: N+1 получил → поставил →
перезапустился → раздаёт.

### 3.4 Автоматический забор скачанного файла (официальная загрузка)

APK, скачанный с официального сайта (DownloadManager), сам встаёт в
раздел «Обновления» — без человека:

- триггеры: рассылка `ACTION_DOWNLOAD_COMPLETE` (приёмник живёт в
  `ApkSeeder`), догон при старте и при открытии настроек
  (`adoptCompletedDownloads` → `UpdateChecker.completedApkDownloads` —
  успешные загрузки APK из DownloadManager);
- проверка: это ZIP с манифестом и dex; версия читается ИЗ САМОГО APK
  (`PackageManager.getPackageArchiveInfo`, versionName), fallback —
  числа из имени файла; версия старее текущей — честный отказ, равна
  текущей (поставили, а раздел не успел) — просто раздача, новее —
  раздача + карточка «Обновить до vX» (файл — копия из `apk_seed/v1`);
- уже взятый файл (путь и размер совпадают, запись в `adopted.v1`)
  не обрабатывается второй раз — большой файл не пересчитывается зря;
- после установки и перезапуска работает §3.3: раздача той же версии
  подтверждается, имя файла берётся из записи о раздаче — человек
  ничего не вводит.

Выбор APK из проводника (SAF) тоже автоматизирован: настоящее имя
берётся из `OpenableColumns.DISPLAY_NAME`, версия — из самого архива
(временно копируется в кэш); в диалоге поле версии заполнено само,
человек может исправить.

## 4. Где живёт и что где лежит

- `data/update/ApkSeeder.kt` — @Singleton: сид + проситель + помпа
  (одна сторона процесса, как `GroupFileSwarm`).
- `data/update/ApkUpdate.kt` — константы (`CHAT_ID = "apkseed"`,
  `DIR_NAME = "apk_seed/v1"`), разбор/сравнение версий (префикс `v` и
  хвосты `-beta`/`+abc` прощаются, как в `UpdateChecker.isVersionNewer`),
  проверка «это APK» (ZipFile: AndroidManifest.xml + classes*.dex),
  sha256, форматирование размера.
- `data/update/ApkUpdateStore.kt` — хранилище offers/seed/просьбы/взятых
  файлов: однострочные `|`-форматы с шапками `APUSEED1`/`APUOFFER1`/
  `APUREQ1`/`APUADOPT1` (шапка — первое поле), base64url для бинарного,
  tmp+ATOMIC_MOVE, битый файл → null/пусто, узлы только `pk_`. Лежит в
  `noBackupFilesDir/apk_seed/v1/`.
- `GroupWire` — `upk`/`upwant`/`upnone` (build/parse + тесты).
- `GroupRepository` — хуки `onUpdatePack/onUpdateWant/onUpdateNone`
  (опциональные параметры конструктора, как `onFileWant`).
- `GroupsModule` — связка хуков через `Provider<ApkSeeder>`.
- `FileTransferRouter` — `routeOffer` сначала рой групп, затем
  `ApkSeeder.routeApkOffer`; `notifier` — `ApkSeeder.onFileReceived`
  (строку в чат не писать); `onOfferAccepted` — и рою групп, и
  `ApkSeeder.onSeedJoined` (полосы со всех сидов); `GroupFileSeeder.mayServe`
  — для `apkseed` разрешено всем.
- `CoreServerService` — `apkSeeder.pump()` в файловом насосе (20 с),
  `onPeerOnline` — разбудить запрос.
- UI — Настройки, раздел «Обновления» (`SettingsScreen` + карточка
  `ApkUpdatesCard`): своя раздача (версия, имя файла, размер, «получили:
  N», «Остановить раздачу»), «Обновить до vX» (файл скачан — установка +
  раздача уже идут; появляется и сам, когда официальная загрузка встала
  в раздел), приём с прогрессом и «Остановить приём», предложение соседа
  (только версии новее моей, «Скачать v…» — версия на кнопке),
  «Раздать полученный APK» (список принятых `.apk`, версия — из самого
  файла), «Отметить APK как обновление» (SAF-выбор: имя и версия читаются
  из файла сами) и «Проверить новую версию» (кнопка: `upask` всем
  соседям + GitHub-релиз + перечитать принятые APK). Если проверка нашла
  обновление И на официальном сайте, И у соседей — карточка показывает
  ОБЕ кнопки выбора: «С официального сайта v…» и «По сети v… (кусками от
  N сосед(ей))». Версия в диалогах подставляется из самого APK (или из
  имени), человек может исправить; не новая для телефона версия — честный
  отказ.

## 5. Границы и честность

- Размер APK без отдельного предела (он файл, как любой; квота «Место
  под пересылку» действует на куски).
- «Новая версия» определяется численным сравнением (11.70.28 > 11.70.9);
  сборка, помеченная как новая, не обязана быть официальным релизом —
  но APK не проверяется подписью (подпись релиза — для официального
  обновления; это «раздать свой файл», ответственность — владельца).
- Если прямой канал к просителю не поднимается (симметричный NAT с обеих
  сторон) — файл не пойдёт (как и у групп): сид ответит `upnone` после
  попытки, проситель переспросит другого.
- Старые версии: ничего не видят и не ломаются (неизвестные виды —
  отбрасываются; `grp_apkseed` у них не «своё» — предложение бросится).
- Официальное окно обновления (`UpdateChecker`, GitHub) не меняется;
  сетевая раздача — отдельный путь.

## 6. Дифф-патч в рое (раунд 133, 2026-09-23)

Просьба владельца: «по рою тоже отправляй только маленькую нужную часть
для обновления». Ответ: патч (формат APUBSP1, см. tools/ci/make_apk_patch.py)
ходит по рою как обычный файл в `apkseed`:

- **Кто раздаёт патч.** Телефон, который обновился КОМПАКТНО с сайта
  (раунд 132): `UpdateChecker` больше не удаляет патч, а отдаёт его
  рой-слою (`onPatchKept` → `ApkSeeder.adoptPatchFromSite`); тот
  сохраняет файл в разделе раздачи и метаданные (от/до, sha256 патча,
  sha256 итогового APK). Общую копию и объявление достраивает помпа.
  Тот же путь у телефона, получившего патч по рою: его строка
  `INCOMING/COMPLETE` — готовый источник (перешифровки нет).
- **Кто просит.** Телефон версии «от» видит карточку «Скачать компактно
  v<до>» (патч, размер). Дальше тот же круг просьб, что у целого APK:
  `uppwant` по сидам, `upnone` — следующий, полосы от нескольких сидов.
- **Что на приёме.** Патч применяют к установленному APK
  (`ApkDiffPatch.apply`), собирают файл, сверяют sha256 с объявленным
  (он равен sha256 релиза) — карточка «Установить»; и сразу: патч
  становится раздачей для остальных «от»-телефонов, собранный APK —
  раздачей для всех остальных (как скачанный с сайта).
- **Честность.** Собранный APK обязан сойтись по sha256; не сошёлся —
  выбрасывается, остаётся обычный путь за целым APK. Патч старее моей
  версии подчищается. Телефонам не «от»-версий патч-объявления
  невидимы — они качают целый APK как раньше.
