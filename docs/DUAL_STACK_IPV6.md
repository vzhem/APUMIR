# Dual-stack: IPv6 и IPv4 в прямом канале

> Часть 1 задачи «полная поддержка IPv6». Часть 2 (реакция на смену сети,
> MTU, единая политика таймаутов, настройки «только через relay» и «экономия
> трафика») — отдельным выпуском, см. `docs/APP_DELIVERY_TRACKER.md`.

## Что было

Прямой канал был чисто IPv4, хотя вызовы и передача файлов уже предпочитали
IPv6:

| Место | Было |
|---|---|
| `network/direct_transport.rs` + `engine/core.rs` | endpoint привязан к `0.0.0.0:7777` |
| `network/quic_client.rs` | `Endpoint::server(config, addr)` — без `only_v6` |
| `network/mdns.rs` | публиковался один IPv4, у пира брался первый IPv4 (`find(\|a\| a.is_ipv4())`) |
| `network/direct_transport.rs` (STUN) | из ответа DNS брался только IPv4 |
| `network/ice.rs` | `UdpSocket::bind("0.0.0.0:0")`, резолв — «первый из списка» |
| `engine/core.rs` (QR) | подсказки только IPv4 (`filter(\|ip\| ip.is_ipv4() && ...)`) |
| `engine/core.rs` (TCP 7778) | слушатель истории на `0.0.0.0` |
| `data/call/CallUdpChannel.kt`, `data/file/FileUdpChannel.kt` | **уже** IPv6 первым, IPv4 запасным |

Итог: половина приложения умела IPv6, вторая половина не давала ей шанса.

## Что стало

Новый модуль `network/dual_stack.rs` — единственная точка правды про адреса:

| Функция | Что делает |
|---|---|
| `canonical` / `canonical_ip` | v4-mapped `::ffff:a.b.c.d` → IPv4 |
| `rank` / `pick` / `pick_addr` | порядок: глобальный IPv6 → глобальный IPv4 → ULA → (link-local не годится) |
| `reachable` / `shareable` | что можно отдавать соседям: без loopback, link-local, multicast, unspecified, `2001:db8::/32` |
| `local_shareable_ips` / `contact_hints` | локальные адреса для mDNS и QR (одна реализация на оба места) |
| `bind_udp_dual` / `bind_tcp_dual` | привязка к `[::]` с `only_v6(false)` и откатом на `0.0.0.0` |
| `resolve_ordered` | резолв DNS в порядке предпочтения (IPv6 → IPv4), все адреса |

Что это даёт по пунктам задачи:

1. **QUIC-endpoint** — `[::]:7777` через собственный сокет (`endpoint_socket` в
   `quic_client.rs`), `only_v6 = false`. Явный адрес (например `127.0.0.1:0` в
   тестах) уважается.
2. **mDNS** — публикуются все пригодные локальные адреса (IPv6 впереди), при
   выборе пира предпочтение IPv6 с откатом на IPv4. link-local не публикуется и
   не выбирается: он достижим только с zone id, а `SocketAddr` зону не несёт —
   это ограничение формата, а не недоделка.
3. **STUN** — резолв обеих семей (`resolve_ordered`) и перебор адресов;
   отражение нормализуется (`::ffff:` не уезжает в каталог как IPv6).
   Отдельный «IPv6-STUN сервер» не нужен: у `stun.cloudflare.com` есть AAAA,
   у `stun.l.google.com` — только A, и оба варианта обрабатываются одним списком.
4. **QR и каталог адресов** — подсказки собираются из обоих стеков
   (`dual_stack::contact_hints`), формат `SocketAddr::to_string()`, то есть
   `[2001:db8::1]:7777`. Приём уже был готов: `device_pairing` и
   `peer_exchange::is_public_endpoint` разбирают IPv6 (у последнего есть тест
   на `[2606:4700:4700::1111]:7777`).
5. **TCP-listener 7778** — `bind_tcp_dual` с откатом на IPv4.

## Главная ловушка dual-stack — v4-mapped

На сокете `[::]` входящий IPv4-пир выглядит как `::ffff:a.b.c.d`. Без
нормализации он:

* не проходил `is_public_endpoint` (ветка IPv6 требует глобального unicast);
* не проходил `usable_local_endpoint`;
* давал другой ключ в пуле соединений.

Поэтому нормализация вызывается на границе: входящее соединение
(`conn.remote_address()`), адрес для дозвона (`acquire`), резолв DNS, отражение
STUN, аренда адреса (`AddressLease::create`). В коде это `check-dual-stack.py`
и тесты `v4_mapped_addresses_become_plain_ipv4`,
`dual_stack_socket_accepts_ipv4_traffic`.

## Чего сознательно нет в этом выпуске

* **Схема адреса узла не менялась.** `AddressClaims` несёт один `endpoint`, а
  структуры `peer_exchange` помечены `#[serde(deny_unknown_fields)]`: новый
  клиент с дополнительным полем заставил бы **старый** парсер отвергнуть
  запись целиком, а не проигнорировать её. «Оба стека в объявлении» требует
  версионирования формата и отдельного решения владельца — это следующий шаг.
* **link-local IPv6 не поддержан** (нужна зона интерфейса; потребуется
  расширить `DiscoveredNode.address` до `(IpAddr, port, zone)`).
* **Диагностика «по какому стеку идёт канал»** — UI-часть, отдельный шаг:
  `SettingsScreen.kt` и `DiagnosticsReport.kt` стоят на потолке god-файлов
  (AGENTS.md п. 8), поэтому строка диагностики выносится отдельным файлом.

## Как проверить руками

1. **IPv4-only сеть (главное).** Wi-Fi с выключенным IPv6 (или точка доступа
   только с IPv4): отправка, приём, файл, звонок — как раньше.
2. **IPv6-only сеть.** Точка доступа с раздачей только IPv6 (NAT64/CLAT нет):
   сосед в той же сети виден и сообщения идут **напрямую**, а не только через
   relay; в логе `network` есть приём на `[::]`.
3. **Смешанная сеть.** Один телефон с IPv6, второй без: оба видят друг друга
   (первый — по IPv6, второй — по IPv4 через тот же dual-stack сокет).
4. **mDNS.** В сети с IPv6 объявление содержит AAAA (проверяется `avahi-browse`
   или приложением с экрана диагностики).

Регресс-контракт: `python3 scripts/ci/check-dual-stack.py` (входит в
`ci-core-check`). Он падает, если кто-то вернёт фильтр «только IPv4», уберёт
откат на `0.0.0.0` или снимет тесты на IPv4-путь.
