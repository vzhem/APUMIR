# Dual-stack: IPv6 и IPv4 в прямом канале

> Части 1–4 задачи «полная поддержка IPv6 и устойчивость сети»: dual-stack,
> устойчивость (смена сети, MTU, паузы, настройки пути доставки), kill-switch
> IPv6 и оба стека в подписанном каталоге адресов. Статус и проверка сборкой —
> `docs/APP_DELIVERY_TRACKER.md`.

## Что было

Прямой канал был чисто IPv4, хотя вызовы и передача файлов уже предпочитали
IPv6:

| Место | Было |
|---|---|
| `network/direct_transport.rs` + `engine/core.rs` | endpoint привязан к `0.0.0.0:7777` |
| `network/quic_client.rs` | `Endpoint::server(config, addr)` — без `only_v6` |
| `network/mdns.rs` | публиковался один IPv4, у пира брался первый IPv4 (`find(\|a\| a.is_ipv4())`) |
| `network/direct_transport.rs` (STUN) | из ответа DNS брался только IPv4 |
| `network/ice.rs` | `UdpSocket::bind("0.0.0.0:0")`, резолв — «первый из списка» |
| `engine/core.rs` (QR) | подсказки только IPv4 (`filter(\|ip\| ip.is_ipv4() && ...)`) |
| `engine/core.rs` (TCP 7778) | слушатель истории на `0.0.0.0` |
| `data/call/CallUdpChannel.kt`, `data/file/FileUdpChannel.kt` | **уже** IPv6 первым, IPv4 запасным |

Итог: половина приложения умела IPv6, вторая половина не давала ей шанса.

## Что стало

Новый модуль `network/dual_stack.rs` — единственная точка правды про адреса:

| Функция | Что делает |
|---|---|
| `canonical` / `canonical_ip` | v4-mapped `::ffff:a.b.c.d` → IPv4 |
| `rank` / `pick` / `pick_addr` | порядок: глобальный IPv6 → глобальный IPv4 → ULA → (link-local не годится) |
| `reachable` / `shareable` | что можно отдавать соседям: без loopback, link-local, multicast, unspecified, `2001:db8::/32` |
| `local_shareable_ips` / `contact_hints` | локальные адреса для mDNS и QR (одна реализация на оба места) |
| `bind_udp_dual` / `bind_tcp_dual` | привязка к `[::]` с `only_v6(false)` и откатом на `0.0.0.0` |
| `resolve_ordered` | резолв DNS в порядке предпочтения (IPv6 → IPv4), все адреса |

Что это даёт по пунктам задачи:

1. **QUIC-endpoint** — `[::]:7777` через собственный сокет (`endpoint_socket` в
   `quic_client.rs`), `only_v6 = false`. Явный адрес (например `127.0.0.1:0` в
   тестах) уважается.
2. **mDNS** — публикуются все пригодные локальные адреса (IPv6 впереди), при
   выборе пира предпочтение IPv6 с откатом на IPv4. link-local не публикуется и
   не выбирается: он достижим только с zone id, а `SocketAddr` зону не несёт —
   это ограничение формата, а не недоделка.
3. **STUN** — резолв обеих семей (`resolve_ordered`) и перебор адресов;
   отражение нормализуется (`::ffff:` не уезжает в каталог как IPv6).
   Отдельный «IPv6-STUN сервер» не нужен: у `stun.cloudflare.com` есть AAAA,
   у `stun.l.google.com` — только A, и оба варианта обрабатываются одним списком.
4. **QR и каталог адресов** — подсказки собираются из обоих стеков
   (`dual_stack::contact_hints`), формат `SocketAddr::to_string()`, то есть
   `[2001:db8::1]:7777`. Приём уже был готов: `device_pairing` и
   `peer_exchange::is_public_endpoint` разбирают IPv6 (у последнего есть тест
   на `[2606:4700:4700::1111]:7777`).
5. **TCP-listener 7778** — `bind_tcp_dual` с откатом на IPv4.

## Главная ловушка dual-stack — v4-mapped

На сокете `[::]` входящий IPv4-пир выглядит как `::ffff:a.b.c.d`. Без
нормализации он:

* не проходил `is_public_endpoint` (ветка IPv6 требует глобального unicast);
* не проходил `usable_local_endpoint`;
* давал другой ключ в пуле соединений.

Поэтому нормализация вызывается на границе: входящее соединение
(`conn.remote_address()`), адрес для дозвона (`acquire`), резолв DNS, отражение
STUN, аренда адреса (`AddressLease::create`). В коде это `check-dual-stack.py`
и тесты `v4_mapped_addresses_become_plain_ipv4`,
`dual_stack_socket_accepts_ipv4_traffic`.

## Часть 2: устойчивость и гибкость сети

**Смена сети (Wi-Fi → LTE, VPN, авиарежим).** `NetworkMonitor` и раньше знал о
смене сети, но ядро только сбрасывало статус. Теперь
`P2PCore::on_network_available`:

* закрывает **весь** пул прямых соединений (`DirectTransport::network_changed`
  → `Command::ForgetAll`): адрес источника и маршрут у старых соединений уже
  не существуют, иначе каждая отправка ждёт таймаут мёртвого соединения;
* будит переподключение брокера (`mqtt_transport::wake_reconnect`) — раньше
  пауза могла доходить до 30 с уже при живом интернете;
* сбрасывает внешний адрес и ставит флаг «свой адрес изменился», чтобы
  presence разослал новый.

Сам сокет `[::]` не пересоздаётся: он слушает на всех интерфейсах, а старый
порт 7777 после пересоздания мог бы остаться занятым. Очередь сообщений живёт
выше транспорта (Room + relay-очередь) и не теряется: недосланное повторяется.

**MTU.** `QUIC_INITIAL_MTU = 1200` и `QUIC_MIN_MTU = 1200` выставлены явно:
1200 — единственный размер, который обязан пропускать любой путь (RFC 9000
§14), а минимальный MTU IPv6 равен 1280, и туннели (VPN, 6to4, часть мобильных
APN) держат ровно его. Датаграмма файлового канала (`FileUdpWire.MAX_DGRAM_BYTES
= 1231`) проверена тестом: 1231 + 40 (IPv6) + 8 (UDP) = 1279 ≤ 1280.

**Паузы и повторы.** Единая политика в `network/timing.rs`
(`BackoffPolicy::RECONNECT`: 1 с, удвоение, потолок 30 с). MQTT считает паузу
через неё, ряд 1/2/4/8/16/30 закреплён тестом. Досылка в приложении
(`ChatOutboxPump`/`OutboxCadence`) **специально не унифицируется**: она
нарочно частая, и «общая политика» вернула бы минутную задержку.

**Настройки пути доставки** — карточка «Сеть сообщений»:

| Настройка | Что делает | По умолчанию |
|---|---|---|
| «Только через relay» | прямой канал не используется ни на отправку, ни на приём | выключено |
| «Экономия трафика» | на мобильной сети прямой канал не поднимается без нужды | выключено |
| «Использовать IPv6» | kill-switch: приложение ходит только по IPv4 | включено |

Обе живут в `p2p_prefs` (`NetworkPathSettings`), применяются сразу
(`set_network_path_policy`) и переживают перезапуск: при старте службы их
передаёт `NetworkMonitor`, при смене сети — он же. Старое поведение остаётся
по умолчанию.

## Kill-switch IPv6

Бывает сеть, где IPv6 объявлен, но не работает: оператор выдал адрес, а
маршрута нет; VPN держит половину стека; роутер раздаёт RA и молчит. Приложение
в такой сети сначала пробует IPv6, ждёт таймаут и только потом берёт IPv4 —
человек видит «сообщения доходят с задержкой». Переключатель «Использовать
IPv6» (по умолчанию **включён**) убирает v6 из всех решений сразу:

| Место | Что делает выключенный v6 |
|---|---|
| `dual_stack::rank` / `reachable` | адреса IPv6 не годятся ни для выбора, ни для публикации |
| `bind_udp_dual` / `bind_tcp_dual` | сокеты сразу привязываются к `0.0.0.0`, без пробного `[::]` |
| `resolve_ordered` | из DNS-ответа v6 выбрасывается, STUN не ждёт таймаут на v6 |
| `local_shareable_ips` / `contact_hints` | в mDNS и QR уходят только IPv4 |

Правило одно: **выключение v6 не должно менять ничего, кроме самого v6**.
Поэтому v4-mapped адреса (`::ffff:a.b.c.d`) нормализуются до проверки стека —
это IPv4, и он продолжает работать. Флаг живёт на процесс
(`dual_stack::set_ipv6_enabled`), приложение передаёт его из `p2p_prefs`
(`NetworkPathSettings`) при старте службы и при переключении; уже открытые
соединения не рвутся — их закроет смена сети или перезапуск службы.

## Часть 4: оба стека в подписанном каталоге адресов

Задача звучала как «в объявлении адреса узла должен быть не один endpoint».
Первое, что хочется сделать, — добавить в `AddressClaims` поле
`endpoints: [..]`. Так делать **нельзя**: структуры `peer_exchange` помечены
`#[serde(deny_unknown_fields)]`, и старое приложение, получив запись с новым
полем, отвергло бы её **целиком** — узел пропал бы из каталога у половины
сети. Поэтому сделано иначе.

**Каталог уже умеет несколько адресов на узел.** Запись ключуется парой
«узел + endpoint», `trim_records` разрешает по два адреса на узел
(`MAX_PER_NODE_ADDRESSES`), каждая аренда подписана отдельно. То есть «оба
стека» — это **две обычные аренды одного узла**, которые понимает и старый
телефон (для него это просто два известных адреса узла).

Что добавлено в этом выпуске:

| Место | Было | Стало |
|---|---|---|
| `peer_exchange::State::self_lease` | одна своя аренда | `self_leases` — по одной на стек |
| `PeerExchange::plan` | один свой адрес | `plan_multi` — оба, `plan` остался обёрткой |
| STUN (`run_stun_discovery`) | одно отражение | если отражение пришло по IPv6, дополнительно спрашивается IPv4-отражение (`stun_via_side_channel_family`) |
| `P2PCore::public_addr` | один адрес | плюс `public_addr_alt` — второй стек |
| DHT-ответ (`dhtr`) | один адрес цели | `reply_payload_multi`: первый адрес в прежнем поле, второй — записью `цель@адрес` **первой** в кольце |
| Приём DHT-ответа | адрес цели | второй адрес цели ложится в `_public` и пробуется, если основной не ответил |
| Приём PEX-кандидатов | второй адрес терялся | второй стек того же узла ложится в `_public` |

Совместимость:

* **старый телефон читает новый кадр**: `dhtr` остаётся текстовым, число полей
  и их порядок не изменились; второй адрес — обычная запись `id@addr`, а
  `parse_reply` держит три записи кольца, поэтому новый адрес поставлен
  первым (он ценнее третьего соседа). Старый движок записи про цель в кольце
  игнорирует и продолжает работать по первому адресу;
* **новый телефон читает старый кадр**: поле "второго адреса" просто
  отсутствует;
* **старый телефон получает вторую аренду**: это ещё одна обычная подписанная
  запись каталога, ровно как если бы у узла сменился адрес.

**presence в брокере по-прежнему несёт один адрес.** Строка presence —
плоский текст в общем топике, и добавлять туда второе поле без версии формата
означало бы сломать чтение у старых сборок. Второй стек доезжает до пира по
каталогу/PEX и по DHT, а presence остаётся «маяком»: адрес, который там указан,
всегда рабочий (главный стек).

## Чего сознательно нет в этом выпуске

* **link-local IPv6 не поддержан** (нужна зона интерфейса; потребуется
  расширить `DiscoveredNode.address` до `(IpAddr, port, zone)`).
* **Второй адрес в presence-строке брокера** — см. выше: это смена формата
  строки, которую читают все версии сразу; каталог и DHT закрывают ту же
  задачу без риска.

## Как проверить, когда IPv6 нет (IPv4-only сеть)

Самая частая ситуация: мобильный оператор выдаёт только IPv4/CGNAT, дома
провайдер IPv6 не даёт. **Проверить, что работа сделана, всё равно можно** —
и вот по каким признакам, по порядку от самого надёжного.

1. **`bind=ipv6` в карточке «Сеть сообщений».** Прямой сокет поднимается на
   `[::]` (dual-stack) и прекрасно работает в сети без IPv6: IPv4-пиры
   приходят на него как `::ffff:a.b.c.d` и нормализуются. То есть если в
   строке `DIRECT:` стоит `bind=ipv6`, новый код на телефоне **работает**, даже
   когда в сети нет ни одного IPv6-адреса. Рядом будет честное
   `lan_v6=no · public=ipv4` — это и есть нормальный IPv4-путь.
2. **Поведение не изменилось.** Отправка, приём, файлы, звонки, обновление по
   Wi-Fi и по мобильной — как в предыдущей версии. Это главный критерий
   приёмки: IPv6 добавляет второй путь, а не заменяет первый.
3. **`bind=ipv4`** — единственный признак, который стоит считать проблемой:
   значит `[::]` не поднялся и включился откат на `0.0.0.0`. В логе при этом
   будет `dual-stack: [::] bind failed, falling back to IPv4` с причиной.
4. **Выключить/включить «Использовать IPv6».** В IPv4-only сети разницы быть
   не должно (это и проверяем — настройка ничего не ломает); в строке меняется
   только `ipv6=off/on`, а карточка пишет «IPv6 выключен в настройках» вместо
   «в этой сети IPv6 нет».

### Где всё-таки взять IPv6, чтобы увидеть второй путь

* **Домашний Wi-Fi.** У крупных российских провайдеров IPv6 обычно уже выдан
  (Ростелеком, МГТС, МТС, Билайн, Мегафон — на домашних тарифах). Проверить
  на телефоне: открыть `test-ipv6.com` — если он показывает IPv6-адрес,
  карточка «Сеть сообщений» должна показать `lan_v6=yes`, а при включённом
  IPv6 в mDNS появятся AAAA-записи (видно по `avahi-browse` с компьютера в
  той же сети).
* **Мобильный интернет.** Чаще всего CGNAT без IPv6 — там работает
  IPv4-путь, и это ожидаемо.
* **Один телефон с IPv6, остальные без.** Этого достаточно для проверки
  смешанной сети: оба вида узлов должны видеть друг друга и обмениваться
  сообщениями без ручных настроек.
* **Туннель (6in4/Hurricane Electric) ставить не нужно.** Работа не требует,
  чтобы IPv6 был у всех: она требует, чтобы там, где он есть, он
  использовался, а там, где нет, ничего не ломалось.

## Как проверить руками

1. **IPv4-only сеть (главное).** Wi-Fi с выключенным IPv6 (или точка доступа
   только с IPv4): отправка, приём, файл, звонок — как раньше.
2. **IPv6-only сеть.** Точка доступа с раздачей только IPv6 (NAT64/CLAT нет):
   сосед в той же сети виден и сообщения идут **напрямую**, а не только через
   relay; в логе `network` есть приём на `[::]`.
3. **Смешанная сеть.** Один телефон с IPv6, второй без: оба видят друг друга
   (первый — по IPv6, второй — по IPv4 через тот же dual-stack сокет).
4. **mDNS.** В сети с IPv6 объявление содержит AAAA (проверяется `avahi-browse`
   или приложением с экрана диагностики).
5. **Kill-switch.** «Сеть сообщений» → «Использовать IPv6» выключить: то же
   самое, что пункт 1 (всё работает по IPv4). Включить обратно — IPv6-путь
   возвращается без перезапуска приложения.

Регресс-контракт: `python3 scripts/ci/check-dual-stack.py` (входит в
`ci-core-check`). Он падает, если кто-то вернёт фильтр «только IPv4», уберёт
откат на `0.0.0.0` или снимет тесты на IPv4-путь.
