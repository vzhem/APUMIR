# Разбор большого relay-хранилища после отчётов v11.74.357

Это расследование и дополнительные **read-only** показатели, не выполненная
очистка телефона и не новый релиз. Тексты/идентификаторы/исходные отчёты устройств
в репозиторий не добавлены. Содержимое зашифрованных записей не исследовалось.

## 1. Что уже объяснено числами

Во втором снимке:

| Показатель | Байты / количество | Значение |
|---|---:|---|
| SQLite DB | 1 150 394 368 | 1097,10 МиБ |
| WAL | 37 277 792 | 35,55 МиБ |
| SHM | 32 768 | 0,03 МиБ |
| DB+WAL+SHM | 1 187 704 928 | 1132,68 МиБ |
| Свободные страницы **внутри DB** | 939 921 408 | 896,38 МиБ; 81,70% DB |
| Страницы не в freelist | 210 472 960 | 200,72 МиБ; не «полезная переписка» |
| Зашифрованные записи | 35 174 | 35 080 live по expiry, 94 expired |
| Tombstones | 959 365 | Маркеры ID, не тела сообщений |

Свободные страницы не прибавляются к DB второй раз. Они уже освобождены для
повторной записи SQLite, но занимают диск. Остальные страницы включают таблицы,
индексы, tombstones и служебную структуру; 200,72 МиБ не являются оценкой объёма
пользовательских сообщений. WAL может содержать несколько версий страниц.

**Подтверждено:** главная составляющая текущего физического размера — сохранённая
ёмкость после удалений. **Не подтверждено:** какие именно прежние пакеты довели
DB до такого максимума. Удаление 94 expired rows само по себе не вернёт 940 МБ ОС.
`physical_delta=0` относится лишь к четырём секундам между последними снимками,
не доказывает отсутствие роста за часы/дни.

В первом снимке DB+WAL+SHM составляли 176 100 936 байт, свободные страницы —
24 387 584 байт. Там 5 720 expired из 44 058 encrypted rows. Снимки разных
хранилищ нельзя вычитать друг из друга как динамику одного телефона.

## 2. Это может быть одно и то же?

Да, **по смыслу**, но отчёт этого не доказывает. Важны три разных явления:

1. Одинаковый transport `msg_id`: в `relay_records_enc` PRIMARY KEY +
   `INSERT OR IGNORE` не создают вторую строку. Два брокера не означают две
   SQLite-копии одного и того же ID.
2. То же служебное состояние с **новым ID**: это новая строка. На отправке
   каталогов GIF/стикеров `CoreServerService` генерирует новый UUID для batch;
   это не строка пользовательского чата. Повторное объявление одинакового
   состояния может накопить отдельные записи, если прежняя доставка/TTL ещё
   не завершилась. Доля таких пакетов в старой DB неизвестна.
3. Повторная постановка прежнего ID в RAM после вытеснения: может увеличить
   счётчик evictions, не увеличив число durable rows. Восстановление при старте
   также вызывает `enqueue_own` и может вытеснять записи сверх резерва.
   Поэтому 5 896 evictions **не равны** 5 896 уникальным пользовательским сообщениям.

`repeated_ids_sampled=0` ожидаемо внутри таблицы с уникальным ID. Эта метрика
не проверяет совпадение смысла/тела. Сравнение ciphertext не решит вопрос:
повторное шифрование того же текста может дать другие байты. Дедупликация
пользовательских сообщений по тексту опасна: два отдельных «привет» должны остаться
двумя сообщениями. Исправлять нужно идентичность логической операции и retry.

## 3. Подтверждённые проблемы/границы кода

### A. Tombstones не имеют подключённого обслуживания

`RelayStore::prune_tombstones` существует и имеет unit tests, но production-вызова
в engine нет. `purge_expired_encrypted` очищает expired records/quarantine, не
таблицу tombstones. Они могут накапливаться между запусками без этого обслуживания.
Возраст нынешних 959 365 маркеров прежний отчёт не показывал.

`remove_encrypted_and_tombstone` добавляет маркер и при отсутствии удалённой
записи. Поэтому число маркеров нельзя читать как число реально удалённых тел.
Повтор того же ID не создаёт новую строку, но обновляет `removed_at_ms`.
Входные подтверждения требуют отдельного аудита: не следует автоматически
создавать новые постоянные маркеры для неизвестных операций.

**Нельзя просто обнулить таблицу:** она предотвращает возвращение доставленных
relay-пакетов. Retention должен учитывать максимальное replay/TTL окно, запас
на часы и корректную авторизацию, не только произвольный лимит числа строк.

### B. RAM-лимиты не ограничивают SQLite

`MAX_TOTAL`/`MAX_PER_RECIPIENT` и свой резерв — лимиты `RelayQueue`. В foreign path
engine сохраняет durable record **до** RAM enqueue; отказ enqueue по лимиту не
откатывает уже сохранённую запись. Поэтому DB может иметь больше записей,
чем рабочая RAM-очередь. Квота `file_buffer_quota_bytes` — другой файловый буфер,
не ограничение этой DB. Нужна отдельная политика durable admission для чужой
пересылки; нельзя ради неё молча удалять свою недоставленную переписку.

### C. Очистка expired зависит от событий

В текущем engine `purge_expired_encrypted` вызывается при startup и обработке
адресованной этому узлу gossip summary. Нет независимого периодического вызова
этой функции по таймеру. Нулевое окно purge logcat не доказывает, что очистка
никогда не работала, но обслуживание не должно зависеть только от входящего gossip.

### D. Защищённые служебные пакеты не всегда распознаются как короткоживущие

Rust классифицирует префикс тела либо известные file/LAN/UDP ID. После sealing
префикс приватного control скрыт. Например, fallback `TypingRouter` отправляет
приватное «печатает…» с обычным новым UUID и chat scope; Rust видит opaque body
и относит его к Correspondence, а не ServiceSignal. На origin это может означать
durable retention как у переписки. Другие служебные типы требуют отдельного аудита.

Это дефект категории/retention, **не доказательство**, что вся старая DB состоит
из typing. Нельзя объявить всякий sealed body сигналом: тогда потеряется переписка.
Нужно сохранять проверенную категорию на пути отправки, не ослабляя шифрование,
с коротким TTL/отдельным бюджетом для ephemeral traffic. Старые неразличимые
записи не удаляются по догадке.

### E. Удалённые страницы не возвращаются ОС автоматически

`RelayStore::migrate` включает WAL, но не настраивает auto_vacuum. Рабочего
VACUUM/incremental-vacuum пути здесь нет. Checkpoint переносит WAL в DB, но
сам по себе не уплотняет свободные страницы DB. Нужен engine-owned maintenance,
не VACUUM на каждом открытии «Логов» и не unlink активных WAL/SHM.

## 4. Что добавлено сейчас

В прежнем read-only аудите, под тем же общим CancellationSignal/2s budget:
- `non_freelist_page_bytes` и `auto_vacuum_mode`;
- количество tombstones старше 7 дней, MIN/MAX `removed_at_ms`;
- явное пояснение, что возраст — диагностика, не разрешение удалять;
- пояснение, что отсутствие повторных ID не исключает смысловые повторы.

Без чтения/хеширования/расшифровки BLOB, новых ключей, schema migration,
checkpoint или очистки. При timeout значения unknown, не ноль. Снимок остаётся
приблизительным при concurrent writer. 7 дней — фиксированное окно измерения,
не внедрённая retention-политика.

Проверки: 6 Python/SQLite characterization tests на SQL-константах из настоящего
RelayStore (same-ID/new-ID, age refresh, marker без записи, expiry отдельно от
markers, размер после DELETE/VACUUM). Последний VACUUM выполняется **только на
одноразовой синтетической тестовой DB** в ignored target, не на телефоне.
Это не Rust encryption/network integration test.

Дополнительно 3 Rust tests: real encrypted store dedup/new-ID, повторные RAM
вытеснения двух ID, безопасная классификация opaque sealed body без hint.
2 новых JVM render tests и Android fixture age/no-prune. Android fixture только
компилируется в CI; на реальном устройстве ещё не выполнен.

## 5. План безопасного исправления (пока не выполнен)

1. Счётчики фиксированных типов на origin **до sealing**, new/reused logical ID,
   сохранено/дедуп/отклонено durable, исход ACK — без тел/IDs/хешей в отчёте.
   Они покажут текущего производителя лишних записей, не угадывая старое содержимое.
2. Устойчивые ID/соединение повторов служебной операции; отдельный ephemeral path
   для typing/transport. Приватность и настоящие пользовательские повторы сохраняются.
3. Независимое периодическое bounded обслуживание TTL и tombstone retention,
   с тестами replay, ACK/cancel/delete и restart. Исправить admission/учёт неизвестных
   подтверждений, не блокируя законный ACK вытесненной durable-записи.
4. Отдельный durable disk budget для чужой пересылки и честные отказы. Своё pending
   не терять молча; размер основной истории чатов не смешивать с relay custody.
5. Контролируемое уплотнение с остановкой/координацией writer, проверкой места,
   завершением транзакций, сохранностью всех live records/tombstones и проверкой
   restart. Для старой DB понадобится отдельный maintenance; incremental mode
   нельзя просто включить и ожидать сжатия существующей none-mode DB.

Локальное unwrap_failed на одном из устройств — отдельный блокер историй;
второй снимок имеет ready keys и durable custody. Сжатие DB не восстановит ключи.
Ни очистка телефонов, ни сброс/ротация ключей, ни новый release/merge этим
расследованием не выполнены.
