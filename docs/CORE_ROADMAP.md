# Ядро APU: план «чем больше людей - тем устойчивее»

Дата: 2026-09-15. Просьба владельца: «давай сделаем чтобы у нас было ядро
самое лучшее, чтобы всё работало отлично с большим количеством людей, чтобы
чем больше людей - тем больше стабильность; если что-то нужно установить на
ПК - давай ставить».

Этот документ - единственное место, где живёт план работ по ядру
(`rust-core/`). Факты о выпущенных релизах - `START_HERE.md` §3, детали кода -
`AI_HANDOFF.md`, рой файлов и постов - `CHANNEL_SWARM_DESIGN.md`.

## 0. Что такое «ядро» и почему оно было заморожено

Приложение = оболочка на Kotlin (экраны, группы, каналы, рой, звонки, копии) +
ядро на Rust (QUIC, шифрование, брокер MQTT, очередь доставки). Между ними -
«мост» `android-app/app/src/main/java/uniffi/p2p_core/p2p_core.kt`, который
порождается генератором `uniffi-bindgen` из описания `rust-core/src/lib.udl`.

До 2026-09-15 мост лежал в git готовым, а генератора не было ни у владельца
(на его ПК Rust не ставим - MSVC давал синие экраны), ни у бота (в песочнице
нет доступа к crates.io). Новая функция ядра была невозможна: Kotlin её не
видел, а мост, дописанный руками, ронял приложение на старте по контрольным
суммам. Ядро менялось только «изнутри» существующих функций.

**Решение (2026-09-15, `scripts/ci/build-release.yml`):** CI сам собирает
генератор (`tools/uniffi-bindgen`, uniffi =0.28.3 - та же линия 0.28, что у
ядра) и переписывает мост из `lib.udl` перед сборкой APK. Страховки: при
ошибке генератора или смене `bindings_contract_version` берётся файл из git;
свежие мост и ядро выкладываются артефактом `core-bindings` (30 дней); после
публикации релиза мост и `.so` коммитятся обратно в `main`, если тег стоял
на его вершине. **На ПК владельца ставить ничего не нужно** - Rust собирает
CI при каждом теге.

Что нужно от владельца один раз: скопировать новый workflow (бот не может
писать в `.github/workflows/`):

```
cd C:\APU-M8
git pull
Copy-Item -Force scripts\ci\build-release.yml .github\workflows\build-release.yml
git add .github\workflows\build-release.yml
git commit -m "ci: regenerate uniffi bindings from lib.udl"
git push
```

Проверка, что заморозка снята: релиз v11.70.23 добавляет функцию
`core_build_info()` и строку «Ядро» в Настройки → «О приложении». Если там
видно «p2p_core 0.1.0 · сборка v11.70.23 · 2 брокера» - мост перегенерирован.
(Со стороны CI это уже подтверждено 2026-09-15; workflow скопирован
владельцем коммитом `ad70242`.)

## 1. Как устроено сегодня (честная картина)

| Слой | Что есть | Слабое место при росте числа людей |
|---|---|---|
| Прямая связь | QUIC (порт 7777) в LAN и через интернет, адрес узнаём по STUN **с того же порта** и разносим через presence; TCP 7778 | До v11.70.24 соединение открывалось заново на каждое сообщение; с K1 - один endpoint, пул, keep-alive, ответ по входящему соединению. Осталось: симметричный NAT с обеих сторон не пробивается, нет миграции при смене сети |
| Брокер | Два публичных MQTT-брокера (HiveMQ, EMQX), presence + конверты `sender|msgId|chatId|text`, ACK | Публичные брокеры: потолок ~10 КБ на сообщение, чужая инфраструктура, один общий канал на всех; при 1 000+ узлах presence-трафик растёт линейно у каждого |
| Доставка офлайн | `RelayQueue` + `relay_at_rest` (шифрованное хранение у релея), Cloudflare Worker store-and-forward | Кастодия у соседей (`file_custody`) написана в Rust, но к движку и FFI не подключена |
| Файлы | Шифрование кусков в ядре (`file_transfer.rs`), конверт ключа на получателя (`file_key_envelope.rs`); передача - в Kotlin (`FileTransferSender/Receiver`), рой в группах/каналах - Kotlin | До v11.70.25 ключ куска был привязан к паре отправитель→получатель; с K2 у файла группы общий манифест `grp_` - полосы от нескольких сидов. Осталось: куски идут текстовыми кадрами (base64, 4 КиБ) - K3 |
| Подпись | Ed25519 в ядре есть (`signing_identity.rs`), но FFI `crypto_ffi.rs` sign/verify - заглушка; Kotlin использует Java-библиотеку `net.i2p.crypto:eddsa` | Работает; переносить в ядро не обязательно |
| DHT | `dht.rs` (Kademlia) есть, в `engine/core.rs` создаётся, наружу не отдан | Поиск узлов без брокера не работает |

## 2. Этапы (каждый = свой релиз; порядок по пользе для «много людей»)

### Этап K0 - снятие заморозки (v11.70.23) - СДЕЛАНО 2026-09-15

`core_build_info()` через мост; цепочка `lib.udl → CI → p2p_core.kt → APK`
доказана прогоном 35005340748: мост перегенерирован, APK собран, CI сам
закоммитил мост и `.so` в main (`551f0d4`). Правило «uniffi заморожен» в
`AI_HANDOFF.md` снято. На телефоне строка «Ядро» ещё не проверена.

### Этап K1 - постоянные QUIC-соединения (v11.70.24) - ВЫПУЩЕН 2026-09-16

Было: каждое прямое сообщение = новый endpoint + рукопожатие TLS (сотни мс)
и `block_on` в потоке вызывающего до 10 с; слушатель, отправитель и STUN -
три разных сокета, поэтому адрес в presence был бесполезен.

Сделано (`rust-core/src/network/direct_transport.rs`, детали -
`AI_HANDOFF.md` 0t): один endpoint `0.0.0.0:7777` на всё (входящие,
исходящие, STUN); `ConnectionPool` включён; keep-alive 20 с, idle 60 с;
отправка через полосу на узел в tokio, вызывающий ждёт ≤ 10 с без
`block_on`; **входящее соединение усыновляется** - ответ узлу за строгим
NAT идёт по его же соединению, адрес не нужен; приём не останавливается на
неудачном рукопожатии. Мост не менялся. Проверка на телефонах - после
релиза (что смотреть в logcat - `AI_HANDOFF.md` 0t).

Что K1 НЕ делает: пробив симметричного NAT с обеих сторон (там по-прежнему
брокер/relay), выбор лучшего из нескольких адресов узла (LAN vs public),
миграцию соединения при смене сети (quinn умеет, нужен `rebind` - K4).

### Этап K2 - полосы одного файла от нескольких сидов (v11.70.25) - ВЫПУЩЕН 2026-09-17

Сделано так: ключ куска не привязан к получателю, потому что у файла группы
ОБЩИЙ манифест (версия 3, получатель = метка группы `grp_<id>`), а
шифрование кусков осталось прежним (nonce = transfer_id‖index, aad =
sha256(манифеста)‖index) - и все сиды отдают одинаковые байты. Ключ файла
заворачивается каждому просителю прежним `create_file_key_envelope` с
байтами общего манифеста (отдельная `wrap_group_file_key` не понадобилась).
Новая функция моста: `create_group_file_manifest` (`lib.udl`) - вторая
функция после снятия заморозки; CI перегенерирует мост при теге. Kotlin:
`GroupFileSeeder` (раздача общей копии по плечам), приём от нескольких сидов
с инвентарём `WANT` (тип 9) в `FileTransferReceiver`, `fwant` с меткой
`#g1`, `GroupFileSwarm.STRIPE_SEEDS`=3. Карта кода и проверка на телефонах -
`CHANNEL_SWARM_DESIGN.md` §9.4 «Этап K2», детали - `AI_HANDOFF.md` 0u.
Эффект: чем больше участников уже скачали файл, тем быстрее он приходит
следующему; автор шифрует файл один раз. Размер/sha256 релиза - `START_HERE.md` §3.

Что K2 НЕ делает: куски по-прежнему идут текстовыми кадрами по
LAN/QUIC (base64, 4 КиБ фрагменты) - это K3; личные файлы (чат один на
один) остаются на манифесте V2 с конвертом под получателя.

### Этап K3 - куски по QUIC напрямую - КОД ГОТОВ (2026-09-17, ждёт релиза)

Реализовано на ветке `arena/01a0af3e-apumir` (PR #6; релиз - после явного
разрешения владельца, версия следующая за v11.70.26):

- **Кадры.** Готовый кодек F4-B1 (`file_wire.rs`, магик `APUF`) подключён
  к транспорту: кусок = кадры `ChunkData` с диапазонами
  `(chunk_index, offset, len)` — порядок и дубли не важны, 256 КиБ предел
  кадра, без base64. Новых старых форматов не тронуто (правило N↔N-1).
- **Мост.** `send_file_chunk(recipient, transferIdHex, chunkIndex, offset,
  cipherLen, range) -> bool` и событие `file_chunk_received`
  (`CoreEventFfi` + 5 полей: transferId, chunkIndex, chunkOffset,
  ciphertextChunkLen, payload).
- **Приоритет.** Новый путь отправки: `QuicConnection::send_file_data` +
  `DirectTransport::send_file_blocking` (JobKind::FileData) — стрим с
  `FILE_DATA_STREAM_PRIORITY`; формат стрима (длина + payload) не изменился.
- **Совместимость.** Старые телефоны: APUF-стрим принимается как
  «сообщение», первое поле не `pk_…` → движок молча отбрасывает (страж
  от контактов-призраков). Новый тип пакета **FCAP** (wire 10): приёмник
  отвечает на принятое предложение «умею бинарный»; до FCAP отправитель
  остаётся на текстовых фрагментах — первый файл не проседает.
- **Приёмник.** Сборка куска из диапазонов (пересечения — брак), дальше
  тот же путь: AES-GCM тег, диск, ACK, окно. До оффера — буфер. Подложные
  диапазоны не соберутся в подлинный шифртекст (AEAD).
- **Личные файлы только**: файлы группы (K2) по-прежнему текстовые — рою
  нужна личность сида, которой в APUF-кадре нет.
- **Поллинг.** CoreServerService: пока событий много — шаг 100 мс,
  в простое — прежние 5 с (иначе куски ждали бы полный цикл, а ACK-окно
  почти не двигалось).

Эффект: личные файлы не идут через брокер (потолок 10 КБ, base64),
LAN/интернет — до предела канала (окно насоса 2 МиБ в полёте; жёсткий
лимит — пото-контроль QUIC). Детали — `AI_HANDOFF.md` 0v.

### Этап K4 - presence и поиск узлов, которые не растут линейно

При 1 000+ узлах каждый телефон получает presence всех остальных через
общий топик. Делаем: presence только по «своим» (контакты, участники моих
групп), общий топик - редкий маяк; DHT (`dht.rs`) наружу для поиска адреса
по nodeId без брокера; свой relay/rendezvous на Cloudflare Worker как третий
брокер (владелец разрешил внешние ресурсы; обязательны таймаут + фолбэк).

#### K4-1 - presence «своим» и редкий маяк - КОД ГОТОВ (2026-09-17, ветка `arena/01a0b097-apumir`)

Сделано:

- **Новый модуль** `rust-core/src/network/presence_scope.rs`: список «своих»,
  расписание и формат личного кадра. Общий топик - маяк раз в
  `BEACON_INTERVAL_MS` (10 минут), «своим» - лично раз в `OWN_INTERVAL_MS`
  (минута) по прямому QUIC. Порог `SCALING_MIN_PEERS` = 50 узлов.
- **Маленькая сеть не меняется.** Пока узлов меньше порога, presence идёт в
  общий топик раз в минуту, как до K4: старые сборки и телефоны владельца
  видят прежнее поведение (тот же приём, что в K2 с «волной»).
- **Маяк остаётся retained**, поэтому новый узел, подписавшись, сразу
  получает последний адрес; ждать конца десятиминутного окна не нужно. Если
  нас в общем списке нет вовсе - публикуем немедленно, не дожидаясь маяка.
- **Личный кадр** `ppres|node|имя|адрес|relay|client|версия|время` идёт
  текстом, первое поле не `pk_…` - старые сборки отбрасывают его тем же
  стражем, что и любой чужой кадр (правило N ↔ N-1).
- **Приём**: `handle_direct_frame` узнаёт кадр до K3-кадров, проверяет
  версию и срок годности (та же арифметика, что у presence из брокера),
  регистрирует отправителя в списке узлов и усыновляет входящее соединение.
- **«Свои» наполняются сами** из переписки (`send_message`,
  `send_message_mqtt`, входящее сообщение) и вызовом моста
  `set_presence_audience` (для будущей передачи контактов и участников групп
  из Kotlin).
- **Проверка компиляции**: `.github/workflows/ci-core-check.yml` - `cargo
  check --release --features mqtt-dual-broker` на pull request. Раньше первый
  компилятор ядра ждал тега; теперь ошибку видно до релиза.

Что K4-1 НЕ делает: не убирает presence для чужих полностью (маяк остаётся -
он нужен новому узлу, чтобы узнать адрес) и не трогает путь сообщений.

#### K4-2 - DHT наружу: поиск адреса по nodeId без брокера - КОД ГОТОВ (2026-09-17)

- **Новый модуль** `rust-core/src/network/address_lookup.rs`. Два текстовых
  кадра прямого канала: вопрос `dhtq|кто_спрашивает|кого_ищем` и ответ
  `dhtr|кто_ответил|кого_искали|адрес|id@адрес|…`. У обоих тот же страж
  `pk_…`, что у сообщений и presence, поэтому старые сборки молча
  отбрасывают их как любой чужой кадр (правило N ↔ N-1).
- **XOR-расстояние из `dht.rs` работает наружу**: ответ содержит до трёх
  ближайших к цели узлов (`sort_closer` / `dht::xor_distance`), поэтому
  спрашивающий продолжает поиск сам - это и есть итеративный DHT-поиск.
- **Отвечаем на любой вопрос**: про нас - своим публичным адресом (если STUN
  уже нашёл), про другого - адресом из своей таблицы, плюс всегда кольцо
  ближайших. Адреса, которые узел уже знает (presence, mDNS), чужим ответом
  не перетираются: иначе один вредный узел уводил бы наши отправки.
- **Расписание**: кулдаун 5 минут на цель (`LOOKUP_COOLDOWN_MS`), не больше
  трёх соседей на вопрос, вращение по списку «своих» по 32 за круг. Вопросы
  задаёт поток presence, ответы уходят оттуда же - приёмник кадров только
  кладёт их в очередь: блокирующая отправка (до 10 с на узел) не должна
  занимать рабочий поток runtime.
- **Фолбэк остаётся**: не нашлось по прямым каналам - работает маяк K4-1 в
  общем топике брокера и mDNS по Wi-Fi. Поиск идёт и в маленькой сети: это
  просто ещё одна возможность найти адрес, когда брокер молчит.

#### K4-3 - свой брокер из настроек, строгий таймаут, фолбэк - КОД ГОТОВ (2026-09-17)

- **`multi_broker.rs` стал рабочим, а не справочным**: `parse_broker_endpoint`
  принимает то, что человек напишет руками (`mqtt://host:1883`, `host:1883`,
  `host` - тогда порт 1883); `probe_broker` проверяет порт строгим таймаутом
  `BROKER_PROBE_TIMEOUT` = 6 с; `MultiBroker::with_own` + `candidates` дают
  порядок перебора: свой брокер первым, публичные за ним.
- **`mqtt_transport.rs`**: при подключении перебираются кандидаты (свой
  брокер и не больше двух публичных) и берётся первый, кто ответил в пределах
  строгого таймаута. Свой брокер молчит - переход на публичные без ожидания;
  не ответил никто - остаётся публичный по умолчанию, дальше переподключением
  занимается rumqttc, как и до K4-3.
- **Настройка**: `EngineConfig.own_broker` + мост `set_own_broker("host:port")`
  (в `lib.udl`). Вызывать до `start()`; пустая строка выключает своего
  брокера и возвращает прежнее поведение. На компьютере адрес можно задать
  переменной окружения `APU_MQTT_BROKER`.
- **Осталось по K4-3** (серверная часть, отдельным шагом): свой MQTT-брокер
  на Cloudflare Worker. Worker уже есть (`tools/worker/p2p_relay_worker.js`,
  реестр узлов `/register`, `/lookup`, хранилище личности), но MQTT поверх
  Worker требует WebSocket-транспорта (у `rumqttc` - фича `websocket`) и
  Durable Object на стороне сервера; ядро сейчас ходит в MQTT по TCP.
  До этого шага свой брокер можно поднять на любом хосте с обычным MQTT и
  прописать его адрес в настройках - код K4-3 для этого готов.

### Этап K5 - кастодия у соседей (store-and-forward между телефонами)

#### K5-1 - копия сообщения у соседей по прямому каналу - КОД ГОТОВ (2026-09-17)

Задача этапа: доставка не должна зависеть от брокера. Сегодня сообщение
офлайн-получателю уходит в общий топик MQTT и ждёт там (M3/M8: relay-очередь
и durable custody) - если брокер недоступен, доставки нет.

- **Новый модуль** `rust-core/src/network/custody_relay.rs`. Кадры прямого
  канала: `cust|offer|<конверт>` («подержи до появления получателя»),
  `cust|ack|<msg_id>|ok|full|refused`, `cust|deliver|<конверт>` (хранитель
  отдаёт получателю), `cust|drop|<msg_id>` (копия больше не нужна).
  Конверт - тот же `relay|…`, что ходит через брокер (`network::wire`):
  формат не меняется, старые сборки получают то же сообщение, а сами кадры
  отбрасывают по стражу «первое поле не `pk_…`» (правило N ↔ N-1).
- **Двое соседей** (`MAX_CUSTODY_PEERS` = 2, как в плане этапа): отправитель,
  который не смог отдать сообщение напрямую, предлагает копию «своим»
  (контакты и участники групп), которых видит в сети, и перестаёт искать,
  когда двое подтвердили. Предложений ждём до ближайшего круга: ответы
  (`ack`) приходят на приём и учитываются отдельно.
- **Хранитель отдаёт сам**: раз в минуту поток presence смотрит, кто из
  получателей, для которых у нас лежат копии, появился в сети, и отдаёт
  сообщение лично - без брокера. После отдачи копию убираем и говорим автору
  `drop`, чтобы он не искал других хранителей.
- **Ограничения**: не больше `MAX_HELD_MESSAGES` = 64 чужих сообщений,
  `MAX_HOLD_PER_RECIPIENT` = 16 на получателя, срок годности берётся из
  конверта, уже отданные идентификаторы помним (`MAX_DELIVERED_MEMORY` =
  512), поэтому две копии у разных соседей не покажут получателю одно и то
  же сообщение дважды.
- **Согласие владельца**: по умолчанию кастодия выключена, включение - мост
  `set_custody_enabled(boolean)` (вызывать можно до `start()`).
#### K5-2 - файловая кастодия в движке и мосте - КОД ГОТОВ (2026-09-17)

- **Модуль перевозки** `rust-core/src/network/file_custody_relay.rs`: кадры
  прямого канала `fcust|offer|<автор>|<ключ кастодии>|<получатель>|<до
  когда>|<кадр b64>`, `fcust|ack|<unit_id>|ok|<квитанция b64>` (или `refused`,
  `full`), `fcust|deliver|<автор>|<получатель>|<unit_id>|<кадр b64>`,
  `fcust|drop|<unit_id>`. Первое поле - `fcust`, поэтому телефоны до K5-2
  молча отбрасывают кадр тем же стражем, что и любой чужой: правило
  N ↔ N-1 не нарушено. Внутри кадра - тот же бинарный кусок B1
  (`network::file_wire`, магик APUF), что ходит прямым каналом в K3:
  получателю приходит то же событие `CoreEvent::FileChunkReceived`, поэтому
  приложению не нужен новый код приёма файлов.
- **`unit_id`** считается из (автор, получатель, transferId, индекс куска,
  смещение) и одинаков у всех участников: по нему хранитель отвечает, автор
  понимает ответ, а получатель проверяет, что кадр - тот самый (пересчитывает
  идентификатор из содержимого кадра).
- **Два имени - нарочно**: `origin` в кадре - обычное сетевое имя автора (по
  нему проверяем «свой ли» и отвечаем), а ключ в кадре - ключ кастодии
  (личность подписи устройства, `identity_signing_*`). Квитанция связывает
  ключ кастодии и имя `pk_`+sha256(ключ) попарно, поэтому она проверяема, а с
  сетевым именем её связывает привязка личности, которую ведёт приложение.
- **Склад - существующий** `network::file_custody` (SQLite, квитанции,
  квоты, TTL, партии томbstones): движок открывает его лениво при первой
  надобности в режиме `ContactsOnly`, поэтому выключенная кастодия не
  создаёт файл базы вовсе. Пределы движка поверх склада: 128 кусков и 64 МиБ
  на телефоне, срок не длиннее недели, не больше двух хранителей на кусок.
- **Роли как у сообщений**: автор кладёт кусок в очередь предложений и
  предлагает «своим» соседям (по одному предложению за круг - куски
  тяжёлые); хранитель отвечает подписанной квитанцией и держит кусок, пока
  получатель не появится в сети; отдав, убирает копию и говорит автору
  `drop`; получатель показывает кусок приложению один раз, даже если его
  принесли оба хранителя.
- **Согласие владельца**: по умолчанию выключено, включение - мост
  `set_file_custody_enabled(boolean, string db_path)` (пустой путь - склад в
  памяти), размер занятого - `file_custody_usage_bytes()`, отдать кусок -
  `offer_file_chunk_for_custody(...)` (аргументы те же, что у
  `send_file_chunk`).
- **Что осталось за пределами этапа**: приложение пока ходит своим путём
  (`FileCustodySender`/`FileCustodyPdu` в Kotlin) - чтобы включить новый
  путь, ему нужно позвать три функции моста; план репликации
  (`file_custody_replication`) остаётся готовым слоем для политики «сколько
  копий держим».

### Этап K6 - тесты ядра в CI

**КОД ГОТОВ (2026-09-17).** Правило этапа: падение тестов = нет релиза.

- **На pull request**: `cargo test --lib` уже гоняется в проверке ядра
  (`scripts/ci/ci-core-check.sh`). Блокирующим он становится по файлу-маркеру
  `scripts/ci/tests-blocking` - маркер лежит в репозитории с 2026-09-17,
  после первого зелёного прогона (K3-фикс + K4-1/K4-2/K4-3 + K5-1). Убрать
  файл = снова сделать тесты не блокирующими: без правок воркфлоу и без
  участия владельца.
- **На теге (релиз)**: в копии релизного воркфлоу
  `scripts/ci/build-release.yml` появился шаг `Core tests (K6)`, он вызывает
  `scripts/ci/release-tests.sh` до сборки под Android: упали тесты - сборка
  APK не начинается, релиз не выходит. Ставится в `.github/workflows` один
  раз скриптом `scripts/install-release-workflow.ps1` (у приложения Arena
  нет права `workflows`, поэтому файл уходит в репозиторий владельцем).
  Правила тестов после этого меняются обычным коммитом: шаг вызывает скрипт
  из репозитория.
- **Зачем отдельный скрипт для релиза**: релизный прогон собирает под
  Android и хостовых пакетов не ставит, а `cargo test --lib` собирается на
  хосте (aws-lc-rs, rusqlite bundled) - пакеты ставит `release-tests.sh`.
- **Проверка самих воркфлоу**: `scripts/ci/check-workflow-yaml.py` ловит
  грабли, из-за которых GitHub молча не берёт файл (двоеточие с пробелом в
  имени шага и т.п.); его запускает установщик релизного воркфлоу.

## 3. Правила работы с ядром после K0

- Правка `lib.udl` + Rust → релиз-тег → CI собирает ядро, переписывает мост,
  собирает APK. Ошибка компиляции Rust видна только по упавшему прогону
  (как и Kotlin) - смотреть логи по инструкции в `AI_HANDOFF.md`.
- Новые функции моста вызывать из Kotlin **полным именем**
  `uniffi.p2p_core.xxx()` внутри `try/catch (Throwable)` с фолбэком -
  старые `.so` на телефонах не бывает (APK несёт своё ядро), но так
  безопаснее при частичной сборке.
- Сетевой формат менять только с совместимостью N ↔ N-1: старые телефоны
  молча отбрасывают неизвестные виды пакетов - новые виды, а не изменение
  старых.
- Каждый внешний ресурс (брокер, STUN, Worker) - с таймаутом и фолбэком.
- `RustBridge.sendMessage` и всё, что ходит в ядро с ожиданием сети, - только
  с `Dispatchers.IO`.
