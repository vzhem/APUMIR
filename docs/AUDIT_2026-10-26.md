## 2. P0 — блокеры

### P0-1. Android 15 убивает постоянно работающий сервис, и он не поднимается после перезагрузки

**Факты.**

- `android-app/gradle/libs.versions.toml`: `targetSdk = "35"`.
- `android-app/app/src/main/AndroidManifest.xml`: `CoreServerService`
  объявлен как `android:foregroundServiceType="dataSync"`.
- `CoreServerService.kt` **не переопределяет** `onTimeout(int, int)` (поиск по
  файлу не находит ни одного вхождения).
- `EmergencyKeepAlive.kt:40-46` поднимает сервис из будильника, а
  `EmergencyKeepAliveReceiver` (manifest, `exported="true"`) — из
  `BOOT_COMPLETED`; оба вызова обёрнуты в `runCatching`, то есть отказ
  проглатывается без единой строки в логе.

**Что это значит.**

Правила Android 15 для приложений с `targetSdk ≥ 35`
([developer.android.com](https://developer.android.com/about/versions/15/behavior-changes-15)):

1. `dataSync`-сервис живёт суммарно не больше **6 часов за 24 часа**. Дальше
   система вызывает `Service.onTimeout(int, int)`; если сервис не вызвал
   `stopSelf()` за несколько секунд, процесс падает с
   `RemoteServiceException$ForegroundServiceDidNotStopInTimeException`.
2. `BOOT_COMPLETED`-приёмнику **запрещено** запускать `dataSync` FGS —
   `ForegroundServiceStartNotAllowedException`.

Совокупность даёт ровно ту картину, на которую жалуется владелец: «после
какого-то времени письма не приходят, после перезагрузки — тоже», причём
приложение не пишет ничего внятного, потому что исключения пойманы
`runCatching`/`catch`.

**Решение (в порядке предпочтения).**

1. Перевести основной сервис на `specialUse` (единственный тип FGS, допустимый
   для «постоянной связи мессенджера»), оставив `dataSync` только на реальные
   выгрузки:

```xml
<service android:name=".service.CoreServerService"
    android:foregroundServiceType="specialUse">
    <property android:name="android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE"
        android:value="persistent peer-to-peer message delivery" />
</service>
```
   плюс `FOREGROUND_SERVICE_SPECIAL_USE` в манифесте.
2. Обязательно реализовать `onTimeout`, что бы ни было выбрано:

```kotlin
override fun onTimeout(startId: Int, fgsType: Int) {
    Log.w(TAG, "FGS timeout (type=$fgsType); stopping and rescheduling")
    EmergencyKeepAliveReceiver.scheduleNext(applicationContext)
    stopSelf(startId)
}
```
3. После `BOOT_COMPLETED` не запускать FGS напрямую: выставить
   `OneTimeWorkRequest` или `AlarmManager` на 10–30 секунд и стартовать сервис
   из него (это уже разрешено), а сам `startForegroundService` обернуть так,
   чтобы отказ **логировался** (`Log.e`, счётчик в диагностике), а не молчал.
4. Добавить в диагностику счётчик «сервис остановлен системой» — без него этот
   класс отказов невидим.

**Проверка:** два дня на телефоне с Android 15, затем посмотреть в диагностике,
что сервис пережил > 6 ч суммарно и что после перезагрузки он поднялся.

### P0-2. CI красный всегда — из-за ложного срабатывания своей же проверки

**Факты.**

- Прогон `40304251118` (PR #57) упал за 36 секунд, и бот написал в PR:
  «Проверка ядра не прошла (шаг: kotlin unresolved symbols (main + tests))»,
  при этом «строк с ошибками компилятора в выводе нет».
- Локально шаг воспроизводится один в один:

```
$ python3 tools/sandbox/check_unresolved_symbols.py \
    android-app/app/src/main/java/com/vladimir/messenger ...
проверено файлов: 744, подозрительных имён: 27
exit=1
```
  27 «подозрительных» имён — это исключительно `Row` (15) и `Column` (12).
- Причина: `Row` объявлен как вложенный `private data class` в
  `data/update/DownloadTrashCleanup.kt:81`, а `Column` — в
  `data/mirror/MirrorAccountSnapshot.kt:76`. Инструмент складывает **все**
  объявления проекта в один глобальный набор `project_names` (включая
  вложенные приватные классы) и в `check_unresolved_symbols.py:384` и `:402`
  использует условие

```python
if name not in project_names and external_wildcards:
    continue      # «имя из чужой библиотеки — молчим»
```

  Из-за `name in project_names` для `Row`/`Column` «вежливое» правило не
  срабатывает, и любой Compose-файл с `import androidx.compose.foundation.layout.*`
  получает ложное срабатывание.

**Последствия.** Гейт, который должен ловить «имя вызвано, но нигде не
объявлено» (грабли v11.74.171), сейчас красит каждый PR. Его либо игнорируют,
либо ждут «пока пройдёт» — и PR #57 действительно влит с красной проверкой.
Заодно он закрывает дорогу к настоящим шагам: `android compileReleaseKotlin`,
`cargo check`, `cargo test` в этом прогоне **не выполнялись вообще**.

**Решение (проверено локально).** В индексе «имя → пакет» учитывать только
объявления верхнего уровня: вложенный класс из другого файла по короткому имени
недоступен (только `Outer.Inner` или импортом), поэтому `Row`/`Column` перестают
«разрешать» чужие `Row`/`Column`, и проверка не ослабевает.

```diff
-def declarations(text):
-    """Все имена, объявленные в файле (на любом уровне вложенности)."""
+def declarations(text, top_level_only=False):
+    """Все имена, объявленные в файле (на любом уровне вложенности).
+
+    top_level_only=True — только верхний уровень: для индекса «имя -> пакет»,
+    потому что вложенный класс из другого файла по короткому имени недоступен.
+    """
     names = set()
     for line in text.split('\n'):
+        if top_level_only and line[:1].isspace():
+            continue
         m = DECL_RE.match(line)
         if m:
             names.add(m.group(1))
+    if top_level_only:
+        return names
     for m in ENUM_RE.finditer(text):
         ...

-        packages.setdefault(pkg, set()).update(declarations(strip_noise(raw)))
+        packages.setdefault(pkg, set()).update(
+            declarations(strip_noise(raw), top_level_only=True))
```

Результат после патча: `подозрительных имён: 0`, `exit=0`,
`--self-test` по-прежнему `OK`. То есть чинится одной правкой, без ослабления
правила.

**Дополнительно.** В `ci-core-check.sh` стоит запускать тяжёлые шаги
(`android compileReleaseKotlin`, `cargo check/test`) **до** эвристики, а
эвристику считать предупреждением (`::warning::`), пока её точность не
подтвердится на 20 прогонах подряд.

### P0-3. Две трети юнит-тестов не запускаются ни в одном пайплайне

**Факты.** В `android-app/app/src/test` объявлено **154** класса `*Test`.
В CI упоминаются (`--tests ...`) — **47**. Значит, **107 классов не выполняются
никогда**, кроме машины разработчика. Среди них именно те, что закрывают
болезненные места:

```
DevicePairingWireTest     (pairing — главная жалоба владельца)
CallStateMachineTest, CallWireTest, CallMediaCryptoTest
BackupCipherTest, BackupManifestTest, BackupLayoutTest
DeliveryAckWireTest, DirectReplyWireTest, EphemeralControlTest
ApkUpdateTest, FileCustodyFlowTest, GroupPermissionsTest ...
```

Кроме того, в `src/androidTest` лежат **30** инструментальных тестов (в том числе
`FileTransferMigrationInstrumentedTest`, `GroupsMigrationInstrumentedTest`,
`IdentitySigningKeyStoreInstrumentedTest`), и ни один из них не запускается:
в workflows нет эмулятора.

Причина, скорее всего, историческая: в `build-release.yml` и
`scripts/ci/check-android-compile.sh` тесты перечислены вручную, чтобы
«не гонять всё». Список не поддерживается.

**Решение.**

1. В `build-release.yml` заменить список `--tests` на полный прогон:
   `./gradlew :app:testReleaseUnitTest --no-daemon` (сборка в CI занимает
   ~20 минут — полный прогон JVM-тестов на этом фоне стоит недорого; точное
   время надо замерить на первом прогоне).
2. Для тестов, которые падают, завести `@Ignore("причина, дата, тикет")` —
   честный список известных падений вместо тишины.
3. Добавить отдельный workflow с `reactivecircus/android-emulator-runner`
   на `ubuntu-latest` (`api-level: 30`, `target: google_apis`) для 30
   инструментальных тестов; в первую очередь — три migration-теста и
   `IdentitySigningKeyStoreInstrumentedTest`.
4. Отдельно запускать `DevicePairingWireTest` в каждом прогоне: это дешёвый
   JVM-тест, а pairing сейчас — самая проблемная фича.

### P0-4. Ключ подписи и пароль лежат в публичном репозитории

**Факты.**

- `android-app/app/p2p-release.jks` — **отслеживается git** (2706 байт).
- `android-app/app/build.gradle.kts:122-125`:

```kotlin
storeFile = file("p2p-release.jks")
storePassword = "p2p2026release"
keyAlias = "p2p"
keyPassword = "p2p2026release"
```

- `build-release.yml:186-191`: если секреты `APU_RELEASE_*` не заданы, шаг
  печатает warning и **оставляет подпись старым ключом из репозитория**.
- `docs/SIGNING_KEY_ROTATION.md` существует, но ротация не выполнена
  (`docs/START_HERE.md:1101` это прямо фиксирует).

**Состояние на 2026-10-26 (со слов владельца).** Ротация **выполнена**: новый
ключ лежит в GitHub Secrets (`APU_RELEASE_*`), родословная
`android-app/app/apu-signing-lineage` закоммичена. В открытом доступе остался
только **старый** ключ — это осознанное решение: при `minSdk 26` он нужен CI
как первый подписант v1/v2 для Android 8, где ротации ключа нет. Удалять его из
репозитория нельзя (это сломает подпись релиза), и защищать его поздно: он
раскрыт навсегда.

Что доделано в коде после этого:

- шаг «Require rotated signing key for a release» падает **до** 40-минутной
  сборки, если тег пришёл без секретов (раньше это выяснялось на шаге
  подписи, уже после сборки);
- контракт `scripts/ci/check-signing.py` стережёт: секреты объявлены, гейт
  стоит до сборки, «тихий» `exit 0` не может стоять раньше отказа, родословная
  закоммичена, `*.jks` в `.gitignore`, а в Gradle нет второго хранилища.

Остаётся риск, который кодом не закрывается: телефон на Android 8, ни разу не
обновившийся после ротации, по-прежнему принимает APK, подписанный старым
ключом.

**Последствия.** Любой человек может подписать APK этим ключом. Подпись такого
APK **совпадёт** с подписью установленного APU, поэтому Android спокойно
примет его как обновление: достаточно того же `applicationId` и
`versionCode` больше текущего. То есть злоумышленнику не нужно взламывать
телефон — достаточно подсунуть «обновление» (через тот же рой раздачи APK,
через ссылку, через любое приложение). Это полный контроль над устройством
пользователя.

**Решение (порядок из `SIGNING_KEY_ROTATION.md`, но выполнить до следующего
релиза):**

1. Сгенерировать новый ключ **вне** репозитория.
2. Положить его и пароль в GitHub Secrets: `APU_RELEASE_KEYSTORE_B64`,
   `APU_RELEASE_KEYSTORE_PASSWORD`, `APU_RELEASE_KEY_ALIAS`.
3. Оставить `apu-signing-lineage` (механизм уже реализован в
   `build-release.yml`) — Android примет новый ключ как преемника.
4. В `build.gradle.kts` убрать литералы: брать `storeFile` из переменной
   окружения/локального `local.properties`, а при отсутствии — собирать
   `unsigned` (debug-сборка это позволяет).
5. **Удалить `p2p-release.jks` из git** (`git rm --cached`) и добавить в
   `.gitignore` (уже есть `*.jks`) — файл останется в истории, поэтому ключ
   считается скомпрометированным навсегда, независимо от удаления.
6. Проверить, что при отсутствии секретов сборка **падает**, а не тихо
   подписывает старым ключом. Сейчас это warning — должно быть `exit 1`.

**Важная оговорка про lineage (её стоит понимать до, а не после).**
`apksigner rotate` создаёт файл родословной, подписанный **старым** ключом.
Android принимает новый ключ только у устройства, которое уже получило
обновление с этим файлом. Отсюда два следствия:

- Ротация защищает **будущие** обновления, но не отменяет того, что ключ уже
  утёк: пока телефон не обновился на сборку с lineage, он по-прежнему доверяет
  старому ключу — и злоумышленник может воспользоваться тем же механизмом,
  чтобы объявить преемником **свой** ключ. Поэтому ротацию надо выпускать
  срочно и следить, чтобы устройства реально обновились (счётчик версий в
  диагностике это уже показывает).
- Полного «лечения» у утёкшего ключа подписи не существует: это ровно та
  причина, по которой ключи подписи не хранят в репозиториях. Практическая
  цель — как можно быстрее перевести активные устройства на новый ключ и
  перестать выпускать сборки старым.

### P0-5. `fallbackToDestructiveMigration()` — тихая потеря всех сообщений

**Факт.** `android-app/app/src/main/java/com/vladimir/messenger/di/AppModule.kt:70`:

```kotlin
Room.databaseBuilder(...)
    .addMigrations( /* 33 миграции, 5 -> 38 */ )
    .fallbackToDestructiveMigration()   // <-- здесь
    .build()
```

Сама цепочка миграций полная (`APP_DATABASE_VERSION = 38`,
`MIGRATION_5_6 … MIGRATION_37_38` зарегистрированы все). То есть
`fallbackToDestructiveMigration` сейчас не нужен вообще — он срабатывает
только в аварийных случаях. Но именно в них он и опасен: если в следующем
релизе забыть миграцию или изменить сущность без `version++`, Room **молча
удалит все таблицы** — вся переписка, контакты и группы исчезнут без
исключения, без лога и без возможности восстановления.

**Решение.**

```kotlin
// Совсем убрать fallback: ошибка схемы должна быть громкой (краш + диагностика),
// а не «тихой амнезией» пользователя.
.addMigrations(...)
.build()
```

Если очень нужна поддержка древних установок (< v5), использовать адресный
вариант: `.fallbackToDestructiveMigrationFrom(1, 2, 3, 4)`.

**Дополнительно:** добавить в CI тест миграций
(`MigrationTestHelper`, `androidTest`) — три таких теста уже написаны
(`FileTransferMigrationInstrumentedTest` и др.), их просто никто не запускает
(см. P0-3).

## 3. P1 — высокий приоритет

### P1-1. Две функции с сетью по LAN не работают на Android 9+ (молча)

**Факты.**

- `ProfileSyncDirect.kt:195`: `URL("http://$host:$port/$token")` — приём
  резервной копии профиля по Wi-Fi («Синхронизировать аккаунт»).
- `MirrorLan.kt:148`: то же самое для первичной синхронизации по LAN.
- В `AndroidManifest.xml` **нет** `android:usesCleartextTraffic="true"` и нет
  `android:networkSecurityConfig`; в `res/xml` только `backup_rules`,
  `data_extraction_rules`, `file_paths`.

Начиная с `targetSdk 28` cleartext по умолчанию запрещён. `HttpURLConnection`
на `http://192.168.x.x` бросает `UnknownServiceException: CLEARTEXT communication
… not permitted by network security policy`. В `ProfileSyncDirect.pull()` это
`catch (e: IOException)` → `return false` с одной строкой `Log.w`
(«pull failed»), в `MirrorLan.pull()` — `runCatching { … }` → `false`.
Пользователь видит «не удалось», причина не видна никому.

**Решение.** Правильный путь — **перевести обмен на TLS**: сервер уже умеет
генерировать сертификат (`rcgen` в ядре), для LAN хватает самоподписанного
сертификата с проверкой отпечатка, который и так едет в QR/коде. Тогда
`network-security-config` не нужен вовсе, а метаданные перестают утекать.

Быстрый компромисс на один релиз (если TLS не успеть): разрешить cleartext
глобально и **ограничить его в коде** проверкой, что `host` — приватный адрес
(10/8, 172.16/12, 192.168/16, 169.254/16, fe80::/10), иначе отказ:

```xml
<!-- AndroidManifest.xml, application -->
android:usesCleartextTraffic="true"
```

```kotlin
// перед открытием соединения
require(isPrivateAddress(host)) { "cleartext allowed only for LAN" }
```

Учтите: `<domain-config>` в `network-security-config` умеет только имена хостов,
CIDR там нет — поэтому «разрешить только локальную сеть» декларативно не
выражается, нужна проверка в коде. Содержимое и так зашифровано
(`ProfileBackup` + `BackupCipher`), но метаданные (кто, когда, размер) при
открытом HTTP видны в эфире — это надо честно написать в release notes.

**Проверка:** два телефона, Android 12+ и 14+, «Синхронизировать аккаунт» по
Wi-Fi без интернета.

**Как исправлено (2026-10-26).** Взят не глобальный `usesCleartextTraffic`, а
узкий транспорт `data/net/LanHttpGet.kt`: тот же HTTP/1.1 поверх `Socket`,
который отдающая сторона и так обслуживает. Причины: глобальный флаг молча
разрешает cleartext **всему** приложению (включая будущие запросы), а
`<domain-config>` не умеет диапазоны IP. Клиент пускает соединение только к
локальному адресу — проверяется РАЗРЕШЁННЫЙ адрес (`isSiteLocalAddress`,
loopback, link-local), поэтому имя, ведущее на публичный IP, не проскочит.
Платформенная политика для остальных сетевых вызовов осталась строгой.
Добавлен юнит-тест на loopback-сервере и отказ для `8.8.8.8`.
Перевод на TLS с проверкой отпечатка из QR остаётся следующим шагом (метаданные
в эфире всё ещё видны).

### P1-2. `panic = "abort"` в релизном профиле ядра

**Факт.** `rust-core/Cargo.toml`:

```toml
[profile.release]
opt-level = 3
lto       = true
strip     = true
panic     = "abort"
```

UniFFI ловит паники и превращает их в `InternalException` только при
`panic=unwind`; с `abort` любая паника — это `SIGABRT` всего процесса
мессенджера, без стектрейса в Kotlin и без шанса показать ошибку.

Хорошая новость: паникующих мест в production-коде немного. Из 2108 вхождений
`unwrap/expect/panic!` подавляющее большинство — в `#[cfg(test)]`. Вне тестов и
вне `Mutex::lock().unwrap()` (который при `abort` не может «отравиться»)
остаётся **~50** мест, и почти все проверяют длину через `?` перед
`try_into().unwrap()`.

**Решение.** Снять `panic = "abort"` (цена — доли процента скорости и
+1–2 % размера `.so`) и добавить `catch_unwind`-политику на FFI-границе.
Это превращает «приложение умерло» в «операция вернула ошибку».

Если `abort` остаётся сознательно (размер/скорость), то:
- запретить `unwrap()` в `network/**` и `storage/**` линтом
  (`#![deny(clippy::unwrap_used)]` для этих модулей);
- в `catch_unwind`-недоступной среде хотя бы логировать входные данные
  последнего пакета перед разбором.

**Как исправлено (2026-10-26).** В `rust-core/Cargo.toml` релизный профиль
переведён на `panic = "unwind"`. Ветка `CALL_PANIC → throw
InternalException("Rust panic")` в сгенерированном мосте
(`uniffi/p2p_core/p2p_core.kt`) существует давно, но при `abort` была
недостижима: паника в ядре убивала процесс раньше, чем uniffi успевал
вернуть статус. Теперь паника в Rust превращается в исключение Kotlin —
операция возвращает ошибку вместо «Приложение остановлено». Контракт
`scripts/ci/check-rust-pinning.py` не даст вернуть `abort` обратно.

### P1-3. `Cargo.lock` не в git → сборки невоспроизводимы

**Факты.**

- `.gitignore` содержит `Cargo.lock`; `git ls-files | grep Cargo.lock` — пусто.
- `ci-core-check.yml` кэширует cargo по ключу
  `hashFiles('rust-core/Cargo.lock')` — ключ всегда пустой, кэш не работает
  (каждый прогон тянет и собирает зависимости заново).

Для приложения (а не библиотеки) `Cargo.lock` **обязан** быть в репозитории:
иначе `cargo build` может подтянуть новую минорную версию `quinn`/`rustls`/
`rumqttc`, и релизный `.so` соберётся из другого кода, чем проверялся вчера.
Для мессенджера с собственным крипто-стеком это ещё и вопрос аудита: «какой
именно код у пользователя».

**Решение.**

```bash
git add rust-core/Cargo.lock tools/uniffi-bindgen/Cargo.lock
# и убрать строку Cargo.lock из .gitignore
```

плюс зафиксировать версию Rust в CI (`dtolnay/rust-toolchain@1.99.1` вместо
`@stable`) — сейчас `stable` уже дважды менялся в течение проекта.

**Как исправлено (2026-10-26).** Строка `Cargo.lock` убрана из `.gitignore`,
версия закреплена в `rust-toolchain.toml` (`1.99.1`) и продублирована во всех
четырёх workflow — иначе android-target'ы поставились бы для `stable`, а
собирал бы закреплённый компилятор. Самого `Cargo.lock` в песочнице нет
(cargo недоступен, а crates.io закрыт), поэтому первый lock создаёт
`sync-bindings.yml` — он генерирует оба файла и коммитит их вместе с мостом.
`unit-tests.yml` до первого коммита печатает предупреждение, после — падает
на устаревшем lock-файле. Контракт — `scripts/ci/check-rust-pinning.py`.

### P1-4. APK вырос в 2,4 раза за 12 дней

По данным GitHub Releases:

| Релиз | Размер APK |
|---|---|
| v11.74.355 (14.10) | 96 603 009 Б |
| v11.74.400 | 228 395 213 Б |
| v11.74.447 | 229 259 299 Б |
| v11.74.452 (26.10) | 229 328 931 Б |

Причины видны в `build.gradle.kts`: `isMinifyEnabled = false` для release,
`isShrinkResources` не включён, `abiFilters` — три ABI, а состав зависимостей
пополнился тяжёлыми `vosk-android:0.3.47` (тащит JNA и нативные библиотеки),
`mlkit:segmentation-selfie` (встроенная модель), `mlkit:translate`,
`media3-*`, `eddsa`, `jna@aar`.

**Последствия.** 229 МБ на телефоне, 229 МБ мобильного трафика при обновлении,
и ровно столько же нужно раздать роем (см. `docs/UPDATE_SEEDING.md`) — то есть
каждое обновление теперь стоит пользователям в разы дороже.

**Решение (по убыванию эффекта):**

1. Включить R8 и сжатие ресурсов:
   `isMinifyEnabled = true`, `isShrinkResources = true`, `proguardFiles(...)`,
   правила для JNA/UniFFI/ML Kit (они уже частично есть в репозитории — надо
   проверить `keep` для `uniffi.p2p_core.**` и `com.sun.jna.**`). Экономия
   обычно 25–40 %.
2. Раздавать **AAB** или отдельные APK по ABI (`splits { abi { ... } }`):
   у пользователя останется один ABI вместо трёх. Только нативных библиотек
   APU сейчас 9,3 МБ (arm64) + 6,7 МБ (armeabi-v7a), плюс столько же нативных
   частей JNA/Vosk в каждой ABI — экономия ощутимая, точную цифру даст
   `apkanalyzer files list`.
3. Vosk и ML Kit модели вынести в загрузку по требованию (у Vosk модель языка
   и так качается отдельно, но нативная часть библиотеки — нет).
4. Замерить вклад каждой зависимости: `./gradlew :app:assembleRelease` +
   [apkanalyzer](https://developer.android.com/studio/command-line/apkanalyzer)
   `files list --split-by-file`. Без этого шага оптимизация будет наугад.

**Что сделано (2026-10-26).** Сокращение **подготовлено, но не включено** —
сознательно: включить R8 вслепую нельзя, а проверить сокращённую сборку можно
только установкой на телефон (`uniffi → JNA`, Vosk и ML Kit общаются через
рефлексию; пропущенное keep-правило выглядит как падение на старте у людей).

- добавлен `android-app/app/proguard-rules.pro` с keep-правилами для
  `uniffi.**`, `com.sun.jna.**`, `org.vosk.**`, ML Kit, osmdroid, Room-сущностей
  и с сохранением имён/строк для читаемых стектрейсов;
- в `build.gradle.kts` сокращение включается **явно**:
  `./gradlew :app:assembleRelease -Papu.r8=true` (`isMinifyEnabled`,
  `isShrinkResources`). По умолчанию релиз собирается как раньше;
- из APK убраны служебные файлы зависимостей (`META-INF/LICENSE*`,
  `NOTICE*`, `DEPENDENCIES`, `*.version`) — это не влияет на поведение;
- удалена устаревшая копия нативных библиотек `rust-core/jniLibs` (390 КБ
  против 9,2 МБ в `android-app/…/jniLibs`; сборка её никогда не использовала) —
  P2 п. 4.7.

**Что осталось и требует решения.** ABI-сплиты и AAB сокращают APK сильнее
всего, но меняют раздачу: `build-release.yml` публикует ровно один
`app-release.apk`, и рой (`docs/UPDATE_SEEDING.md`) раздаёт один файл.
Варианты: (а) оставить универсальный APK и включить R8 (наибольший эффект без
смены раздачи); (б) собирать per-ABI и раздавать тот, что подходит телефону —
нужна правка публикации, роя и ссылок; (в) перейти на AAB для Play и оставить
APK для роя. Выбор — за владельцем.

### P1-5. `FileProvider` отдаёт произвольный файл

`res/xml/file_paths.xml`:

```xml
<root-path name="root" path="." />
```

`root-path` — это корень файловой системы `/`. Значит, приложение технически
может выдать `content://…` на любой файл, к которому имеет доступ — включая
чужие каталоги, доступные процессу. Сейчас это «всего лишь» избыточные права,
но любой будущий баг «поделиться файлом по пути из сообщения» станет утечкой.

**Решение.** Заменить на точный каталог, который действительно нужен
(в комментарии сказано: `noBackupFilesDir/file_received`):

```xml
<root-path name="apk" path="data/user/0/com.vladimir.messenger/no_backup/file_received" />
<files-path  name="files"    path="." />
<cache-path  name="cache"    path="." />
```

и убрать `<external-path>`/`<external-files-path>`, если они не используются.

**Как исправлено (2026-10-26).** Предложенный выше `<root-path ... no_backup/...>`
не работает: `FileProvider` берёт `root-path` от корня `/` и **не знает тега
`no-backup-path`** (в `FileProvider.java` разбираются только `root-path`,
`files-path`, `cache-path`, `external-path`, `external-files-path`,
`external-cache-path`, `external-media-path`). Поэтому:

- раздача APK переехала из `noBackupFilesDir/apk_seed/v1` в
  `filesDir/apk_seed/v1` (`data/update/UpdateFileRoots.kt`) с переносом уже
  скачанного при первом старте;
- принятый APK, который лежит в `noBackupFilesDir/file_received`, перед
  установкой копируется в объявленный `cache/updates`;
- в `file_paths.xml` вместо корня — десять подкаталогов «на передачу»
  (аватар, обои, раздача APK, копии для «Поделиться», голос, снимок истории,
  патч, приглашение, письмо обратной связи, папка «Загрузки»), и ни одного
  `path="."`.

Проверка — `scripts/ci/check-file-provider.py`: нет `root-path`, нет корней
хранилища, каждый каталог из `getUriForFile` объявлен, установка из
`noBackupFilesDir` идёт через копию. Контракт также ловит класс ошибки,
который уже случался в этом проекте: «Failed to find configured root» —
кнопка «Установить» молчала, потому что каталог не был объявлен.

### P1-6. Аварийный будильник: батарея + внешний запуск

`EmergencyKeepAlive.kt`:

- `scheduleNext()` взводит **точный** будильник каждые 5 минут и
  перевзводится при каждом старте сервиса — это 288 пробуждений в сутки,
  даже когда всё работает. `setExactAndAllowWhileIdle` в Doze — самый
  дорогой по батарее механизм, который есть в Android.
- `EmergencyKeepAliveReceiver` объявлен `android:exported="true"`. Любое
  приложение может послать ему явный intent и заставить поднимать
  foreground-сервис — бесплатный способ разрядить чужой телефон (и
  подставить ваш пакет под «злоупотребление батареей»).
- `startForegroundService` обёрнут в `runCatching` — отказ невидим.

**Решение.**

1. `exported="false"` (BOOT_COMPLETED системой доставляется и так; если
   проверка на устройстве покажет обратное — оставить `exported="true"`, но
   добавить проверку `intent.action == ACTION_PUMP || intent.action == ACTION_BOOT_COMPLETED`).
2. Разнести два сценария: «сервис жив» → обычный `Handler`/корутина с
   `delay(5 min)`, без будильника; «сервис убит» → будильник с возрастающим
   интервалом (5 → 15 → 30 → 60 минут, максимум 60).
3. После успешного старта сервиса снимать будильник (`am.cancel(pi)`), а не
   перевзводить; взводить только из `onDestroy`/`onTaskRemoved`.
4. Логировать отказ старта (`Log.e` + счётчик в диагностике), см. P0-1.

**Как исправлено (2026-10-26).** Пункты 1 и 4 были закрыты раньше (allowlist
действий в `onReceive`, счётчики `FOREGROUND_START_REFUSED`/`FOREGROUND_TIMEOUT`).
Пункты 2–3 сделаны теперь:

- сервис жив → одна **неточная** страховка в час (`setAndAllowWhileIdle`):
  если процесс убьют без колбэка, сервис вернётся в течение часа. Было 288
  точных пробуждений в сутки — стало 24 неточных;
- старт не удался (отказ `startForeground`, таймаут foreground, запрет старта
  из фона) → **точные** повторы по лестнице 5 → 15 → 30 → 60 минут, счётчик
  подряд идущих отказов хранится в SharedPreferences, чтобы после
  перезагрузки не начинать с пяти минут заново;
- успешный старт сбрасывает счётчик.

Приёмник остаётся `exported="true"`: на части прошивок `BOOT_COMPLETED`
доходит только так, а посторонние действия отсекаются allowlist'ом.
Контракт — `scripts/ci/check-emergency-keepalive.py`, поведение лестницы —
`EmergencyKeepAliveLadderTest` (JVM).

### 4.3. Нет статического анализа вообще

### 4.5. Чтение файлов целиком в память

`readBytes()` на потенциально больших файлах:
`ProfileBackup.kt:472,485` (резервная копия), `ProfileSyncNet.kt:192`,
`FileTransferKeyVault.kt:206,311`, `AddressBookBackup.kt:109,330`.
Для копии профиля есть лимит 32 МБ в `ProfileSyncDirect`, но в
`ProfileSyncNet` лимита не видно; `FileTransferKeyVault` доверяет размеру
файла. На бюджетном телефоне 2 ГБ RAM это путь к `OutOfMemoryError`.

**Решение.** Потоковая обработка (`DigestInputStream`, `CipherInputStream`) там,
где не нужен весь массив, и явный лимит размера **до** чтения (как сделано в
`ProfileSyncDirect.MAX_COPY_BYTES`).

**Сделано (2026-10-26).** Добавлен `util/BoundedFiles.kt`: `readBytesAtMost`
(лимит проверяется до выделения памяти и повторно во время чтения),
`sha256Hex` (сумма файла потоком) и `copyWithLimit` (перелив потоком).
Применено:

- `AddressBookBackup`: `fileSha` считает сумму потоком (раньше файл целиком
  читался ради 32 байт), снапшот читается с потолком 4 МБ.
- `ProfileBackup`: файлы секретов при восстановлении читаются с потолком
  64 КБ; слишком большой файл трактуется как отсутствующий, с записью в лог.
- `FileTransferKeyVault`: конверт и софт-ключ читаются с лимитом, равным
  ожидаемой длине (закрывает гонку «файл вырос после проверки `length()`»).
- `ProfileSyncNet`: отправка больше не собирает base64 в строку — кодирование
  идёт потоком прямо в сокет, длина объявлена через
  `setFixedLengthStreamingMode` (иначе `HttpURLConnection` буферизует тело
  целиком и выигрыша нет). Скачивание так же разбирается потоком через
  `Base64InputStream`. Предел проверяется по размеру файла
  (`MAX_RAW_BYTES = 18 000 000` — ровно столько, сколько влезает в 24 МБ
  base64), тела ошибок релея ограничены 8 КБ.
- `ProfileSyncDirect`: раздача копии идёт потоком и не больше `MAX_COPY_BYTES`.

Пиковое потребление на отправке копии упало примерно с 90 МБ (файл + строка
base64 в UTF-16 + ASCII-массив) до буфера 64 КБ. Инвариант «сколько байт
влезает в лимит» и границы `readBytesAtMost` закреплены JVM-тестами
`BoundedFilesTest` и `ProfileSyncUploadSizeTest`.

### 4.6. Установка APK без проверки разрешения

В коде нет ни одного `canRequestPackageInstalls()` / `ACTION_MANAGE_UNKNOWN_APP_SOURCES`.
На Android 8+ `REQUEST_INSTALL_PACKAGES` — специальное разрешение, которое
пользователь выдаёт вручную; при отказе интент установки просто ничего не
делает (иногда — с системным диалогом, иногда молча).

**Решение.** Перед `startActivity(installIntent)`:

```kotlin
if (Build.VERSION.SDK_INT >= 26 && !packageManager.canRequestPackageInstalls()) {
    startActivity(Intent(Settings.ACTION_MANAGE_UNKNOWN_APP_SOURCES,
        Uri.parse("package:$packageName")))
    return
}
```

## 9. Чего в этом аудите нет

  подтвердить на реальном устройстве (Android 9/12/14/15).
- **Не проверены Rust-тесты** (`cargo test` недоступен); известно лишь, что
  последний зелёный `Core compile check` был 8 дней назад, а сейчас workflow
  падает на эвристике.
- **Не измерялась производительность**: 446 МиБ PSS из прошлого отчёта
  `DIAGNOSTICS_REVIEW_2026-10-16.md` не проверялись повторно.
- **Не проводился аудит криптопротокола pairing построчно** (только

  `rust-core/src/crypto/device_pairing.rs` (41 КБ) с моделью угроз.
