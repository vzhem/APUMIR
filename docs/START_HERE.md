## 1. Суть проекта (одно дыхание)

**APU** (`com.vladimir.messenger`, репо `vzhem/APUMIR`) — Android-мессенджер
с Rust-ядром. Главная цель владельца: **надёжная и максимально быстрая
передача файлов любого практического размера через любые сети БЕЗ своих

(темы день/ночь, обои, золотые акценты, всё по-русски, термин «@никнейм»).

## 4. Первые три шага нового чата (обязательно, до задачи)

1. **Выровнять песочницу по `main`.** Ориентир один — `main` (раздел 9);
   ветка прошлого чата не нужна. Если песочница ещё не склонирована:
   `git clone https://github.com/vzhem/APUMIR <папка>` — обычный clone даёт
   ветку `main`, полную историю и все 49 тегов (проверено 2026-08-29).
   Если песочница Arena уже открыта, она приходит **обрезанной и
   одноветочной**, поэтому порядок такой:
   `git config remote.origin.fetch '+refs/heads/*:refs/remotes/origin/*'` →
   `git fetch origin --prune` → `git fetch --tags origin` →
   `git fetch --unshallow origin main` (если `git rev-parse
   --is-shallow-repository` печатает `true`) → `git reset --hard origin/main`
   (если в рабочем столе нет неприкаянных правок; если есть — сначала
   `git reset -q origin/main` и посмотри `git status`).
   Кончик всегда бери из `git ls-remote origin refs/heads/main`, а не из этого
   файла — текст устаревает. Правда о сервере — `git ls-remote origin`:
   в одноветочном клоне `git fetch origin <не-main>` не создаёт
   `origin/<ветка>`, а пишет только в `FETCH_HEAD`.
2. **Прочитать** раздел 2 и в первом ответе владельцу коротко назвать:
   последнюю выпущенную версию, кончик ветки, что доказано на телефонах,
   что НЕ доказано.
3. **НЕ начинать код по своему почину.** Владелец сам даст серьёзную задачу.
   До неё — только чтение и короткий честный доклад.

## 5. Правила владельца (нарушать нельзя)

- Один маленький шаг: правка → проверка → следующий шаг. Проект не
  перезапускать, не переписывать «с нуля».
- По-русски и простыми словами; объяснять, какие этапы «молчат» и как
  проверить живость.
- **Телефоны не трогать** без явного предупреждения и поимённо. Устройства
  (серийники встречаются в `docs/AI_HANDOFF.md`, `docs/MASTER_PLAN_v2.md` и
  журнале): Стас `11567254BK001192`, Аня `AUYF6R5923006121`,
  Женя `3B665800EES00000`. Командами на телефоне занимается сам владелец.
- **Команды для Windows (правило от 2026-08-29, усилено после краша).** Каждая
  команда даётся В ОТДЕЛЬНОМ блоке кода из ОДНОЙ строки (```` ```powershell ````
  + одна строка), чтобы владелец жал «скопировать» и не тянул лишнего.
  Строка всегда начинается со слова `powershell` и рассчитана на НОВОЕ окно
  PowerShell: `powershell -NoProfile -ExecutionPolicy Bypass -File
  C:\APU-M8\scripts\<имя>.ps1` либо `powershell -NoProfile -ExecutionPolicy
  Bypass -Command "<одна команда git с -C C:\APU-M8>"`. Пути — абсолютные,
  от текущего каталога не зависеть. Никогда не давать: многострочные блоки
  (были парс-краши), команду с опечаткой (даже с исправлением в том же
  сообщении), команду, где первое слово можно потерять при копировании.
  Если у владельца вылетело `-NoProfile : Имя "-NoProfile" не распознано...` —
  это значит, что при копировании потерялось слово `powershell`; сказать ему
  «закройте окно, откройте новое и вставьте команду целиком», а не давать
  команду заново в другом виде.
- **В командах владельцу НЕ использовать `$`-переменные** (ошибка агента
  2026-08-29): строка `-Command "... if ($LASTEXITCODE -eq 0) ..."` до git не
  дошла — ВНЕШНИЙ PowerShell подставил `$LASTEXITCODE` пустым местом, и
  получилось `if ( -eq 0)` с ошибкой `-eq : Имя "-eq" не распознано...`.
  Команда владельцу = ОДИН вызов git/программы без `$`, без `if`, без `;`.
  Проверку «входит ли коммит в main» делать идиомой без переменных:
  `git merge-base <коммит> origin/main` — если напечатан тот же хеш, что
  спрашивали, коммит внутри `main`; если другой — НЕ внутри.
  (`git rev-list --count <коммит>..origin/main` для этого НЕ годится: он всегда
  печатает число больше нуля.)
- **Никогда не давать владельцу `merge` без `fetch`** (ошибка агента
  2026-08-29, дважды): `git merge --ff-only origin/main` двигает только до того
  `origin/main`, который УЖЕ скачан, поэтому новый файл/скрипт до владельца не
  доезжает, и следующая команда падает с `Аргумент ... для параметра -File не
  существует`. Варианты: либо две команды (`fetch`, потом `merge`), либо одна
  `git -C C:\APU-M8 pull --ff-only` (она сама делает fetch). И наоборот: если
  файл нужен СЕЙЧАС, а сети нет — не гонять владельца за скриптом, а дать
  разовые команды чистым git.
- git без пайплайнов и без `2>$null`; перед КАЖДЫМ коммитом `git log --oneline -1`;
  при рассинхроне fetch + reset. Коммиты/пуш своей arena-ветки — без спроса;
  **релиз/тег — только с явного разрешения**.
- `.github/workflows/*` не пушить и не менять.
- Юнит-тесты не смешивать с assemble в одном `--tests`; «зелёный фильтр» ≠ гейт.
- Грубый brace-чекер врёт — есть лексер `tools/sandbox/struct_check.py`
  (полная версия; короткие ранние копии лежат в `tools/` и не являются
  эталоном).
- Свежесть сборки на телефоне смотреть по `dumpsys lastUpdateTime`;
  установка только `adb install -r -t -d`.
- Непроверенное на экране называть непроверенным. Имя приложения — «APU».
- **Резервная копия — после каждого релиза** (уточнение владельца
  2026-08-29): как только релиз выпущен (или вот-вот будет выпущен), агент сам
  предлагает владельцу «вставьте белую флешку (метка `APU_BACKUP`)» и одну
  команду (**powershell**):
  `powershell -NoProfile -ExecutionPolicy Bypass -File C:\APU-M8\scripts\backup-to-flash.ps1`.
  После мелких промежуточных правок предлагать не обязательно — владелец сам
  скажет, когда обновить.

  `git rev-list -n 1 v11.17.1` и `git ls-remote origin "refs/tags/v11.17.1*"`

  опубликован APK именно с `6deb532` (релиз `APU v11.17.1`,
  `app-release.apk` 35 285 255 байт). Лечение — `scripts/fix-tags.ps1`:
  он приводит ЛОКАЛЬНЫЕ теги к origin, проверяя достижимость, и не трогает
  теги, которых в origin нет.
- **`^{}` в строке `-Command "..."` ломает PowerShell** (2026-08-29): владелец
  получил `git.exe : ScriptBlock следует указывать только в качестве значения
  для параметра Command` — фигурные скобки PowerShell читает как блок кода.
  В командах для владельца синтаксис `v11.17.1^{commit}` и
  `refs/tags/v11.17.1^{}` НЕ использовать. Замена: `git rev-list -n 1 <тег>`

## 7. Как устроен выпуск релиза (проверено на v11.23.0)

1. `scripts/make-release.ps1 -Version vX.Y.Z -ExpectedCommit <sha>` —
   проверяет чистоту дерева, гоняет гейт, ставит тег и пушит.
2. GitHub Actions (`.github/workflows/build-release.yml`) собирает подписанный
   `app-release.apk` (~12–20 мин) и публикует **PRERELEASE** с body-заглушкой.
3. `scripts/promote-release.ps1 -Version vX.Y.Z` — ждёт релиз с APK, снимает
   prerelease, делает draft → publish, сверяет `/releases/latest`.
4. `gh release edit vX.Y.Z -R vzhem/APUMIR --notes-file docs\RELEASE_NOTES_<версия>.md`
   — краткие заметки (их видит окно обновления в приложении).
5. **Догнать `main`** (см. раздел 9): рабочий кончик должен попасть в `main`
   в тот же день, иначе `main` снова превращается в мёртвую ветку.

## 9. Как правильно устроен репозиторий на GitHub (правило от 2026-08-29)

**Что должно быть:**

- `main` — ЕДИНСТВЕННАЯ ветка правды. Это «то, что сейчас у людей в телефонах
  плюс документация». Она обязана совпадать с рабочим кончиком (или отставать
  максимум на текущую сессию). Все теги-релизы стоят на коммитах, которые
  входят в `main`.
- Теги `vX.Y.Z` — единственные метки релизов. Сборку запускает только пуш тега
  (`build-release.yml`: `on: push: tags: v*`), поэтому ни мерж в `main`, ни пуш
  обычной ветки релиз НЕ собирают и ничего не публикуют.
- **Правда о теге одна — тег в origin.** Локальный тег, который разошёлся с
  origin, — это авария: `fetch --tags` начинает падать с
  `(would clobber existing tag)`, а `sync-main.ps1` из-за этого
  останавливается. Лечение: `scripts/fix-tags.ps1` (сначала `-DryRun`).
  Ставить тег вручную в обход `scripts/make-release.ps1` нельзя.
- Рабочая ветка сессии `arena/<id>-apumir` — одна живая, пока идёт сессия.
  Она обязана быть потомком `main` (иначе `main` не обновить fast-forward).
- Всё остальное — мусор. Ветку «на память» не держим: история и так в `main`,
  релизы — в тегах и GitHub Releases.

**Что писать владельцу при входе в новый чат:** всегда **`main`** — не ветку
прошлого чата. Arena сама создаёт агенту ветку `arena/<id>-apumir`, и агент
обязан в конце сессии догнать `main` (порядок ниже), поэтому на входе любого
следующего чата `main` уже содержит всю работу.

**Порядок в конце сессии (обязательно):**

1. `git fetch origin main` → `git merge origin/main` (втянуть `main` в рабочую
   ветку, разрулить конфликты в пользу рабочего кода);
2. `git push origin <рабочая ветка>`;
3. обновить `main`: fast-forward-мерж рабочей ветки в `main` — через PR,
   который жмёт владелец, либо одной командой на его ПК (**powershell**):
   `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\sync-main.ps1`;
4. проверить: `git ls-remote origin refs/heads/main` = рабочему кончику.

**Запрещено:**

- держать релиз отдельной веткой (`release-*`) вместо тега;
- принимать в `main` чужие `.gitignore`/сборочные файлы не глядя: глобальный
  `*.so` в `.gitignore` ломает отслеживание
  `android-app/app/src/main/jniLibs/*/libp2p_core.so`;
- плодить ветки: одна сессия — одна ветка, и она продолжает предыдущую,
  а не начинает с `main`.

**Что случилось и почему (2026-08-29, разбор для владельца):**

1. `main` не догоняли с 2026-08-17: в нём висел `6d28249`, а 628 коммитов
   раундов 11–46 жили только в ветках `arena/*`.
2. Каждая новая Arena-сессия создавала СВОЮ ветку, а не продолжала прошлую —
   накопилось 12 веток `arena/*` (в 11 из них не было ни одного уникального
   коммита).
3. 2026-08-17 в `main` влили PR #3 от бота (`qwen.ai[bot]`, ветка
   `instructions-for-the-new-ai-agent-bc4fe`): три файла
   (`create_store_forward.py`, `rust-core/src/network/store_and_forward.rs`,
   `scripts/setup_offline_delivery.ps1`) — Rust-модуль нигде не подключён к
   сборке, не гейтован и не релизнут, плюс переписанный `.gitignore`
   (начинался с markdown-забора ```rust и игнорировал `*.so`). При выравнивании
   2026-08-29 эти файлы сохранены в истории как есть, а `.gitignore` и
   `rust-core/src/network/mod.rs` оставлены рабочие — чужой модуль в сборку
   НЕ включён.
4. Релиз v11.16.1 выпустили веткой `release-v11.16.1`, а не тегом: коммит
   `93d6a4c` (versionName v11.16.1) не входит в тег `v11.16.1` (тег стоит на
   `8ed534e`). Сегодня это не важно: версию берёт из имени тега
   `build-release.yml` (`Sync versionName with tag`).
5. Старые ветки удалены после проверки «в ней нет ничего, чего нет в `main`»
   (`git rev-list --count main..<ветка>` = 0). Проверка перед удалением
   обязательна.
