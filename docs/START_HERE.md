## 4. Первые три шага нового чата (обязательно, до задачи)

1. **Выровнять песочницу.** Локальный HEAD в Arena-песочнице может висеть на
   старом базовом коммите, даже когда все работы давно запушены. Теперь
   достаточно одного ориентира — `main` (см. раздел 9):
   `git fetch origin main` → `git reset --hard FETCH_HEAD` (если в рабочем
   столе нет неприкаянных правок; если есть — сначала `git reset -q FETCH_HEAD`
   и посмотри `git status`). Кончик всегда бери из `git ls-remote origin
   refs/heads/main`, а не из этого файла — текст устаревает.
   Три грабли самой песочницы:
   - нет тегов по умолчанию → `git fetch --tags origin`;
   - клон **обрезанный** (shallow, 1 коммит) → `git fetch --unshallow origin main`;
   - клон **одноветочный** (`git config --get-all remote.origin.fetch` показывает
     только `+refs/heads/main:refs/remotes/origin/main`), поэтому
     `git fetch origin <любая другая ветка>` не создаёт `origin/<ветка>`, а
     пишет только в `FETCH_HEAD`. Правда о сервере — `git ls-remote origin`.
2. **Прочитать** раздел 2 и в первом ответе владельцу коротко назвать:
   последнюю выпущенную версию, кончик ветки, что доказано на телефонах,
   что НЕ доказано.
3. **НЕ начинать код по своему почину.** Владелец сам даст серьёзную задачу.
   До неё — только чтение и короткий честный доклад.

## 7. Как устроен выпуск релиза (проверено на v11.23.0)

1. `scripts/make-release.ps1 -Version vX.Y.Z -ExpectedCommit <sha>` —
   проверяет чистоту дерева, гоняет гейт, ставит тег и пушит.
2. GitHub Actions (`.github/workflows/build-release.yml`) собирает подписанный
   `app-release.apk` (~12–20 мин) и публикует **PRERELEASE** с body-заглушкой.
3. `scripts/promote-release.ps1 -Version vX.Y.Z` — ждёт релиз с APK, снимает
   prerelease, делает draft → publish, сверяет `/releases/latest`.
4. `gh release edit vX.Y.Z -R vzhem/APUMIR --notes-file docs\RELEASE_NOTES_<версия>.md`
   — краткие заметки (их видит окно обновления в приложении).
5. **Догнать `main`** (см. раздел 9): рабочий кончик должен попасть в `main`
   в тот же день, иначе `main` снова превращается в мёртвую ветку.

## 9. Как правильно устроен репозиторий на GitHub (правило от 2026-08-29)

**Что должно быть:**

- `main` — ЕДИНСТВЕННАЯ ветка правды. Это «то, что сейчас у людей в телефонах
  плюс документация». Она обязана совпадать с рабочим кончиком (или отставать
  максимум на текущую сессию). Все теги-релизы стоят на коммитах, которые
  входят в `main`.
- Теги `vX.Y.Z` — единственные метки релизов. Сборку запускает только пуш тега
  (`build-release.yml`: `on: push: tags: v*`), поэтому ни мерж в `main`, ни пуш
  обычной ветки релиз НЕ собирают и ничего не публикуют.
- Рабочая ветка сессии `arena/<id>-apumir` — одна живая, пока идёт сессия.
  Она обязана быть потомком `main` (иначе `main` не обновить fast-forward).
- Всё остальное — мусор. Ветку «на память» не держим: история и так в `main`,
  релизы — в тегах и GitHub Releases.

**Порядок в конце сессии (обязательно):**

1. `git fetch origin main` → `git merge origin/main` (втянуть `main` в рабочую
   ветку, разрулить конфликты в пользу рабочего кода);
2. `git push origin <рабочая ветка>`;
3. обновить `main`: fast-forward-мерж рабочей ветки в `main` — через PR,
   который жмёт владелец, либо одной командой на его ПК (**powershell**):
   `powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\sync-main.ps1`;
4. проверить: `git ls-remote origin refs/heads/main` = рабочему кончику.

**Запрещено:**

- держать релиз отдельной веткой (`release-*`) вместо тега;
- принимать в `main` чужие `.gitignore`/сборочные файлы не глядя: глобальный
  `*.so` в `.gitignore` ломает отслеживание
  `android-app/app/src/main/jniLibs/*/libp2p_core.so`;
- плодить ветки: одна сессия — одна ветка, и она продолжает предыдущую,
  а не начинает с `main`.

**Что случилось и почему (2026-08-29, разбор для владельца):**

1. `main` не догоняли с 2026-08-17: в нём висел `6d28249`, а 628 коммитов
   раундов 11–46 жили только в ветках `arena/*`.
2. Каждая новая Arena-сессия создавала СВОЮ ветку, а не продолжала прошлую —
   накопилось 12 веток `arena/*` (в 11 из них не было ни одного уникального
   коммита).
3. 2026-08-17 в `main` влили PR #3 от бота (`qwen.ai[bot]`, ветка
   `instructions-for-the-new-ai-agent-bc4fe`): три файла
   (`create_store_forward.py`, `rust-core/src/network/store_and_forward.rs`,
   `scripts/setup_offline_delivery.ps1`) — Rust-модуль нигде не подключён к
   сборке, не гейтован и не релизнут, плюс переписанный `.gitignore`
   (начинался с markdown-забора ```rust и игнорировал `*.so`). При выравнивании
   2026-08-29 эти файлы сохранены в истории как есть, а `.gitignore` и
   `rust-core/src/network/mod.rs` оставлены рабочие — чужой модуль в сборку
   НЕ включён.
4. Релиз v11.16.1 выпустили веткой `release-v11.16.1`, а не тегом: коммит
   `93d6a4c` (versionName v11.16.1) не входит в тег `v11.16.1` (тег стоит на
   `8ed534e`). Сегодня это не важно: версию берёт из имени тега

5. Старые ветки удалены после проверки «в ней нет ничего, чего нет в `main`»
   (`git rev-list --count main..<ветка>` = 0). Проверка перед удалением
   обязательна.
