# v11.74.529 — кто первый, кто потом

Собрано из ветки `arena/b19361a0-apumir` после `7687976`.

- В ядре появилась явная лестница важности трафика: **пробуждение и адрес →
  личное → тревога (SOS, звонок) → прочее своё (группы, файлы, «печатает») →
  чужое (пересылка для других узлов)**.
- У каждого класса свой запас внутри прежнего потолка своих записей (64 / 608 /
  64 / 264 из 1000): групповой поток больше не может занять очередь личной
  переписки, а личная — место для адреса собеседника.
- При переполнении уступает самый неважный класс, и только внутри него — самая
  старая запись. Адрес и пробуждение не вытесняются ничем, кроме другого
  пробуждения: кусок файла теперь теряется сам, а собеседник остаётся
  разбудимым.
- Чужое по-прежнему живёт в отдельном запасе: пересылка для других узлов не
  может ни вытеснить, ни задержать свой трафик.
- Журнал: строка `Relay-очередь:` печатает разбивку
  `по-важности=[пробуждение N, личное N, тревога N, прочее N, чужое N]` —
  видно, что именно стоит в очереди, а не только «своих=181».
- Android ставит подсказку `push1-` в id анонса эпохи: тело запечатано, иначе
  класс не определить.
- Сайт: выкладка переживает обрыв FTP — повтор на новой сессии с того файла, на
  котором оборвалось (крупный APK не заливается заново). Причина двух упавших
  выкладок 528 — `TimeoutError` на крупном файле.

**Как проверить:** в журнале процесса найти строку `Relay-очередь:` — в
`по-важности=[...]` видно, что ждёт получателя. На телефоне: при занятой
групповой переписке личное сообщение должно уходить, а не стоять за группой.

**Что ещё не сделано:** очередь входящих MQTT (`LossIntolerantInbox`) до сих
пор одна общая FIFO на 256 записей — чужой поток релея может занять её целиком
и задержать чтение своих пакетов. Это следующий шаг той же задачи.
