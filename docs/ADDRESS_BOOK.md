# АЗБУКА АДРЕСОВ (`ADDRESS_BOOK`)

**Дата:** 2026-09-18. **Статус:** дизайн утверждён, реализация на ветке
`arena/01a0b3cb-apumir` (шаг за шагом), телефоны не проверены, первый
полный компилятор — CI тега. **Релиза нет.**

Задача владельца (своими словами):

> «Нужно, чтобы файл был, и после перезапуска проверялась связь, и если
> кого-то находил на связи — запрашивал бы у него свежие адреса для
> обновления файла. … поддерживался актуальным постоянно.»

Подозрение владельца: именно несведённый список адресов рвёт связь между
абонентами — особенно когда перезагружают телефон, меняют связь
(домашняя Wi-Fi ↔ мобильная) или переустанавливают приложение.

## 1. Почему так бывает (как есть в коде)

Все адреса пинов живут **только в памяти** ядра: `peer_addrs` в
`P2PCore` (`rust-core/src/engine/core.rs`) — `HashMap<node_id, SocketAddr>`.
При каждом старте телефона список пуст:

- личное presence (K4-1) ходит «своим» — но список «своих» тоже пуст,
  Kotlin его никогда не заполнял (FFI-метод `set_presence_audience`
  существовал, а вызывался ни разу);
- DHT-запрос «узнай адрес» (K4-2) можно отправить только тому, с кем уже
  есть живое соединение;
- брокер видит соседей, но адрес в presence приходит только от тех,
  кто уже в сети **в этот момент**.

Итог: кто не был в сети в момент старта — не достижим напрямую, пока его
снова не найдёт общий брокер. После переустановки или смены сети —
«потеряли друг друга».

## 2. Решение

**Файл-азбука адресов** рядом с файлом custody:
`<filesDir>/apu_peer_addresses.json` (там же, где `apu_relay.sqlite` —
путь ядро уже получает, отдельного FFI не нужно).

Ядро само ведёт файл: читает при старте, записывает при каждом новом
адресе, убирает неактуальное при записи. Kotlin добавляет одно: при
старте движка заполняет список «своих» (контакты + проверенные +
групповые админы) существующим методом `set_presence_audience` — тогда
личное presence в первую же минуту после старта постучится к сохранённым
адресам, а онлайн-соседи ответят presence **с актуальным адресом** и
файл обновится. Это и есть «проверил связь — нашёл на связи — спросил
свежий адрес».

### Формат файла (v1)

```json
{
  "v": 1,
  "entries": [
    { "id": "pk_…", "addr": "203.0.113.5:443", "seen": 1758200000000 },
    { "id": "pk_…_public", "addr": "198.51.100.9:443", "seen": 1758200060000 }
  ]
}
```

- `id` — node_id пира (ключи с суффиксом `_public` — WAN-вариант того же
  узла, в памяти ядра они тоже отдельные ключи — храним так же);
- `addr` — `ip:port`, как в `peer_addrs`;
- `seen` — время (мс) последнего обновления адреса.

Запись атомарная: `apu_peer_addresses.json.tmp` + `rename` — телефон не
застрелится на полупустом файле.

### Правила жизни файла

| Параметр | Значение | Почему |
|---|---|---|
| TTL записи | **30 дней** | не видели узла месяц — адрес мёртв, убираем при записи; вернётся сам по presence/DHT, когда понадобится |
| потолок | **1000 записей** (самые свежие) | больше «своих» у абонента физически не будет; файл ~100 КБ |
| троттлинг записи | не чаще **раз в 15 с** | presence-обмен частый, диск — нет |
| финальный flush | при `stop()` движка | последнее, что успеваем сохранить |
| при старте | load → seed → prune (то же TTL/потолок) | файл никогда не растёт бесконечно |

### Кто пишет (7 мест)

Все — существующие точки, где ядро уже узнало адрес пира:

1. DHT-ответ (требовали адрес у соседа — получили адрес цели + ≤3
   ближайших) — `handle_direct_frame`, ветка `dhtr`;
2. mDNS-сосед в одной Wi-Fi (LAN-адрес);
3. mDNS-сосед: alias по полному имени (старые чаты);
4. mDNS-сосед: публичный адрес;
5. брокер-presence: публичный адрес в общем presence;
6. явная привязка (invite/привязка из приложения);
7. **входящее QUIC-соединение** (новое): реальное адрес соединения —
   самый свежий адрес, который вообще возможен. Раньше он хранился
   только в пуле соединений и терялся при его закрытии; теперь хук
   `on_inbound` при «усыновлении» записи его в азбуку.

### Что НЕ меняется

- Протокол: **новых кадров нет** (ни `ppres`, ни `dhtq/dhtr`, ни брокер
  не тронуты).
- UDL/FFI: **новых функций нет** (`set_presence_audience` уже в
  `lib.udl`, просто теперь её вызывают).
- Маршрутизация, `peer_addrs` как структура, лимиты presence (256/32/60 с)
  — без изменений. Азбука — слой под ними: «память между запусками».

## 3. Как это чинит сценарии владельца

| Сценарий | Было | Стало |
|---|---|---|
| Перезагрузка телефона | список адресов пуст, «свои» пуст | азбука загружена в первую строку `start()`; Kotlin сразу засевает «своих»; ≤60 с — personal presence постучал всем сохранённым адресам; онлайн-ответившие обновили файл свежими адресами |
| Смена связи (Wi-Fi ↔ мобильная) | новый NAT-адрес известен только по брокеру, пока оба онлайн | первый же обмен (presence/сообщение/входящий QUIC) записывает новый адрес в файл; следующий старт стучит уже по нему |
| Переустановка приложения | всё потеряно | личность восстанавливается (ключи/сундук), азбука пустая — но «свои» засеяны, первый же онлайн-сосед вернёт адрес, DHT дополнит остальных |
| 1:1 в оффлайне | очередь на ретрансляторе, адрес получателя забыт | адрес в азбуке: дошли до него напрямую — доставили; не дошли — очередь на ретрансляторе как раньше, но при появлении адрес уже известен |

## 4. Где что в коде

- `rust-core/src/resilience/address_book.rs` (новый) — сам модуль:
  `open()` (load+prune), `seed()` (в `peer_addrs`), `record()`, `flush()`,
  атомарный save, unit-тесты формата/лимита/TTL.
- `rust-core/src/engine/core.rs` — поле `address_book`; seed в `start()`;
  `flush()` в `stop()`; `record()` в 6 старых точках записи; хук
  `on_inbound` в `direct_transport` (7-я точка).
- `rust-core/src/network/direct_transport.rs` — необязательный колбэк
  `on_inbound(sender, addr)` при усыновлении входящего соединения.
- `android-app/…/data/RustBridge.kt` — `setPresenceAudience(ids)` (обёртка
  над существующим FFI, try/catch + лог).
- `android-app/…/data/swarm/SwarmPeerDirectory.kt` — `audienceIds()`:
  контакты ∪ проверенные обмены ∪ владельцы/админы групп (та же база
  знаний, что у роёв).
- `android-app/…/service/CoreServerService.kt` — после `Engine OK` —
  запуск посева «своих».

## 5. Как проверять на телефонах (после релиза)

Фильтры logcat:

- `ADDRESS BOOK` — загрузка при старте (`loaded N entries`),
  запись/flush, prune;
- `PRESENCE K4: personal presence sent to X/Y own peer(s)` — после
  старта должно быть `X>0` (раньше у нового старта `Y=0`);
- `DIRECT: adopted inbound connection` — входящие, адрес ушёл в азбуку;
- файл: `files/apu_peer_addresses.json` (app-private, не в бэкапах).

Непроверено на экранах/телефонах: вся реализация (первый компилятор —
CI; JVM-частичная проверка диагностической компиляцией).
